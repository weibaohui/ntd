## 1. 修复内容

全部改动在 `backend/src/services/loop_runner.rs`（无 schema/API 变更）：

| 改动 | 说明 |
|------|------|
| 新增纯函数 `task_status_for_loop_status` | loop 终态 → 任务状态映射（success/partial→success，failed/capped_*→failed，其余→running），从启动路径内联代码抽出，供两路径共用与单测。 |
| 新增纯函数 `execution_duration_secs` | 执行时长计算，从启动路径内联代码抽出。 |
| 新增 `sync_task_status` | 按 loop 执行终态回写 `tasks.status`；启动路径改为调用它，resume 路径新增调用。 |
| 新增 `broadcast_loop_finished` | 收集统计（含时长、累计 Token）并广播 `LoopFinished`；resume 路径新增调用。 |
| 新增 `complete_run` | run 结束的统一收尾：Finished→同步+广播；Paused→仅同步（多审批环节 loop 会再次暂停）；Err→终态化+异常处理 Todo+WS 刷新+同步+广播。 |
| resume 路径接入收尾 | `resume_loop_execution` 的 spawn 由"只打日志"改为 `complete_run`；就地终态化分支（`on_success=end` 无下一步）补 `sync_task_status` + `broadcast_loop_finished`。 |
| 启动路径修连带缺陷 C | Err 分支在 `finish_loop_execution` 之后补一次 `sync_task_status`——此前同步发生在终态化前读到 running，run 失败的任务会永远"进行中"。 |

### 明确未做

## 3. 安全反思

- **无新输入面**：不新增 API、不新增用户输入处理；`sync_task_status` 的 id 均来自数据库记录。
- **行为一致性**：两路径共用同一映射函数，消除了"启动路径一套、恢复路径没有"的分叉；后续改映射只改一处。
- **失败不扩散**：`sync_task_status` / `broadcast_loop_finished` 均为尽力而为（读不到记录静默返回、发送用 `let _ =`），收尾失败不会中断 resume 主流程；Err 分支保证 loop_execution 必落终态，不再出现"永远 running"的僵尸执行。
- **并发**：审批与收尾在同一 spawn 内顺序执行；重复审批已被 NTD-004 的状态校验拦截，不会触发两次 resume/收尾。

## 4. 已知限制与待改进

1. resume 路径终态时，绑定飞书对话的场景只收 LoopFinished 广播（按 workspace 推送配置），不会像启动路径那样"回复原对话"——需透传 receive_id 上下文，另立优化。
2. `spawn_run` 启动路径的收尾块仍是大型内联闭包（飞书回复两个分支在其中），本次只抽出可安全共用的部分；彻底统一两路径收尾结构建议结合飞书上下文传递一起做。
3. 存量 `tasks.status` 已是"进行中"但执行早已结束的历史数据不会自动修复，可通过重新触发执行或在 DB 层一次性订正（本次未提供订正脚本）。
