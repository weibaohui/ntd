## 3. 触发条件（Trigger Conditions）

### 3.1 前置条件

- 系统状态：某 loop（工艺实例）的环节配置了 `human_approval` 类型门禁，且该环节执行完成
- 数据状态：`loop_step_executions.status = 'pending_approval'`，`loop_step_execution_gates.status = 'pending'`，`loop_executions.status = 'running'`

### 3.2 输入条件

- 请求：前端工艺执行看板（ProcessExecutionBoard）点击「通过」或「拒绝」
  → `POST /api/v1/workspaces/{ws}/loops/{id}/executions/{eid}/steps/{seid}/gates/{gid}/approve`，body `{approved: bool, comment?}`

### 3.3 时序 / 并发条件

- 无并发要求，单次请求必现

## 4. 实际行为（Observed Behavior）

1. **审批后 loop 不继续（主缺陷，后端）**：上述请求只把 `loop_step_execution_gates` 记录更新为 `passed`/`failed` 即返回；`loop_step_executions` 保持 `pending_approval`、`approval_status` 不写入；`resume_loop_execution` 不被调用。loop 永远停在该环节，`loop_executions.status` 永远为 `running`。发生频率：必现。
2. **「拒绝」按钮实际发出"通过"（前端）**：`ProcessExecutionBoard.tsx` 的「通过」「拒绝」两个按钮调用同一 handler，`approved` 由 `!(gate.status === 'passed')` 计算，pending 状态下恒为 `true`，点「拒绝」发出的也是 `approved: true`。发生频率：必现。
3. **任务（Todo）界面无审批入口（交互缺失）**：`TaskDetailPanel.tsx` 只把门禁渲染为只读标签，任务视角下用户能看到环节卡住但找不到审批操作处。
4. **resume 通过判定依赖评分（后端隐患）**：`resume_loop_execution` 以 `rating >= min_rating` 判定走向；gate 审批路径不写评分时 `rating = NULL → 0`，若 `min_rating = 0` 则拒绝也会被判定为"通过"并走 `on_success` 分支。

## 5. 期望行为（Expected Behavior)

- 点击「通过」：gate → `passed`，环节 → `success`，写入 `approval_status='approved'` 与审批意见，loop 从下一环节继续执行。
- 点击「拒绝」：请求携带 `approved: false`，gate → `failed`，环节 → `failed`，loop 按 `on_rating_fail` 策略流转。
- 任务（Todo）详情界面在环节处于 `pending_approval` 时提供「通过/拒绝」操作入口。
- 重复审批（环节已非 `pending_approval`）应返回 400 错误而非静默覆盖。

## 6. 行为偏差定义（Deviation）

> 在【工艺环节进入 pending_approval 后，用户在看板点击通过/拒绝】下，系统实际执行了【仅更新 gate 记录即返回，loop 永久停滞；且"拒绝"被当作"通过"发送】，但期望执行的是【更新环节终态并恢复 loop 执行，且通过/拒绝语义与按钮一致】。

## 7. 影响范围（Impact)
