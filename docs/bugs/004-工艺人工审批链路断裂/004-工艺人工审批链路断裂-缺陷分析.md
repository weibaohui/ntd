# NTD-004 工艺人工审批链路断裂 — 缺陷分析

| 修改人 | 修改时间 | 修改内容 |
|--------|---------|---------|
| AI(claude) | 2026-07-29 | 初始版本 |

---

## 1. 数据流链路

```
环节执行完成
  → phase_driver::execute_step（backend/src/services/process/phase_driver.rs）
      gate_evaluator 评估 human_approval 门禁 → 恒返回"未通过 + 等待人工"
      → step_execution.status = 'pending_approval'，StepOutcome.paused = true
  → LoopRunner 主循环收到 paused → return Paused（loop_runner.rs:877-879）
      主循环退出，loop_execution 保持 'running'，无内存等待，纯 DB 状态定格

【审批动作（新接口，断裂路径）】
ProcessExecutionBoard「通过/拒绝」
  → POST .../gates/{gid}/approve → handlers/process.rs::approve_gate
      仅 update_loop_step_execution_gate(gid, passed|failed)   ← 到此为止
      ✗ 未更新 step_execution.status / approval_status
      ✗ 未调用 resume_loop_execution
      → loop 永久停滞

【审批动作（旧接口，完整路径，对照组）】
StepExecList 评分滑块
  → POST .../steps/{seid}/approve → handlers/loop_.rs::approve_step_execution(_v1)
      db.approve_step_execution：写 rating / status(success|failed) / approval_status='approved'
      → resume_loop_execution（loop_runner.rs:387）
          找 approval_status='approved' 的环节 → rating >= min_rating 定走向 → run_inner_from 续跑
```

## 2. 根因（三处叠加）

### 根因 1（主因）：新旧两套审批 API 语义未打通

系统存在两代审批接口：

| 接口 | Handler | 语义 | 链路 |
|------|---------|------|------|
| `POST .../steps/{seid}/approve` | `loop_.rs:576 / 2726` | 评分制（rating vs min_rating） | 完整 ✅ |
| `POST .../gates/{gid}/approve` | `process.rs:858` | 布尔制（approved: bool） | **只完成 1/3** ❌ |

`approve_gate` 实现时只写了"更新 gate 记录"这一步，遗漏了审批链路的后两步——更新环节终态（含 `approval_status='approved'`）与触发 `resume_loop_execution`。而 resume 的查找条件（`loop_runner.rs:414`）恰好依赖 `approval_status='approved'`，该字段在全仓库仅由旧接口路径写入，因此新接口审批后 resume 即使被调用也找不到目标环节。

### 根因 2（前端放大器）：通过/拒绝按钮共用一个 handler

`ProcessExecutionBoard.tsx:63`：`const approved = !(gate.status === 'passed')`。按钮只在 gate 为 `pending` 时渲染，故 `approved` 恒为 `true`；「拒绝」按钮（L204-211）调用同一 handler，语义被颠倒。

### 根因 3（隐藏判定错误）：resume 用评分而非环节终态定走向

`loop_runner.rs:453-455`：`gate_passed = rating.unwrap_or(0) >= min_rating.unwrap_or(0)`。审批 handler 已经算出了终态 `status`（success/failed），resume 却不使用它而重新用评分推导。在布尔审批路径下：若拒绝时不写评分，`rating=NULL→0`、`min_rating=0` 时 `0>=0` 成立，拒绝会被误判为通过并走 `on_success` 分支。

## 3. 修复方案（已获用户确认）

1. **后端 `approve_gate` 补全链路**：
   - 校验：环节存在且 `status='pending_approval'`；gate 属于该环节且为 `human_approval` 类型、`status='pending'`（防越权/重复审批）；
   - 更新 gate → `passed`/`failed`；
   - 复用 `db.approve_step_execution` 写环节终态：通过→`success`/评分 100，拒绝→`failed`/评分 0，并写 `approval_status='approved'` + 审批意见；
   - 发 `ExecEvent::ReviewStatusChanged` 触发前端刷新；
   - 调 `resume_loop_execution` 续跑。
2. **后端 resume 判定修正**：`gate_passed` 改为 `approved.status == "success"`。旧路径语义不变（其 status 本就由 `rating >= min_rating` 推出），新路径拒绝时不再误判。
3. **前端看板**：拆分「通过」「拒绝」传参，分别发 `approved: true/false`；审批后刷新看板。
4. **前端任务界面**：`TaskDetailPanel` 在环节执行状态为 `pending_approval` 时渲染「通过/拒绝」按钮（复用 `approveGate` API），让任务视角可直接审批。

## 4. 影响面与回归点

- 旧评分审批路径（StepExecList → `approve_step_execution_v1`）：行为必须保持不变（resume 判定修正后语义等价，需回归）。
- 看板审批后 loop 续跑：新增端到端验证。
- 重启后待审批状态保留 + 重启后审批可续跑：回归验证。
- 工艺路径暂停时 `failed` 计数器已 +1（loop_runner.rs:832-839），resume 时又计一次 completed/failed（loop_runner.rs:463-468）——**既有的计数口径问题，不在本次修复范围**，列入已知限制。
