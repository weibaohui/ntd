## 1. 修复内容

### 后端

| 文件 | 改动 |
|------|------|
| `backend/src/handlers/process.rs` | `approve_gate` 补全完整链路：runner 可用性前置校验 → 环节归属与 `pending_approval` 状态校验（`load_pending_step_execution`）→ gate 类型/pending 校验（`validate_pending_human_gate`）→ 更新 gate（passed/failed）→ 复用 `db.approve_step_execution` 写环节终态（通过→success/100，拒绝→failed/0）+ `approval_status='approved'` + 审批意见 → 发 `ReviewStatusChanged` WS 事件 → `resume_loop_execution` 续跑。校验逻辑抽为纯函数 `ensure_step_approvable` / `ensure_gate_approvable`。 |
| `backend/src/services/loop_runner.rs` | resume 的通过判定由 `rating >= min_rating` 改为按环节终态 `approved_step_passed(status)`（拒绝审批在 rating=0、min_rating=0 下不再被误判为通过）。旧评分路径语义不变（其 status 本就由评分阈值推出）。 |
| `backend/src/db/loop_.rs` | `count_pending_approvals_by_execution_ids` 统计条件由仅 `approval_status='pending'` 扩展为 `OR status='pending_approval'`，覆盖工艺（phase_driver）暂停路径——该路径不写 approval_status，此前前端所有「N 待审批」角标对工艺路径恒为 0。 |
| `backend/src/handlers/tasks.rs` | `get_task_detail` 的 executions 增加 `pending_approval_count` 字段，支撑任务界面引导标记。 |

### 前端

|------|------|

## 3. 安全反思

- **越权**：`approve_gate` 新增三重校验——execution 必须属于路径中的 loop（防路径参数伪造，与旧接口一致）；环节必须为 `pending_approval`；gate 必须属于该环节、为 `human_approval` 类型且 `pending`。非人工门禁（AI 评审/脚本校验）无法借道本接口篡改结果。
- **幂等**：重复审批返回 400（环节已非 pending_approval / gate 已评价），不会覆盖终态或重复触发 resume。
- **半完成状态**：runner 可用性校验前置到任何写库之前，避免"审批已落库但 resume 失败"的中间态。
- **注入**：审批意见作为参数化绑定写入（SeaORM ActiveModel），前端以文本渲染（React 默认转义），无 SQL/XSS 注入面；计数 SQL 的 id 列表来自数据库整型，非用户输入。
- **并发**：两个客户端同时审批时，后到请求因状态校验失败返回 400；resume 由先到请求触发一次。

## 4. 已知限制与待改进

1. **人工审批无超时**：一直不审批 loop 永远停在 running。`GateDefinition.timeout_secs` 目前仅对 AI 评审门禁生效，human_approval 不消费该字段。是否支持"超时自动失败/提醒"需另立需求。
2. **计数口径**：工艺路径暂停时已计一次 failed（loop_runner.rs 暂停分支前），resume 后又按终态计一次 completed/failed——暂停环节的 failed 计数偏多。属既有口径问题，本次未动。
3. **审批入口层级**：任务视角的审批仍需「执行历史 → 展开 → 看板」两步到达按钮；本次以引导 Tag 提示。如需在任务行上直接审批（免展开），需执行列表接口携带 gate/环节 id，另立优化。
4. **存量测试基建**：`check_*.cjs` 调试脚本依赖 `agent-browser` 二进制、onboarding spec 的 baseURL 为 5173，与本项目 `make dev`（18088）不一致，建议后续统一。
