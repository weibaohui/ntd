## 4. 实际行为（Observed Behavior）

共 3 个关联问题：

### 问题 A：工艺列显示 `#0-#0--`（格式错误）
- **触发**：委派任务（`template_id=Some(0)`）或环路任务未选工艺（`template_id=0`）
- **现象**：「工艺」列 Tag 内显示 `#0-#0--`，而不是预期的占位符 `—`
- **根因线索**：`formatProcessText` 只判 `id == null`，`0` 被当作有效 ID 进入拼接

### 问题 B：无工艺 / 委派任务的状态显示为「待执行」（与实际不符）
- **触发**：新建委派任务，首帖已触发讨论区执行，但任务主状态 `status` 仍为 `pending`
- **现象**：列表「状态」列显示「待执行」灰色 Tag，但实际执行已启动
- **根因线索**：委派任务创建时初始状态走 DB 默认 `pending`，未同步为 `running`；执行完成/失败回写时可能只更了 `loop_executions.status`，没更 `tasks.status`

### 问题 C：委派任务在列表中无委派信息显示
- **触发**：列表中存在委派任务
- **现象**：「工艺」列显示错误格式（见 A），无任何委派处理人信息，用户无法区分「环路任务」与「委派任务」，也看不到委派给了谁
- **根因线索**：TaskItem 已带 `execution_mode` / `assignee_kind` / `assignee_name` / `auto_continue`，但前端列表完全未利用

## 5. 期望行为（Expected Behavior）

- **问题 A**：`template_id` 为 `None` 或 `0`（或无效值）时，工艺列显示灰色 `—`（同无工艺来源）
- **问题 B**：
  - 新建委派任务首帖触发后，`tasks.status` 应为 `running`（进行中）
  - 执行成功回写时，`tasks.status` 同步为 `success`
  - 执行失败回写时，`tasks.status` 同步为 `failed`
  - 与环路任务的状态口径一致
- **问题 C**：
  - 委派任务在「工艺」列位置显示委派信息：蓝色 Tag `委派给：<处理人名>（<专家/执行器>）`，若开自动接力追加 `🚀自动接力`
  - 环路任务「工艺」列保持原三段式显示不变
  - 可选：状态 Tag 旁加极小徽标（`环路` / `委派`），一眼区分任务类型

## 6. 行为偏差定义（Deviation）

> **三问题汇总：**
> 1. 工艺列 `id=0` 时没走占位分支，错误输出 `#0-#0--`；
> 2. 委派任务主状态 `status` 没与实际执行同步（初始、成功、失败三处），导致「待执行」Tag 与执行进展不一致；
> 3. 委派任务的列表缺少委派信息（处理人、类型、接力）透出，用户无法在列表层感知「这是委派任务」。

## 7. 影响范围（Impact）

- 受影响模块 / 功能：
  - 后端：`create_delegate_task`、执行完成回写路径（task.status 同步）
  - 前端：`formatProcessText`、`TasksTableView`「工艺」列渲染、`TasksCardView`、`TasksKanbanView`（保持口径一致）
- 受影响用户或场景：所有使用委派功能的用户；任务列表一眼判断任务类型与进展的能力受损
- 风险：

  - 认知成本：用户必须点进详情才知道这是委派任务 + 委派给谁

- 看板 / 卡片视图如需同步委派信息显示，作为同口径扩展
