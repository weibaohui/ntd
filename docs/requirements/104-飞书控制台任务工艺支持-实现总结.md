## 1. 实现了什么

飞书 `/help` 斜杠命令打开的「NTD 控制台」交互卡片从 4 Tab 扩展为 6 Tab（状态/事项/环路/任务/工艺/工作空间）：

- **任务页**：按 bot 当前工作空间列最近 20 条任务（每页 10 条），显示状态图标（⏸️/⏳/✅/❌）、标题与执行方式标签（环路 / 委派@处理人）。环路模式任务带「执行」按钮（`act:/runtask <id>`），复用任务描述经绑定的环路触发一次新执行；委派任务纯文本展示、无按钮。
- **工艺页**：列出系统内置 + 当前工作空间用户模板（最多 20 条，每页 10 条），纯查看（名称 · 复杂度 · 版本 · 系统/用户），不提供安装/实例化。
- **分页**：`nav:/tasks <page>`、`nav:/processes <page>`，与事项/环路页同形态（上一页/下一页/返回状态）。

## 3. 关键实现点

### 3.1 复用既有管线，零新框架

新 Tab 完全复用事项/环路的链路：`assemble_help_card_state` 组装 → `build_help_console_card` 渲染 → `handle_card_callback` nav/act 路由 → `patch_after_action` 刷新。不改 HTTP API、DB 层与前端。

### 3.2 任务再执行的触发等价路径

飞书层拿不到 `loop_trigger_dispatcher`（仅在 AppState），故用 `LoopRunner::spawn_run(loop_id, {requirement: 任务描述, source:"task"}, …)` 触发——meta 口径与 Web 端 `dispatch_manual_with_meta` 一致；随后 `update_loop_execution_task_id` 把新 loop_execution 绑定回任务。`spawn_run` 返回 -1（创建执行失败）时直接报失败，杜绝假成功。

### 3.3 评审驱动的小函数拆分

- `validate_task_runnable(task, workspace_id) -> Result<loop_id, String>`：归属/模式/环路三重校验纯函数化，可单测。
- `parse_nav_page(action) -> Option<(Tab, page)>`：四个列表 Tab 的分页解析收敛到一个纯函数，`handle_nav_action` 由 4 个复制分支变 1 个通用分支。
- `bot_workspace_id(context) -> Result<Option<i64>, String>`：区分「未设置工作空间」与「DB 查询失败」。
- `load_task_items` / `load_process_items`：查询 + take(20) + 降级日志内聚，止住 `assemble_help_card_state` 的持续膨胀。

### 3.4 顺带修正的历史页行为漂移

历史页「返回控制台」按钮值原为占位串 `nav:/help task`（旧代码里 task 不是有效 Tab，落到默认状态页）；104 起 task 成为真实 Tab，若不改会漂移到任务页。改为显式 `nav:/help status`，行为与历史一致。

## 4. 测试与验证

- 新增单测 20 个（渲染 6 + 回调解析/校验 5 + 组装映射 7 + 分页 2），清单见 `docs/testing/104-飞书控制台任务工艺支持-测试.md`。

## 5. 已知限制或待改进点

- 委派任务在飞书侧不可执行（需求 2a：讨论区 @处理人 接力路径不接入卡片）。
- 工艺页仅查看；安装/实例化仍需 Web 端（需求 3c）。
- 任务正在运行时点「执行」不防重入（与环路页同口径），防重入留待后续迭代。
- `act_run_task` 完整 async 链路无集成测试环境，核心逻辑以纯函数形态覆盖。
