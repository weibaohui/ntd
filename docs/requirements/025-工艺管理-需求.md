# 1. 背景（Why）

ntd 已经具备 Loop Studio 多步骤自动化工作流（`loops` / `loop_steps` / `loop_executions`）、
AI/人工评审门禁、`blackboard` 结论传递、专家/技能注入等能力。
但在实际重复性工作中（如大项目开发、小功能开发、口头需求转需求文档），
用户仍需要把"做这件事的标准套路"显式地定义出来：

- 有哪些**阶段**（phase）
- 每个阶段有哪些**环节**（link/step）
- 每个环节该用哪个**专家**、哪个**skill**
- 每个环节该产出什么**产物**（artifact）
- 产物如何按**验收标准**被客观评价
- 评价不通过时如何**返工**并留下记录
- 多个阶段如何有机结合成一条**工艺流水线**

本需求目标是把 Loop Studio 升级为"工艺管理"：
内置可复用的工艺模板、阶段化组织、结构化产物、客观质量门禁、自动流转与审计。

# 3. 非目标（Explicitly Out of Scope）

- 不替换现有通用 Todo/Loop；工艺管理是 Loop Studio 的增强 specialization。
- 不实现 BPMN 通用工作流引擎（不引入并行网关、泳道、事件子流程等复杂控制流）。
- 不改变现有 AI 执行器适配层；继续复用 `executor_service`、`auto_review`、`expert` 模块。
- 不实现通用"撤销副作用"回滚；只保留执行记录与产物快照。
- 首期不实现工艺模板的在线可视化编排器；先通过 YAML 定义 + 导入使用。

# 4. 使用场景 / 用户路径

## 场景 A：标准需求交付（4P12S 裁剪）

1. 用户在工艺库选择"标准需求交付"工艺。
2. 一键实例化到当前工作空间，生成一个 Loop，包含阶段：
   - 需求：生成 PRD（产品专家 + `4p12s-prd` skill）
   - 设计：生成用户故事、技术设计、验证计划
   - 编码：Tasking、TDD 开发、集成测试
   - 验证交付：E2E 测试、Git 提交、测试环境部署
3. 每个环节自动执行，产物（`PRD.md`、`user-stories.md`、`design.md`、`TASK*.md`、测试报告、`delivery-state`）被捕获。
4. AI 门禁根据验收标准评价产物；不通过则返工到对应环节，并记录 `repair-log`。
5. 关键节点（PRD、技术设计）触发人工确认后继续。
6. 用户可在看板查看每个阶段的进度、产物、门禁结果、返工记录。

## 场景 B：轻量任务（Superpowers）

1. 用户选择"轻量任务"工艺（阶段少、门禁轻，对应材料 Superpowers）。
2. 系统自动创建 Loop 与对应 step todos。
3. 执行 brainstorming → writing-plans → TDD → code-review → verification → reflect。
4. 编码环节产物为某个文件路径，门禁检查文件存在并运行 `cargo clippy` 脚本校验。
5. 通过则进入下一环节，不通过则返工并记录 `repair-log`。

## 场景 C：工艺审计

1. 用户打开工艺执行看板。
2. 看到某次工艺实例的每个阶段状态、每个环节的产物列表、门禁通过/失败原因、返工次数、审批人意见。
3. 可导出审计记录为 Markdown。

# 6. 约束条件

## 6.1 技术约束

- 后端：Rust + Axum + SeaORM + SQLite；新增实体需要 migration。
- 前端：React + TypeScript + Ant Design + Vite。
- 复用现有 Loop 执行引擎、自动评审、专家注入、内置资源同步机制。
- 不引入新的外部服务或数据库。

## 6.2 架构约束

- 工艺模板与 Loop 实例解耦：模板是只读/版本化定义，Loop 是运行时可执行的副本。
- 阶段/环节数据模型向后兼容：现有 `loop_steps` 无 `phase_id` 的环节视为"未分组"。
- 门禁引擎必须是可扩展的插件式结构，便于后续新增门禁类型。

## 6.3 安全约束

- 产物路径必须限制在工作空间目录内，禁止目录遍历。
- `script_check` 门禁首期仅允许执行项目内已存在的脚本文件或白名单命令，禁止任意命令注入。
- 人工审批接口必须校验用户对工作空间的权限。

## 6.4 性能约束

- 工艺模板列表接口响应 < 500ms（依赖内存缓存）。
- AI 门禁评审应受 `limits_config.max_total_tokens` 约束，防止无限消耗 token。

  display_name: 标准需求交付工艺

            type: file

      - id: req-02

        review_type: human
        gates:
          - type: human_approval
        on_success: next
        on_gate_fail: goto:req-01
  - id: design
    name: 技术设计
    ...

# 9. 验收标准（Acceptance Criteria）

- **AC1** 如果用户执行 `ntd process list`，则能看到至少 3 条内置工艺模板。
- **AC2** 如果用户调用安装接口，则在 2 秒内在当前工作空间生成对应的 Loop、阶段、环节与 step todos。
- **AC3** 如果一个环节配置了 `expected_artifacts`，则环节执行完成后，`loop_step_artifacts` 中至少出现对应记录；若产物缺失，门禁应失败。
- **AC4** 如果一个环节配置了 `ai_criteria_review` 门禁，则 AI 评审结果包含 `pass`（bool）、`score`（0-100）、`issues`（数组），并写入 `loop_step_execution_gates`。
- **AC5** 如果门禁失败且配置了 `on_gate_fail: goto:<step_id>`，则 `LoopRunner` 跳转到指定环节并递增 `rework_count`。
- **AC6** 如果 `rework_count` 达到 `max_rework`，则工艺实例状态变为 `failed` 且不再继续执行。
- **AC7** 如果用户打开工艺执行看板，则能看到阶段进度、环节状态、产物清单、门禁结果、返工次数。
- **AC8** 所有新增公开函数都有单元测试；`cargo clippy --all-targets -- -D warnings` 与 `npx tsc --noEmit` 零告警。

# 10. 风险与已知不确定点

| 风险 | 影响 | 处理方式 |
|------|------|---------|
| AI 门禁评审结果不稳定 | 导致反复返工 | 允许配置 `min_rating` 阈值；评审 prompt 要求结构化 JSON；保留人工审批兜底 |
| 产物捕获依赖 AI 输出格式 | 文件/文本产物可能提取失败 | 提供多种提取策略（标记、正则、整段），并允许手动补充 |
| `script_check` 安全风险 | 任意脚本可能破坏工作目录 | 首期仅支持项目内已存在脚本或白名单命令，路径安全校验 |
| 工艺模板版本更新后实例是否同步 | 行为不一致 | 实例化时复制模板内容到 Loop；后续模板更新不影响已有实例 |
| 同步/扫描 bundled processes 可能影响启动性能 | 启动变慢 | 与现有 bundled 市场一样使用内存缓存，按需失效 |

---

# 11. 非目标（再次明确）

- 不开发独立于 Loop 的全新工作流引擎。
- 不实现工艺模板的拖拽式可视化编辑器（首期）。
- 不做跨工作空间的工艺实例共享/协作。
- 不做已产生副作用（如文件修改、部署）的自动回滚。
