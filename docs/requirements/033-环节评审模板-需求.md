## 1. 背景（Why）

工艺模板（Process）安装后实例化为环路（Loop），环路在执行每个环节（step / YAML 中的 `links[]`）时会触发一次 AI 评审。经代码调查，当前评审模板内容的真实来源是 `review_templates` 表，与工艺 YAML 定义**完全解耦**：

- 评审模板优先级当前只有两级：环路级 `loops.review_template_id` → 全局默认（`review_templates` 表中名为「默认评审任务」的行，其 prompt 来自 `services/auto_review.rs::DEFAULT_REVIEWER_PROMPT` 常量）。
- 环节（`LinkDefinition`）层面只能定制**验收标准**（`acceptance_criteria`），它作为 `{{acceptance_criteria}}` 占位符被注入评审 prompt；但**无法定制评审模板本身**（评审人设、评审维度、输出格式）。
- 工艺 YAML 中没有任何评审模板字段，`installer.rs` 安装时也完全不碰 `review_templates`。

因此用户无法在工艺定义中为每个环节指定专属评审模板，评审行为不可按环节定制。本需求在工艺 YAML 的每个环节新增 `review_prompt` 字段，安装时写入环路、执行评审时优先使用，让每个环节都能拥有自己的评审模板。

## 4. 使用场景 / 用户路径

### 场景 A：为某环节定制专属评审模板

1. 用户在工艺编辑器选中某个环节（link）
2. 在右侧属性面板填写「评审 Prompt」——一段完整的评审指令，可含 `{{original_output}}`、`{{acceptance_criteria}}` 等占位符
3. 保存工艺（版本自动递增）
4. 安装或升级环路
5. 该环节执行完成触发评审时，AI 收到的评审 prompt = 用户填写的 `review_prompt`（占位符已替换）
6. 其它未填写 `review_prompt` 的环节评审行为不变

### 场景 B：环节未填写时的回退

1. 某环节未填 `review_prompt`（列为空）
2. 该环路设置了 `review_template_id` → 使用环路级评审模板
3. 环路级也未设置 → 使用全局「默认评审任务」模板

### 场景 C：仅有 review_prompt、无验收标准的环节

1. 某环节填写了 `review_prompt` 但未填 `acceptance_criteria`
2. 该环节仍会触发评审（用 `review_prompt` 作为模板），因 `review_prompt` 本身已是完整评审指令

## 6. 约束条件

- **占位符替换一致性**：`review_prompt` 是含占位符的模板正文，必须经过 `{{original_prompt}}` / `{{original_output}}` / `{{acceptance_criteria}}` / `{{max_output_chars}}` 替换后再发给 AI，机制与现有评审模板完全一致。
- **完整替代语义**：当 `review_prompt` 非空时，它**整体替代**默认评审模板正文。默认模板内置的 `{{acceptance_criteria}}` 注入不会额外叠加 —— 若用户希望验收标准出现在评审中，需自行在 `review_prompt` 中写入 `{{acceptance_criteria}}` 占位符。
- **触发条件扩展**：环节执行评审的触发条件从「`acceptance_criteria` 非空」扩展为「`acceptance_criteria` 非空 **或** `review_prompt` 非空」。`min_rating` 仍作为评分闸门阈值的外层前置条件（无 `min_rating` 不进入评审分支），不在本次改动范围。
- **向后兼容（YAML）**：旧工艺 YAML 无 `review_prompt` 字段时，serde 反序列化为空串，不影响现有工艺的保存/安装/执行。
- **向后兼容（DB）**：旧环路 `loop_steps.review_prompt` 为 NULL，评审时回退到环路级/默认，行为与现状一致。
- **性能**：`review_prompt` 非空时跳过 `review_templates` 表查询，不增加 DB 负担。
- **安全**：`review_prompt` 由工艺作者定义，信任级别与 `acceptance_criteria` 相同，不做额外内容过滤（与现状一致）。

## 8. 接口与数据约定

| 层 | 位置 | 约定 |
|----|------|------|
| YAML | `phases[].links[].review_prompt` | string，可选，多行；空串/缺省 = 未设置 |
| DB | `loop_steps.review_prompt` | `TEXT NULL`；NULL = 未设置 |
| 运行时 | 评审 prompt 占位符 | 复用 `{{original_prompt}}` `{{original_output}}` `{{acceptance_criteria}}` `{{max_output_chars}}` |
| 解析优先级 | step 级 `review_prompt` 非空 → 用之（跳过查表）；否则 `ensure_review_template(loop.review_template_id)` → 否则全局默认 | |

## 9. 验收标准

1. 在工艺 YAML 中为某环节写 `review_prompt`，安装后 `loop_steps.review_prompt` 有对应值
2. 该环节执行评审时，AI 实际收到的评审 prompt = 用户写的 `review_prompt`（占位符已替换）
3. 未写 `review_prompt` 的环节，评审行为与现状完全一致（使用环路级/默认模板）
4. 仅写 `review_prompt`、无 `acceptance_criteria` 的环节也能触发评审（触发条件扩展生效）
5. 无 `review_prompt` 字段的旧工艺可正常保存、安装、执行，无回归
6. `cd backend && cargo test` 全量通过；`cargo clippy --all-targets -- -D warnings` 零告警
7. `cd frontend && npx tsc --noEmit` 零错误
8. Playwright 验证：编辑器能编辑「评审 Prompt」，保存后重新打开工艺，值被保留

## 10. 风险与已知不确定点

- **`review_prompt` 与 `acceptance_criteria` 的语义边界**：用户可能误以为填了 `review_prompt` 后验收标准仍会自动注入。已在约束「完整替代语义」中明确：需自行在 `review_prompt` 中引用 `{{acceptance_criteria}}`。设计文档与 UI placeholder 需就此给出清晰提示。
- **prompt 注入**：`review_prompt` 最终拼入 AI 请求。因内容由工艺作者定义（信任级别同 `acceptance_criteria`），按现状不做过滤；若未来开放给非信任用户需重新评估。
- **环路升级（upgrade）路径**：`installer.rs` 的 `upgrade_process_template_loop` 需同步把新版 `link.review_prompt` 写回已有 `loop_steps`，避免升级后环节评审模板停留在旧值。
