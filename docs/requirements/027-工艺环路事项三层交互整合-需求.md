# 1. 背景（Why）

系统的核心心智模型是四层执行链路：

```text
任务 (tasks) ──选工艺创建──▶ 工艺 (process_templates) ──实例化──▶ 环路 (loops) ──环节引用──▶ 事项 (todos)
```

**数据层这条链路已完整存在**（`tasks.template_id/loop_id`、`loops.process_template_id`、`loop_steps.todo_id`，见 `docs/design/025-工艺管理-设计.md` §3 映射表），**但交互层是断裂的**。用户无法在任何页面直观感知「这个工艺产生了哪些环路」「这个环路来自哪个工艺」「这个环节对应哪个事项」。

已确认的交互断裂点（现状代码证据）：

| # | 断裂点 | 证据 |
|---|--------|------|
| B1 | 工艺详情只展示裸 YAML 文本，阶段/环节无结构化可视化 | `frontend/src/components/ProcessPage.tsx:248-260` |
| B2 | 工艺 → 实例环路不可达：无「该工艺的实例列表」，后端仅有 `loop_count` 计数 | `backend/src/handlers/process.rs:486`；前端 `TasksPage.tsx:42` 靠客户端过滤 |
| B3 | 安装工艺成功后不跳转，仅 `message.success` | `ProcessPage.tsx:84`（响应中本有 `loop_id`） |
| B4 | 环路详情看不出它来自哪个工艺模板、哪个版本快照 | `LoopStudioDetailPanel.tsx` 无 process 渲染（`LoopDto` 已带 `process_template_id`） |
| B5 | 环路流程图节点显示 `#todo_id 标题` 但不可点击跳事项 | `frontend/src/components/loop-flow/LoopFlowGraph.tsx:314` |
| B6 | 事项详情页不显示被哪些环路引用（仅卡片视图有 `ReferencingLoops`） | `TodoDetail.tsx` 无 loop 内容；`TodoCenterCard.tsx:292` |
| B7 | 工艺入口在导航「配置」组，与技能/专家并列，而非工作区主链路 | `frontend/src/components/shell/LeftRail.tsx:111` |
| B8 | `ProcessDashboard.tsx` 为死代码（定义后无引用）；`process_templates.previous_version_id`（v72 迁移）未同步进 sea-orm 实体 | 全仓库无引用；`backend/src/db/migration/v72.rs:43` vs `entity/process_templates.rs` |

环路侧已有良好的流程图（`LoopFlowGraph`）与执行卡片（`loop-kanban`）体验，工艺侧却退化为 YAML——**同一结构的两种形态，展示质量倒挂**。

# 3. 非目标（Explicitly Out of Scope）

- ❌ 不做工艺的可视化**编辑**（拖拽编排 YAML），本期只读展示；编辑属 M3 可视化编排器范围（`docs/design/025-工艺管理-M3-设计.md` §3.4）
- ❌ 不改工艺 YAML 的 schema 与实例化逻辑（`installer.rs` 不动）
- ❌ 不改触发器、门禁、审批等运行时行为
- ❌ 不做移动端适配的专项设计（移动端保持现状，新组件仅桌面端）
- ❌ 不重命名 tasks/todos 概念（命名双轨问题单独立项，不在本期）

# 4. 使用场景 / 用户路径

## 场景 1：从工艺到环路的正向钻取

1. 用户打开左侧导航「工艺」（位于工作区组，顺序：任务 → 工艺 → 环路 → 事项）
2. 点击工艺卡片打开详情，默认看到「流程图」Tab：阶段泳道 + 环节节点 + 连线，节点带 skill/产出/验收标识
3. 点击某环节节点，弹出环节详情卡：prompt 模板、skill 列表、预期产出、验收标准
4. 切到「实例环路」Tab，看到该工艺已安装的环路列表（名称、状态、版本、创建时间）
5. 点击某环路，跳转 `/#/loops?id=x`，顶部面包屑显示「来源：工艺A v1.2」，点击可回到工艺详情

## 场景 2：安装工艺后立即看到实例

1. 用户在工艺详情点击「安装」
2. 安装成功后自动跳转 `/#/loops?id={新loop_id}`
3. 环路详情顶部面包屑显示来源工艺，用户立即理解「工艺→环路」的实例化关系

## 场景 3：从环路到事项的向下钻取

1. 用户打开环路详情，流程图节点显示 `#todo_id 事项标题`
2. 用户点击节点上的事项标题，跳转 `/#/items?id=x`
3. 事项详情页展示「所属环路」区块（环路名 + 环节名），点击回到环路

## 场景 4：任务视角的全链路追溯

1. 用户创建任务（选工艺环路 + 需求描述）
2. 任务详情页顶部链路：`工艺A v1.2 › 环路B`，内嵌工艺执行看板
3. 用户从任务 → 工艺执行看板 → 环节 → 事项，全程有链路可循

# 6. 约束条件

## 6.1 技术约束

- 后端：Rust (Axum + SeaORM)，`cargo clippy --all-targets -- -D warnings` 零告警；生产代码禁止 `.unwrap()`/`.expect()`/`panic!`
- 前端：React + TypeScript + Ant Design，`npx tsc --noEmit` 零错误；跨目录导入用 `@/` 别名
- 单函数体 ≤ 30 行；每个公开函数有单元测试
- 前端 UI 改动必须 Playwright 验证（脚本放 `frontend/tests/`）

## 6.2 架构约束

- 不新增数据表；不修改工艺 YAML schema；不改实例化逻辑
- 流程图渲染优先复用/扩展 `loop-flow/` 现有组件，避免维护两份 SVG 布局逻辑；差异化通过样式参数（如 `variant="template"`）实现
- 追溯面包屑抽象为可复用组件（如 `components/trace/TraceBreadcrumb.tsx`），各详情页传入链路数据

## 6.3 安全约束

- 新 API 必须做 workspace 层级权限校验（与现有 process/loop handler 一致）
- YAML 解析失败（用户层工艺可能手写损坏）时流程图 Tab 降级展示错误提示 + YAML 源 Tab，不白屏

## 6.4 性能约束

- 「实例环路」Tab 数据在切到该 Tab 时才请求（懒加载），避免工艺详情打开即多查
- 流程图节点数与现有环路流程图同量级（<50），无需虚拟化

# 7. 可修改 / 不可修改项

## 7.1 ❌ 不可修改

- 工艺 YAML schema、`installer.rs` 实例化逻辑、`loops`/`loop_steps` 表结构
- 环路流程图的编辑交互（`onSelectStep` 打开环节编辑弹窗行为保留）
- `LoopFlowGraph` 现有两处使用方（编辑态、执行轨迹只读态）的默认样式与行为

## 7.2 ✅ 可调整

- 流程图「模板感」差异化的具体视觉参数（虚线/实线、配色、徽标位置）——**本期先实现差异化版本，与环路流程图样式并排对比后，由用户选定最终保留方案**（已在需求澄清中确认）
- 追溯面包屑的分隔符、省略策略（链路过长时中间折叠）
- 「所属环路」在事项详情页的具体位置（建议置于基本信息与执行历史之间）
- 导航组内「消息/黑板/看板」的相对顺序

# 8. 接口与数据约定

## 8.1 新增 API

```text
GET    /api/v1/processes/{id}/loops
       → 返回该工艺模板实例化的环路列表
       → 响应：{ success: true, data: ProcessLoopItem[] }
       → ProcessLoopItem: { id, name, description, status, process_template_version, created_at, execution_count }
       → 排序：created_at DESC
       → 错误：404 工艺不存在
```

## 8.2 扩展 DTO

```typescript
// LoopDto 扩展（面包屑用，避免前端二次查询工艺名）
export interface LoopDto {
  // ... 现有字段 ...
  process_template_id: number | null;          // 已存在
  process_template_version: string | null;     // 已存在
  process_template_name?: string | null;       // 新增：模板唯一名
  process_template_display_name?: string | null; // 新增：模板显示名
}
```

## 8.3 前端路由（现有 hash 路由扩展，不改机制）

```text
/#/processes?id={templateId}     → 工艺页并打开该工艺详情（面包屑回跳用）
/#/loops?id={loopId}             → 环路详情（已存在）
/#/items?id={todoId}             → 事项详情（已存在）
```

# 9. 验收标准（Acceptance Criteria）

## 9.1 后端验收

- `GET /api/v1/processes/{id}/loops` 仅返回 `process_template_id = {id}` 的环路，按 created_at DESC；无实例时返回空数组
- sea-orm 实体 `process_templates.rs` 含 `previous_version_id` 字段，与 v72 迁移一致

## 9.2 前端验收

- 工艺详情默认展示流程图 Tab，节点/阶段数量与 YAML 中 steps/phases 一致；YAML 损坏时显示错误提示而非白屏
- 安装工艺成功后 URL 变为 `/#/loops?id={新id}`
- 有来源工艺的环路详情顶部显示 `来源：工艺A v1.2`，点击跳工艺详情；无来源的环路不显示该行
- 环路流程图节点的事项标题可点击，跳 `/#/items?id=x`；点击节点其余部分仍打开环节编辑
- 事项详情页展示「所属环路」区块（无引用时不显示），点击跳环路详情
- 左侧导航工作区组顺序为：任务 → 工艺 → 环路 → 事项
- 任务/环路/事项详情顶部链路每段可点击跳转

## 9.3 编译验收

- `cd backend && cargo clippy --all-targets -- -D warnings` 零告警零错误
- `cd backend && cargo test` 全部通过
- `cd frontend && npx tsc --noEmit` 零错误
- 前端改动经 Playwright 验证通过

# 10. 风险与已知不确定点

## 10.1 风险

| 风险 | 处理 |
|------|------|
| 用户层手改 YAML 导致 definition 解析失败 | 流程图 Tab 降级为错误提示 + 引导查看 YAML 源 Tab |
| `LoopFlowGraph` 复用改造影响现有环路页 | 差异化收敛为 `variant` 参数，默认行为不变；Playwright 回归环路页 |
| 工艺环节与环路环节数据结构不完全同构（模板引用 vs 实例） | 设计文档中明确字段映射表；缺失字段（如 step_template 软引用）在详情卡中显式标注 |
| 导航顺序调整影响老用户肌肉记忆 | 一次性调整，变更在 PR 说明中显式标注 |

## 10.2 已知不确定点

1. **「模板感」差异化样式的最终取舍**：本期先实现差异化版本，用户对比环路流程图样式后二选一（可能最终统一为同一样式）——实现时需保证样式可参数化切换，避免返工
2. **事项详情「所属环路」数据口径**：复用 `todos/center` 的引用信息还是新增查询，设计阶段定
3. **追溯面包屑在移动端的展示**：本期移动端保持现状，面包屑仅桌面端

# 11. AI 的决策权限

## 11.1 AI 可以自行决策

- 面包屑、Tab、详情卡的 Ant Design 组件选型与样式细节
- 「实例环路」Tab 的列定义与空态文案
- Playwright 测试脚本的具体组织方式

## 11.2 AI 遇到歧义时允许假设

- 工艺 definition 中 phases/links 的解析可复用后端同款结构体的前端类型镜像（如已有则复用，无则在 `types/process.ts` 定义）
- 流程图差异化样式参数命名自定（如 `variant="template" | "instance"`）

## 11.3 必须停止并请求人工确认的情况

- 工艺 definition YAML 结构与环路 steps/phases 差异大到无法复用流程图布局逻辑
- 删除 `ProcessDashboard.tsx` 前发现其实有间接引用
- `cargo test` 出现非本需求引入的失败

# 14. 终极判断标准

> 如果一个新加入的 AI，只看这份需求，就能独立完成开发，并且结果符合预期——那么这就是一份合格的 AI 可执行需求。

- ✅ 自洽性：断裂点均有代码证据，目标均可验证
- ✅ 明确性：两个关键决策（导航顺序自上而下；流程图先差异化后对比选定）已在澄清中确认
- ✅ 可验证性：每个目标对应 §9 验收标准
- ✅ 一个需求 = 一个职责：只解决「三层交互断裂」，不动数据模型与运行时
