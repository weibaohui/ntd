# 026-工艺模板用户目录-需求

| 修改人 | 修改时间 | 修改内容 |
|--------|---------|---------|
| AtomCode (GLM-5.2) | 2026-07-25 | 初始版本 — 仿照专家双层目录，为工艺模板新增用户层 `~/.ntd/processes/`，避免 bundled 同步覆盖用户自定义工艺 |

对应设计文档：`docs/design/026-工艺模板用户目录-设计.md`

---

# 1. 背景（Why）

当前工艺模板只存放在 `bundled-repo/processes/` 下，属于系统层。
`bundled-repo` 是一个 git 仓库，每次"立即同步"会执行 `git reset --hard <remote/branch>`（`backend/src/git_sync/mod.rs:267`），
**强制覆盖 `bundled-repo/processes/` 下的所有文件**。
用户若直接修改系统层工艺，下次同步就丢失。

专家模板已采用双层目录设计（系统层 `~/.ntd/bundled/experts/` + 用户层 `~/.ntd/experts/`）解决此问题。
本需求为工艺模板引入同构的用户层目录。

---

# 2. 目标（What，必须可验证）

- [ ] 工艺模板拥有用户层目录 `~/.ntd/processes/`，结构与系统层 `~/.ntd/bundled/processes/` 完全一致
- [ ] 用户层工艺被 upsert 到 `process_templates` 表，`is_system=false`，`source_path` 前缀为 `user://`
- [ ] 系统层工艺被 upsert 到 `process_templates` 表，`is_system=true`，`source_path` 前缀为 `bundled://`
- [ ] 同名工艺：用户层覆盖系统层（`is_system` 从 `true` 变为 `false`）
- [ ] 系统同步不会删除用户层工艺文件，也不会删除 `is_system=false` 的数据库记录
- [ ] 系统同步会先删除所有 `is_system=true` 的 `process_templates` 记录，再重新 upsert（"先删后插"策略）
- [ ] 前端"更多设置 → 模板管理"新增"工艺模板"Tab，展示系统工艺与用户工艺的合并列表
- [ ] 前端"工艺模板"Tab 中，系统工艺行有"复制到用户层"按钮，点击后调用 `POST /api/v1/processes/{name}/copy-to-user`
- [ ] "复制到用户层"成功后，表格刷新，对应工艺的来源从"系统"变为"用户"

---

# 3. 非目标（Explicitly Out of Scope）

- ❌ 不实现"删除用户工艺"功能（M2 范围）
- ❌ 不实现用户工艺 YAML 的前端编辑器（M2/M3 范围，参考 `docs/design/025-工艺管理-M3-设计.md` §3.4）
- ❌ 不引入用户工艺的版本 diff 与升级提示（M3 范围）
- ❌ 不实现工作空间级用户工艺（本需求只支持全局用户工艺，`workspace_id=NULL`）
- ❌ 不修改 `bundled-repo` 仓库本身的同步策略（`git reset --hard` 仍保留，因为系统层工艺本就该被远程覆盖）

# 4. 使用场景 / 用户路径

## 场景 1：用户自定义工艺不被同步覆盖

1. 用户在前端"模板管理 → 工艺模板"Tab 看到系统工艺 `4p12s-delivery`
2. 用户点击"复制到用户层"按钮
3. 后端把 `~/.ntd/bundled/processes/software/4p12s-delivery.yaml` 复制到 `~/.ntd/processes/software/4p12s-delivery.yaml`
4. 后端 upsert 用户工艺，`is_system=false`
5. 表格刷新，`4p12s-delivery` 的来源从"系统"变为"用户"
6. 用户手动编辑 `~/.ntd/processes/software/4p12s-delivery.yaml`
7. 用户点击"立即同步"，系统层被覆盖，但用户层文件保持不变
8. 同步完成后，`4p12s-delivery` 仍显示为"用户"来源，用户编辑的内容保留

## 场景 2：用户从零创建新工艺

1. 用户在 `~/.ntd/processes/software/my-process.yaml` 创建新工艺
2. 用户在前端点击"立即同步"
3. 后端扫描用户层目录，upsert `my-process` 为 `is_system=false`
4. 表格刷新，`my-process` 显示为"用户"来源

## 场景 3：系统层删除某工艺，用户层保留

1. 远程仓库删除 `bundled-repo/processes/software/old-process.yaml`
2. 用户点击"立即同步"
3. 系统层 git reset --hard 后，`old-process.yaml` 从 `~/.ntd/bundled/processes/` 消失
4. 后端"先删后插"删除所有 `is_system=true` 记录，`old-process` 不再被 upsert
5. 如果用户层有同名工艺 `~/.ntd/processes/software/old-process.yaml`，它仍被 upsert 为 `is_system=false`
6. 表格刷新，`old-process` 仅在用户层存在时显示，且来源为"用户"

# 6. 约束条件

## 6.1 技术约束

- 后端：Rust (Axum + SeaORM)，`cargo clippy --all-targets -- -D warnings` 零告警
- 前端：React + TypeScript + Ant Design，`cd frontend && npx tsc --noEmit` 零错误
- 前端导入规范：`frontend/src` 内跨目录用 `@/` 绝对路径
- 函数长度限制：单函数体 ≤ 30 行
- 每个公开函数必须有单元测试

## 6.2 架构约束

- 复用现有 `process_templates` 表，**不新增表**
- 复用现有 `GET /api/bundled/processes` API，**只新增 `copy-to-user` 一个端点**
- 与 `docs/design/025-工艺管理-设计.md` §7 的同步机制完全兼容
- 与 `docs/design/025-工艺管理-M3-设计.md` §3.4 的可视化编排器预留接口

## 6.3 安全约束

- 路径安全：用户层目录扫描与"复制为用户工艺"的路径解析必须使用 `resolve_within` 模式
- 禁止 `..` 逃逸、绝对路径注入、符号链接逃逸
- YAML 校验：用户层 YAML 在 upsert 前必须通过 `parse_process_file` 解析校验

## 6.4 性能约束

- 用户层目录扫描在同步流程中一次性完成，不引入额外的文件系统调用
- `delete_all_system_process_templates` 使用单条 SQL，避免逐条删除

# 7. 可修改 / 不可修改项

## 7.1 ❌ 不可修改

- `bundled-repo` 的 git 同步策略（`git reset --hard` 必须保留，系统层工艺本就该被远程覆盖）
- `process_templates` 表结构（已有 `is_system` 和 `workspace_id` 字段，直接复用）
- 现有 `GET /api/bundled/processes` API 的响应结构（只扩展 `is_system` 字段，不破坏现有调用）

## 7.2 ✅ 可调整

- 用户层目录的子目录结构（本需求约定与系统层一致，但实现时可调整）
- "复制到用户层"按钮的 UI 位置（可放在操作列，也可放在行展开详情中）
- 同步删除策略的实现方式（本需求约定"先删后插"，但可调整为"软删除 + 标记"）

# 8. 接口与数据约定

## 8.1 现有 API（复用）

```text
GET    /api/bundled/processes
       → 返回 ProcessTemplateDto[]，新增 is_system 字段

GET    /api/bundled/processes/{name}
       → 返回 ProcessTemplateDetail，新增 is_system 字段

POST   /api/bundled/processes/{name}/install
       → 安装工艺为 Loop（不变）
```

## 8.2 新增 API

```text
POST   /api/v1/processes/{name}/copy-to-user
       → 把系统工艺复制到用户层 ~/.ntd/processes/
       → 请求体：空
       → 响应：{ success: true, data: { user_source_path: 'user://processes/...' } }
       → 错误：
          404: 系统工艺 {name} 不存在
          409: 用户层已存在同名工艺（提示用户先删除用户层文件）
          500: 文件写入失败
```

## 8.3 ProcessTemplateDto 字段

```typescript
export interface ProcessTemplateDto {
  id: number;
  name: string;              // 唯一标识，如 4p12s-delivery
  display_name: string;      // 显示名，如 "标准需求交付工艺"
  description: string;       // 描述
  category: string;          // 分类，如 software
  complexity: string;        // 复杂度：light | standard | complex
  version: string;           // 版本，如 1.0.0
  source_path: string;       // 来源路径，前缀区分 bundled:// 或 user://
  is_system: boolean;        // 是否为系统工艺（新增字段）
  workspace_id: number | null;
  step_count: number;        // 环节数
}
```

# 9. 验收标准（Acceptance Criteria）

## 9.1 后端验收

- 如果 `~/.ntd/processes/software/test.yaml` 存在，则调用 `import_user_process_templates` 后，数据库中 `test` 工艺的 `is_system=false`
- 如果 `~/.ntd/bundled/processes/software/test.yaml` 和 `~/.ntd/processes/software/test.yaml` 同时存在，则同步完成后数据库中 `test` 工艺的 `is_system=false`（用户层覆盖）
- 如果系统层删除了 `test.yaml`，则同步完成后数据库中不存在 `is_system=true` 的 `test` 记录，但 `is_system=false` 的 `test` 记录（如果存在）保留
- 调用 `POST /api/v1/processes/{name}/copy-to-user` 后，`~/.ntd/processes/<相对路径>.yaml` 文件存在，内容与系统层 YAML 一致
- 调用 `copy-to-user` 时，如果 `name` 包含 `..` 或绝对路径，则返回 400 错误

## 9.2 前端验收

- 打开"更多设置 → 模板管理"，能看到第 4 个 Tab "工艺模板"
- 点击"工艺模板"Tab，表格列出所有工艺（系统 + 用户），每行有"来源"列显示"系统"或"用户"Tag
- 系统工艺行的操作列有"复制到用户层"按钮
- 点击"复制到用户层"按钮，成功后表格刷新，对应工艺的来源从"系统"变为"用户"
- 用户工艺行的操作列有"查看"按钮（不实现编辑，只读展示）

## 9.3 编译验收

- `cd backend && cargo clippy --all-targets -- -D warnings` 零告警零错误
- `cd backend && cargo test` 全部通过
- `cd frontend && npx tsc --noEmit` 零错误

# 10. 风险与已知不确定点

## 10.1 风险

| 风险 | 处理 |
|------|------|
| 用户层目录不存在时扫描失败 | `import_user_process_templates` 在目录不存在时返回 `Ok(())`，与系统层逻辑一致 |
| 用户层 YAML 格式错误 | 解析失败时 warning 跳过，不阻断同步（与现有 `parse_process_file` 逻辑一致） |
| 同名工艺覆盖导致数据丢失 | 用户层覆盖系统层时，系统层 YAML 仍在 `~/.ntd/bundled/processes/`，可随时恢复 |
| "先删后插"策略的中间状态 | 同步是同步操作，前端在同步完成后再刷新列表，不会看到中间状态 |

## 10.2 已知不确定点

1. **用户层目录是否需要自动创建**？
   - 本需求约定：`import_user_process_templates` 在目录不存在时跳过，不自动创建目录
   - `copy-to-user` 时使用 `create_dir_all` 自动创建父目录
2. **用户层 YAML 的字段约束是否与系统层一致**？
   - 是的，复用 `parse_process_file` 解析，字段约束完全一致
3. **"复制到用户层"是否覆盖已存在的用户工艺**？
   - 本需求约定：不覆盖，返回 409 错误，提示用户先手动删除用户层文件

# 11. AI 的决策权限

## 11.1 AI 可以自行决策

- 用户层目录扫描的实现细节（递归扫描、文件过滤）
- "复制到用户层"handler 的错误码选择（404/409/500）

## 11.2 AI 遇到歧义时允许假设

- 如果现有 `ProcessTemplateDto` 类型文件不存在，AI 可以新建 `frontend/src/types/process.ts`
- 如果 `GET /api/bundled/processes` 的响应结构不明确，AI 可以查阅 `backend/src/handlers/process.rs` 后决定

## 11.3 必须停止并请求人工确认的情况

- 如果 `process_templates` 表没有 `is_system` 字段（需要数据库迁移）
- 如果现有 `import_process_templates_from_bundled` 的实现与设计文档描述不符
- 如果 `cargo test` 出现非本需求引入的失败

# 13. 与现有需求的对应关系

本需求是对 `docs/requirements/025-工艺管理-需求.md` 的补充：

- 025 需求定义了工艺管理的整体框架（模板、阶段、产物、门禁、返工）
- 025 需求的"模板同步"部分只覆盖了系统层
- 本需求补充用户层，解决"用户自定义工艺被同步覆盖"的问题

本需求与 `docs/requirements/025-工艺管理-M3-需求.md` 的关系：

- M3 需求的第 3.4 节"可视化编排器"支持用户编辑 YAML，但未明确存储位置
- 本需求为用户工艺提供明确的存储路径 `~/.ntd/processes/`，为 M3 的可视化编排器奠定基础
