## 1. 背景与现状

### 1.1 工艺模板数据模型（已完备）

后端 `process_templates` 表已存在，字段如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | i64 PK | 自增主键 |
| `name` | String | 唯一标识，如 `4p12s-delivery` |
| `display_name` | String | 人类可读名称 |
| `description` | String | 工艺描述 |
| `category` | String | 分类，如 `software`、`migration` |
| `complexity` | String | 复杂度：`light` / `standard` / `complex` |
| `version` | String | 语义化版本，如 `1.0.0` |
| `definition` | Text | 工艺完整定义（YAML 文本） |
| `source_path` | Option<String> | 来源路径，`bundled://processes/...` 或 `user://...` |
| `is_system` | bool | 是否系统内置（系统=true，用户=false） |
| `workspace_id` | Option<i64> | 所属工作空间 ID（NULL=全局） |
| `previous_version_id` | Option<i64> | 版本链（**当前仅留痕，不启用**） |
| `created_at` / `updated_at` | Option<String> | 时间戳 |

### 1.2 双层目录设计（已实现）

| 层 | 路径 | `is_system` | 同步行为 |
|----|------|------------|---------|
| 系统层 | `~/.ntd/bundled/processes/` | `true` | 每次 bundled 同步会被 `git reset --hard` 覆盖 |
| 用户层 | `~/.ntd/processes/` | `false` | **不会被同步覆盖**，用户自定义安全区 |

同名工艺时用户层覆盖系统层（`name` 为唯一键，第二次 upsert 改写 `is_system` 从 `true` 变 `false`）。

### 1.3 现有 API（已实现）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/bundled/processes` | 列出所有工艺模板 |
| GET | `/api/v1/bundled/processes/{name}` | 获取工艺详情（含 `definition` YAML 文本） |
| POST | `/api/v1/bundled/processes/{name}/install` | 实例化工艺为 Loop |
| POST | `/api/v1/processes/validate` | 结构校验（serde 解析） |
| POST | `/api/v1/processes/{name}/copy-to-user` | 复制系统工艺到用户目录 |
| GET | `/api/v1/processes/{name}/loops` | 列出该工艺的实例环路 |
| GET | `/api/v1/processes/stats` | 工艺统计 |
| POST | `/api/v1/processes/recommend` | 推荐工艺 |

### 1.4 现有前端能力（只读展示）

- `ProcessPage`（`/#/processes`）：卡片列表 + 详情 Modal（流程图 / 实例环路 / **只读** YAML 源）
- `ProcessTemplatesTab`（设置 → 模板管理 → 工艺模板）：表格 + "查看" + "复制到用户层"按钮
- `ProcessFlowGraph`：dagre + 手写 SVG 的**只读**流程图
- `processFlowAdapter`：YAML → 节点/边的**单向**适配器

### 1.5 缺失能力（本次需求要补齐的）

| 缺失 | 影响 |
|------|------|
| ❌ `PUT /processes/{name}` 保存编辑后的 YAML | 用户无法编辑工艺 |
| ❌ `POST /processes` 新建工艺 | 用户无法创建新工艺 |
| ❌ `DELETE /processes/{name}` 删除用户工艺 | 用户无法清理误建工艺 |
| ❌ YAML 编辑器（Monaco） | 用户只能看不能改 |
| ❌ 可视化泳道编辑器（React Flow） | 用户必须手写 YAML |
| ❌ YAML ↔ 可视化双向联动 | 两个编辑入口各自孤立 |
| ❌ "创建工艺"按钮 + 元信息 Modal | 没有创建入口 |
| ❌ 编辑器独立路由 + 离开拦截 | 编辑体验缺失 |

## 2. 功能目标与边界

### 2.1 核心目标

1. **工艺 YAML 可编辑**：用户目录下的工艺（`is_system=false`）可编辑保存；帮助目录下的系统工艺（`is_system=true`）不打开编辑，提供"复制到用户目录"按钮
2. **可视化创建工艺**：增加"创建工艺"按钮，提供泳道图式可视化界面——横向向右增加大阶段（phase），每个阶段内纵向从上到下列环节（link）
3. **YAML ↔ 可视化双向联动**：界面改动 → YAML 更新；YAML 改动 → 界面更新；用 sync flag 避免循环

### 2.2 不做的事（Out of Scope）

| 不做 | 理由 |
|------|------|
| 完整 undo/redo | YAGNI，依赖 Monaco 自身 Cmd+Z；可视化操作靠"删除前弹确认"防误删 |
| 版本链 UI（`previous_version_id` 启用） | 后端注释明确"版本链 UI 属后续迭代"，本次只做原地覆盖 |
| 工作空间隔离的工艺模板 | YAGNI，ntd 是个人工具，工艺是个人知识资产 |
| RBAC 权限位 | YAGNI，`is_system` 字段已是唯一编辑权限门槛 |
| 完整 JSON Schema 校验 + 自动补全 | 维护成本高，用 `js-yaml` 实时解析 + 错误标记覆盖 90% 场景 |
| 乐观锁并发冲突保护 | YAGNI，"两个 tab 同时编辑同一工艺"是极端边界场景 |
| 模板变量（`{process_name}`）的补全/高亮 | YAGNI，模板变量是运行时语义，编辑器只负责原样存储 YAML 文本 |

### 2.3 用户故事

**US-1：编辑用户工艺 YAML**
> 作为工艺设计者，我想在工艺详情页直接编辑 YAML 并保存，这样我不用手动改文件再重启服务。

**US-2：复制系统工艺到用户目录后编辑**
> 作为工艺设计者，我想把系统工艺复制到我的用户目录，然后自由编辑它，这样我的修改不会被下次同步覆盖。

**US-3：可视化创建新工艺**
> 作为工艺设计者，我想通过泳道图式可视化界面创建新工艺——横向加阶段、阶段内加环节——而不用手写 YAML，这样降低创建门槛。

**US-4：YAML 与可视化双向联动**
> 作为工艺设计者，我想在 YAML tab 改了内容后切回可视化 tab 能看到变化，反之亦然，这样两个编辑入口不是孤立的。

**US-5：删除误建的用户工艺**
> 作为工艺设计者，我想删除误建的用户工艺，但如果该工艺已有实例 Loop，系统应阻止删除避免断链。

**US-6：未保存修改的离开拦截**
> 作为工艺设计者，我想在编辑器里改了一半没保存就跳路由或关页签时得到提示，这样避免误丢修改。

## 3. 详细需求

### 3.1 后端 API 新增

#### 3.1.1 `PUT /api/v1/processes/{name}` — 保存编辑后的 YAML

**请求体**：
```json
{
  "definition": "<新的 YAML 文本>"
}
```

**处理流程**（3 步，职责单一）：
1. **来源校验**：`get_process_template_by_name` → 若 `is_system == true` 返回 `409 Conflict` + 提示"系统工艺不可直接编辑，请先复制到用户层"
2. **结构校验**：`serde_yaml::from_str::<ProcessDefinition>(&definition)` → 失败返回 `400 Bad Request` + serde 错误消息（含行号）
3. **原子写盘 + 刷新入库**：
   - 计算 `~/.ntd/processes/<rel_path>`（`rel_path` 从 `source_path` 剥 `user://` 前缀）
   - 临时文件 + rename 原子写盘
   - 触发 `import_user_process_templates` 刷新 DB

**成功响应**：`200 OK` + `{ "updated_at": "<新时间戳>" }`

**错误码**：
| 码 | 场景 |
|----|------|
| 400 | YAML 结构校验失败 |
| 404 | 工艺 `{name}` 不存在 |
| 409 | 试图编辑系统工艺（`is_system=true`） |

#### 3.1.2 `POST /api/v1/processes` — 新建工艺

**请求体**：
```json
{
  "name": "my-process",
  "display_name": "我的工艺",
  "category": "software",
  "complexity": "light",
  "version": "1.0.0",
  "definition": "<初始 YAML，至少包含 process: 块>"
}
```

**处理流程**：
1. **name 合法性校验**：复用 `validate_process_name` + 正则 `^[a-zA-Z0-9_-]+$` → 失败 400
2. **name 唯一性校验**：`get_process_template_by_name` 若已存在 → 失败 409
3. **结构校验**：同 3.1.1 第 2 步
4. **写盘**：`~/.ntd/processes/<name>.yaml`（若文件已存在 → 失败 409）
5. **刷新入库**：`import_user_process_templates`

**成功响应**：`201 Created` + `{ "source_path": "user://<name>.yaml" }`

#### 3.1.3 `DELETE /api/v1/processes/{name}` — 删除用户工艺

**处理流程**：
1. `get_process_template_by_name` → 不存在 404
2. **`is_system` 校验**：`is_system == true` → 409 + "系统工艺不可删除"
3. **实例 Loop 校验**：`list_process_loops(name)` 若非空 → 409 + "该工艺已有 N 个实例环路，请先归档相关环路再删除"
4. **删文件**：`std::fs::remove_file(~/.ntd/processes/<rel_path>)`
5. **删 DB 行**：`delete_process_template(name)`

**成功响应**：`200 OK` + `{ "deleted": true }`

#### 3.1.4 路由注册

新增 3 条路由到 `v1_process_routes()`：
```rust
.route("/api/v1/processes", axum::routing::post(create_process))
.route("/api/v1/processes/{name}", axum::routing::put(update_process).delete(delete_process))
```

### 3.2 前端：YAML 编辑器（Monaco）

#### 3.2.1 依赖新增

`frontend/package.json` 新增：
```json
{
  "@monaco-editor/react": "^4.6.0",
  "monaco-editor": "^0.50.0"
}
```

Monaco 通过 web worker 拆分加载，首屏 ~2MB，**只在打开 YAML 编辑时按需动态 import**，对主列表页零影响。

#### 3.2.2 编辑器组件

新建 `frontend/src/components/process/ProcessYamlEditor.tsx`：
- 包裹 `@monaco-editor/react` 的 `Editor` 组件
- 语言设为 `yaml`
- 主题跟随应用暗/亮模式
- `onChange` 触发 debounced（300ms）`yaml.load()`：
  - **成功** → 调用 `onParsed(definition, parsedObj)` 把解析结果回传父组件
  - **失败** → 在 Monaco 的行号槽里标红波浪线（`deltaDecorations` API）+ 浮窗显示 `yaml.load` 抛出的错误消息（含行号）

#### 3.2.3 编辑权限控制

| 来源 | `is_system` | YAML tab 行为 |
|------|------------|---------------|
| 系统工艺 | `true` | 只读 + 顶部黄色 Alert "系统工艺编辑后会被同步覆盖，请先[复制到用户层]" |
| 用户工艺 | `false` | 可编辑 + 顶部绿色 Alert "编辑保存后写入 `~/.ntd/processes/`" |

### 3.3 前端：可视化泳道编辑器（React Flow）

#### 3.3.1 依赖新增

`frontend/package.json` 新增：
```json
{
  "@xyflow/react": "^12.3.0",
  "dagre": "^0.8.5",
  "@types/dagre": "^0.7.52"
}
```

> 注：`@xyflow/react` 是 React Flow v12 的新包名（v11 叫 `reactflow`）。项目已有 dagre 使用经验（`useFlowLayout`）。

#### 3.3.2 节点模型

| 节点类型 | React Flow type | 数据 | 视觉 |
|----------|-----------------|------|------|
| Phase 容器 | `phase` (自定义) | `phase: PhaseDefinition, links: LinkDefinition[]` | 横向矩形泳道，头部显示 `name` + 删除按钮，内部纵向排列 link 节点 |
| Link 环节 | `link` (自定义) | `link: LinkDefinition, phaseId: string` | 卡片显示 `name` + `step_template`，右侧两个 handle（绿=`on_success`，橙=`on_gate_fail`） |

**布局算法**（两层 dagre）：
1. **横向布局**：按 `phases` 数组顺序从左到右排列 phase 容器，容器宽度 = `max(内部 link 节点宽度) + padding`
2. **纵向布局**：每个 phase 内部按 `links` 数组顺序从上到下排列 link 节点，节点间距固定

新增 phase 时自动 fitView 到新节点区域（用 `fitView({ nodes: [newNodeId] })`）。

#### 3.3.3 连线模型

| 边类型 | 触发条件 | 视觉 |
|--------|---------|------|
| 顺向 success 边 | `on_success: next` 或 `on_success: end` | 灰色 smoothstep |
| goto 成功边 | `on_success: goto:xxx` | 绿色 smoothstep |
| goto 门禁失败边 | `on_gate_fail: goto:xxx` | 橙色虚线 smoothstep |

**交互**：
- **新增连线**：用户从 link 节点右侧的绿色或橙色 handle 拖出线，松开在目标 link 的左侧 handle 上 → 触发 `onConnect` → 更新 `ProcessDefinition` 对应字段
  - 绿色 handle 拖出的连线 → `on_success: goto:<target_id>`
  - 橙色 handle 拖出的连线 → `on_gate_fail: goto:<target_id>`
- **删除连线**：hover 边时在中点浮现小叉号按钮，点击删除；同时支持选中边 + Delete 键
  - 删 `on_success: goto:xxx` → `on_success` 改回 `next`
  - 删 `on_gate_fail: goto:xxx` → `on_gate_fail` 改回 `break`

#### 3.3.4 节点选中与属性面板

点击 React Flow 节点 → 右侧属性面板展示该节点的字段表单。

**Link 环节属性面板**（暴露 8 个常用字段，第六题选 B）：

| 字段 | 控件 | 说明 |
|------|------|------|
| `id` | Input + onChange 实时校验 | 合法字符 `^[a-zA-Z0-9_-]+$` + 全局唯一 |
| `name` | Input | 显示名 |
| `step_template` | Select | 选项来自 `GET /processes/step-templates` 或现有 `process_step_templates` 表（第二十九题选 B） |
| `prompt` | Input.TextArea | 提示词 |
| `executor` | Input | 执行器 |
| `review_type` | Select | `ai` / `human` |
| `on_success` | 分组 Select（OptGroup by phase） | `next` / `end` / `goto:<link_id>`（第三十题选 B） |
| `on_gate_fail` | 分组 Select（OptGroup by phase） | `break` / `goto:<link_id>` |

**嵌套字段**（第十七题选 B，嵌套表格 + 行内编辑）：

| 字段 | UI |
|------|-----|
| `gates` | Ant Design Table，可增删行，每行内联 Input/Select 编辑 `name, type, artifact, criteria_ref, min_score, script` |
| `expected_artifacts` | Ant Design Table，可增删行，每行内联 Input 编辑 `name, type, path, locator` |

**`path` 字段**：普通文本输入，原样存储 YAML 文本，**不**解析 `{process_name}` 模板变量（第三十五题选 A）。

#### 3.3.5 全局字段面板

**顶部折叠面板**（第三十四题选 B）— 工艺元信息：

| 字段 | 控件 |
|------|------|
| `name` | 只读（创建后不可改，因作为文件名和路由参数） |
| `display_name` | Input |
| `category` | Input 或 Select |
| `complexity` | Select: `light` / `standard` / `complex` |
| `version` | Input，默认 `1.0.0` |
| `description` | Input.TextArea |

**全局面板**（第十五题选 A 全集可视化，但分层组织）：

| 字段 | UI 形态 |
|------|---------|
| `limits` | 小表单：`max_step_executions` (InputNumber) + `max_total_tokens` (InputNumber) |
| `abnormal_handler` | 静态表单：`trigger_on` (多选 Checkbox Group: `capped_step` / `capped_token` / `failed`) |
| `step_templates` | Collapse 折叠面板（第十六题选 B）：每个原型是一个折叠项，展开编辑 `name, prompt, skills, model, executor` |

#### 3.3.6 删除节点级联处理

**删除 link 节点**（第二十二题选 B）：
- 拦截 React Flow `onNodesDelete`
- 弹 `Modal.confirm`："将删除环节「<link.name>」。有 N 处其他环节的跳转引用了此环节，将被重置为 next/break。确认删除？"
- 确认后：从 `phases[].links[]` 移除该 link + 把所有 `goto:<被删link.id>` 重置为默认值（`on_success: next` / `on_gate_fail: break`）

**删除 phase 容器**（第二十三题选 B）：
- 泳道头部右上角小叉号按钮
- 弹 `Modal.confirm`："将删除阶段「<phase.name>」及其下 N 个环节。有 M 处其他环节的跳转引用了本阶段的环节，将被重置为 next/break。确认删除？"
- 确认后：从 `phases` 数组移除该 phase + 遍历其下所有 link，对每一个执行上述"删除 link 时重置悬空 goto"的级联重置

### 3.4 前端：YAML ↔ 可视化双向联动

#### 3.4.1 数据流模型（第五题选 C：双向 + 显式 sync flag）

**单一数据源**：父组件维护 `ProcessDefinition` 对象作为 source of truth。

**可视化 → YAML**：
1. 用户在 React Flow 上增删 phase/link、改属性面板字段、拖连线
2. 修改 `ProcessDefinition` 对象对应字段
3. 立即 `yaml.dump(processDefinition)` 刷新 Monaco 的内容（用 `editor.setValue`）
4. **设置 `isSyncing = true` flag**，Monaco 的 `onChange` 在 flag 期间忽略，推完后清 flag

**YAML → 可视化**：
1. 用户在 Monaco 编辑 YAML 文本
2. `onChange` 触发 debounced（300ms）`yaml.load()`
3. **成功** → 更新 `ProcessDefinition` 对象 → React Flow 节点重新渲染
   - 设置 `isSyncing = true` flag，React Flow 的 `onNodesChange` 在 flag 期间忽略，推完后清 flag
4. **失败** → 只在 Monaco 上标红错误，**不破坏当前可视化状态**

#### 3.4.2 联动组件结构

```
ProcessEditor (父，维护 ProcessDefinition + isSyncing)
├── ProcessVisualEditor (React Flow，左侧主区)
│   ├── PhaseNode (自定义节点，横向泳道容器)
│   ├── LinkNode (自定义节点，环节卡片)
│   └── Edges (只读 smoothstep 边)
├── ProcessPropertyPanel (右侧，根据选中节点切换)
│   ├── LinkPropertyForm (8 字段 + gates/expected_artifacts 嵌套表格)
│   ├── PhasePropertyForm (6 字段)
│   └── GlobalPropertyForm (limits/abnormal_handler/step_templates)
├── ProcessYamlEditor (Monaco，YAML tab)
└── ProcessEditorToolbar (顶部，保存/删除/元信息折叠面板)
```

### 3.6 前端：未保存修改的离开拦截（第十四题选 B）

**两层拦截**，共享 `isDirty` 状态（用户改了任何字段就置 `true`，保存成功后置回 `false`）：

1. **路由内跳转**：用 React Router 的 `useBlocker`（v6.4+）拦截，弹 Ant Design `Modal.confirm("你有未保存的修改，确认离开？")`
2. **刷新/关页签**：`window.addEventListener('beforeunload', e => { if (isDirty) e.preventDefault() })`，浏览器原生提示

### 3.7 前端：保存反馈与列表刷新（第二十五题选 B）

保存成功后：
1. `message.success("工艺已保存")`
2. 编辑器顶部"未保存修改"红点消失（`isDirty = false`）
3. **不跳路由、不清表单**，保留当前 `ProcessDefinition` 对象和 React Flow 节点位置
4. 列表页 `ProcessPage` 在下次进入路由时自动 `load()` 刷新（现有机制）

### 3.8 前端：空工艺渲染（第二十六题选 B）

进入 `/#/processes/new` 后，YAML 只有一个 `process:` 块、`phases` 为空数组或缺失。可视化编辑器渲染：

- 画布中央显示 Ant Design `Empty` 占位
- 占位下方配突出 CTA 按钮 "＋ 新增阶段"
- 点击后在画布中央生成第一个 phase 容器节点

## 4. 数据流与状态管理

### 4.1 编辑器状态

```typescript
interface ProcessEditorState {
  // source of truth，YAML ↔ 可视化双向联动的共享对象
  definition: ProcessDefinition;
  // 原始 YAML 文本（Monaco 编辑的内容）
  yamlText: string;
  // 双向联动防循环 flag
  isSyncing: boolean;
  // 未保存修改标记，离开拦截用
  isDirty: boolean;
  // 当前选中的节点 id（用于属性面板切换）
  selectedNodeId: string | null;
  // 保存中状态
  isSaving: boolean;
}
```

### 4.2 关键状态转换

| 转换 | 触发 | 副作用 |
|------|------|--------|
| `definition` 变更 | 可视化操作 / YAML 解析成功 | `yaml.dump` 刷新 `yamlText`（可视化操作时）/ React Flow 节点重渲染（YAML 解析时） |
| `isDirty: false → true` | 任何 `definition` 或 `yamlText` 变更 | 顶部红点显示，离开拦截启用 |
| `isDirty: true → false` | 保存成功 | 顶部红点消失 |
| `isSyncing: true → false` | 一方推送完成 | 另一方恢复 `onChange` 监听 |

## 6. 技术决策汇总（grill-me 35 轮结果）

| 编号 | 决策点 | 选择 | 理由 |
|------|--------|------|------|
| 1 | 保存校验严格度 | B 结构校验 | 复用 `validate_process` 的 serde 解析，不引入语义校验阻断 |
| 2 | 保存接口设计 | A 新建 `PUT /processes/{name}` | 保存与复制语义不同，强行复用会混淆 |
| 3 | YAML 编辑器选型 | B Monaco | YAML 高亮/折叠/查找开箱即用，按需动态 import 控制体积 |
| 4 | 可视化编辑器选型 | B React Flow | 成熟节点图库，自定义节点渲染泳道 |
| 5 | 双向联动策略 | C 双向 + sync flag | 防止"可视化→YAML→onChange→再 parse"无限循环 |
| 6 | 环节属性面板字段集 | B 8 常用字段 | 高阶字段（gates/expected_artifacts）走 YAML tab |
| 7 | phase 新增 id/name 策略 | B 自动 id + 手动 name | 避免 id 非法字符导致 YAML 解析失败 |
| 8 | 创建工艺元信息收集 | B 先 Modal 收 5 字段 | name 带实时校验+查重，避免后续保存冲突 |
| 9 | phase 内 link 排序与跳转编辑 | B 属性面板上下箭头 + on_success 下拉 | 拖拽排序实现复杂，下拉比拖连线更精准 |
| 10 | 保存版本管理策略 | A 原地覆盖 | YAGNI，版本链 UI 属后续迭代 |
| 11 | 删除用户工艺能力 | C 受限删除 | 已有实例 Loop 拒绝删除避免断链 |
| 12 | 属性面板字段校验时机 | B 分层校验 | id 字段 onChange 实时校验，跨节点语义保存时校验 |
| 13 | 编辑器入口与路由 | B 独立路由 | 全屏工作台需要独立路由，塞 Modal 会滚动嵌套混乱 |
| 14 | 未保存修改离开拦截 | B 路由 + beforeunload 都拦 | 两种离开场景都覆盖 |
| 15 | 全局字段处理 | A 全集可视化 | limits/abnormal_handler/step_templates 都做可视化表单 |
| 16 | step_templates UI 形态 | B Collapse 折叠面板 | 折叠态节省空间，展开态编辑细节 |
| 17 | gates/expected_artifacts UI 形态 | B 嵌套表格 + 行内编辑 | Ant Design Table 支持单元格内联编辑 |
| 18 | React Flow 节点模型与布局 | B group 节点 + dagre 横向 + 纵向 flex | phase 是 group 容器，link 是子节点 |
| 19 | 连线渲染策略 | B 可拖拽连线编辑 | 用户拖连线更新 on_success/on_gate_fail |
| 20 | 拖拽连线语义区分 | B 双 source handle 颜色编码 | 绿色=on_success，橙色=on_gate_fail |
| 21 | 删除连线交互 | B hover 删除按钮 + Delete 键双通道 | 显式化删除动作，避免误删 |
| 22 | 删除 link 节点级联处理 | B 弹确认 + 重置悬空引用 | 知情同意 + 语义回退到默认值 |
| 23 | 删除 phase 级联处理 | B 泳道头部删除 + 弹确认 + 批量重置 | 列头删除入口符合视觉直觉 |
| 24 | 并发冲突保护 | C 完全不保护 | YAGNI，ntd 是个人工具，极端边界场景 |
| 25 | 保存反馈与列表刷新 | B 停留编辑页 + 红点消失 | 用户保存后大概率继续编辑 |
| 26 | 空工艺渲染 | B Empty + CTA 新增阶段 | 降低首次创建心理门槛 |
| 27 | 属性面板与节点联动 | A 单向数据流 | 属性面板改 ProcessDefinition → React Flow 重渲染 |
| 28 | undo/redo 支持 | A 不专门做 | YAGNI，依赖 Monaco Cmd+Z |
| 29 | step_template 引用校验 | B 下拉选择已存在的原型 | "先定义后引用"标准模式 |
| 30 | on_success/on_gate_fail 下拉来源 | B 分组下拉（OptGroup by phase） | 按 phase 分组展示 link，跨 phase 跳转一目了然 |
| 31 | 鉴权与工作空间隔离 | A 用户级全局资源 + is_system 门槛 | YAGNI，工艺是个人知识资产 |
| 32 | 画布缩放与导航 | B fitView + MiniMap + Controls + 新增节点自动定位 | React Flow 内置导航组件全开 |
| 33 | Monaco YAML schema 校验 | B js-yaml 实时解析 + 错误标记 | 覆盖 90% 场景，无需维护 JSON Schema |
| 34 | 工艺元信息编辑入口 | B 编辑器顶部折叠面板 | 全局配置放顶部，默认折叠 |
| 35 | path 字段模板变量编辑 | A 普通文本输入 | YAGNI，编辑器只负责原样存储 YAML 文本 |
