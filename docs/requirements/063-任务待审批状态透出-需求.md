# 063-任务待审批状态透出-需求

# 0. 文件修改记录表

| 修改人 | 修改时间 | 修改内容 |
|--------|---------|---------|

# 1. 背景（Why）

系统已有人工审批能力：环路环节执行进入 `pending_approval` 后，用户可在执行详情中通过/拒绝。任务详情接口也已统计每次执行的待审批数（NTD-004），在执行历史行上展示红色「N 待审批」标记。

但任务列表接口（`GET /api/v1/workspaces/{ws}/tasks`）不下发待审批信息，任务页（TasksPage）的列表 / 看板 / 卡片三态视图完全无感知：**用户不点进任务详情，就不知道哪个任务正等待自己审批**，审批入口被埋没，待处理审批容易长期滞留。

# 2. 目标（What，必须可验证）

- [ ] 任务列表接口为每个任务返回 `pending_approval_count`（该任务所有执行中未处理的待审批环节总数）
- [ ] 任务页看板视图新增「待审批」泳道，有待审批的任务卡片进入该列
- [ ] 任务页列表视图新增「待审批」列，清晰展示待审批数
- [ ] 任务页卡片视图在卡片上展示「N 待审批」标记
- [ ] 点击待审批标记跳转到任务详情「执行历史」Tab，并自动展开含待审批环节的执行记录，审批按钮直接可见

# 3. 非目标（Explicitly Out of Scope）

- ❌ 不新增落库状态：`tasks.status` 不增加 `pending_review` 等枚举值，无数据库迁移
- ❌ 不做全局导航红点、顶部横幅、独立审批中心页面
- ❌ 不做看板拖拽审批、不做外层弹窗审批（审批操作仍在执行详情内完成）
- ❌ 不改动事项中心（Todo）侧视图；Loop 列表/看板已有待审批展示，不在本期改动范围
- ❌ 不改动审批本身的业务逻辑（通过/拒绝/恢复执行）

# 4. 使用场景 / 用户路径

1. 用户打开任务页，无论处于列表 / 看板 / 卡片哪个视图，都能一眼看到哪些任务有待审批及数量。
2. 看板视图下，待审批任务集中在第一列「待审批」泳道，数量一目了然。
3. 用户点击待审批标记 → 进入任务详情并自动切到「执行历史」Tab → 含待审批的执行记录自动展开 → 用户直接点击环节的「通过/拒绝」完成审批。
4. 审批完成后（WebSocket 事件触发刷新），待审批数归零，任务从「待审批」泳道回到其真实状态泳道。

# 5. 功能需求清单（Checklist）

- [ ] 后端：`list_tasks` 返回项新增 `pending_approval_count: number`
- [ ] 后端：新增 db 批量统计方法 `count_pending_approvals_by_task_ids`，单条 SQL，无 N+1
- [ ] 前端：`TaskItem` 类型新增 `pending_approval_count?: number`
- [ ] 前端：看板 `TASK_LANES` 首部插入「待审批」泳道；`pending_approval_count > 0` 的任务只进该泳道
- [ ] 前端：列表新增「待审批」列（可排序）；状态筛选新增「待审批」选项
- [ ] 前端：卡片头部展示红色「N 待审批」Tag；状态筛选新增「待审批」选项
- [ ] 前端：待审批标记可点击，跳转 `/#/tasks?id=<id>&tab=exec`
- [ ] 前端：`LoopExecutionsPanel` 支持自动展开首条待审批执行记录（仅初始触发一次）

# 6. 约束条件（非常关键）

- 统计口径与 NTD-004 完全一致：`approval_status='pending' OR status='pending_approval'`，兼容旧评分路径与工艺（phase_driver）路径
- 计数口径：该任务**所有执行**的未处理审批总数（与 Loop 列表 `count_pending_approvals_for_loop` 同口径），不只统计最近一次执行——避免新执行掩盖旧执行滞留的审批
- 待审批任务在看板中**只**进入「待审批」泳道，不重复出现在其真实状态泳道（避免看板计数翻倍）
- 待审批展示文案统一为「待审批」，颜色用红色 Tag（与执行历史行内既有标记一致）；泳道色用橙色 `#fa8c16`
- 自动展开仅在进入详情初始加载后触发一次，不得与 WebSocket 刷新重复展开/收起打架

# 7. 可修改 / 不可修改项

- ❌ 不可修改：审批业务逻辑、`loop_step_executions` 表结构、NTD-004 统计口径
- ✅ 可调整：红色 Tag 的具体样式细节、泳道列宽、「待审批」列的列宽

# 8. 接口与数据约定（如适用）

`GET /api/v1/workspaces/{ws}/tasks` 返回项新增字段：

```json
{
  "id": 12,
  "title": "...",
  "status": "running",
  "pending_approval_count": 2,
  "...": "..."
}
```

- `pending_approval_count`：`number`，恒 ≥ 0；无执行或无待审批时为 0
- 其余字段不变，向下兼容

# 9. 验收标准（Acceptance Criteria）

- 如果某任务存在 `approval_status='pending'` 或 `status='pending_approval'` 的环节执行，则列表接口该任务项 `pending_approval_count > 0`
- 如果 `pending_approval_count > 0`，则看板视图中该任务出现在「待审批」泳道且不出现在其他泳道
- 如果 `pending_approval_count > 0`，则列表视图「待审批」列显示「N 待审批」、卡片视图卡片上显示「N 待审批」
- 如果点击待审批标记，则进入任务详情「执行历史」Tab，且含待审批环节的执行记录已自动展开、审批按钮可见
- 如果审批全部处理完，则三态视图中该任务的待审批标记消失
- 后端 `cargo clippy --all-targets -- -D warnings` 与 `cargo test` 通过；前端 `npx tsc --noEmit` 通过

# 10. 风险与已知不确定点

- 历史任务若存在多条滞留的待审批执行，计数会累加（口径如此，属预期行为，非 bug）
- `LoopExecutionsPanel` 分页大小为 5：若待审批执行不在第一页，自动展开不会发生；此时行内仍有红色标记可手动展开。属可接受限制，不做跨页查找（YAGNI）

# 11. 非目标

同第 3 节。AI 不得借本需求顺手重构 TasksPage 其他逻辑或改动 Loop 侧既有待审批展示。
