| 修改人 | 修改时间 | 修改内容 |

# 1. 背景（Why）

当前事项页与环路页的列表形态均采用 `ListDetailPage` 双栏布局：左侧列表，右侧详情面板。这带来三个问题：

1. **详情无独立 URL**：列表与详情共用一个 URL（`/#/items?id=xxx&panel=detail`），刷新/分享/收藏时面板状态依赖 query 参数 `panel`，与项目其他独立路由页面（如 `/tasks`、`/processes`）风格不一致。
2. **列表信息密度低**：`TodoItemRow` 是紧凑卡片样式（左色条 + 标题行 + meta 行），重要字段（状态、执行器、最近执行时间、调度器开关等）挤在 meta 行里靠图标/颜色暗示，扫读效率低。
3. **环路列表与事项列表共用 `TodoList` 组件**：模式切换在列表内部完成，导致列表既要做事项渲染又要做环路渲染，难以针对各自场景做列优化。

事项页的卡片形态（`TodoCenterCardView`）已经是全宽单页，仅列表形态保留了双栏，存在「同一入口两种布局范式」的不一致。

> 注：与 025-1 任务详情页需求类似的设计取向 —— 详情独立为带 URL 的子页面，不依赖左侧列表。本需求把同样的方向推广到事项与环路。

# 3. 非目标（Explicitly Out of Scope）

- ❌ 不改后端 API：所有列表/详情数据接口保持现状
- ❌ 不改数据库 schema：`todos`、`loops`、`loop_steps` 等表结构不动
- ❌ 不重构卡片墙（`TodoCenterCardView`）内部实现，仅改其点击卡片的跳转目标
- ❌ 不做移动端专项改造（移动端继续走 `TodoMobilePage` / `LoopMobilePage`，但需同步切到独立路由）
- ❌ 不改 025-1 任务详情页（`/tasks/:id` 已是独立路由）
- ❌ 不改事项详情页内部组件（`DetailHeader` / `ForumPostList` / `ReferencingLoopsSection` 等保持原样，仅承载容器从右栏改为独立页）
- ❌ 不改环路详情页内部组件（`LoopStudioDetailPanel` 保持原样）
- ❌ 不引入第三方 table 组件，使用 Ant Design `Table`
- ❌ **不做旧 URL 兼容**：不保留 `/#/items`、`/#/items?id=xxx&panel=detail|post` 等旧 URL 形态的自动重定向。所有内部跳转、书签一律迁移到新路由；旧外链失效可接受（成本由用户自行承担，统一即可）

# 4. 使用场景 / 用户路径

## 场景 1：从列表点击进入事项详情

1. 用户在左侧导航点「事项」，进入 `/#/todos`，默认形态（卡片/列表）按 localStorage 恢复
2. 若为列表形态，看到 table：每行一个事项，列含 ID、标题、状态、标签、执行器、专家、调度器、最近执行状态、最近执行时间、更新时间、操作
3. 用户点击某行（除操作列按钮外）→ URL 变为 `/#/todos/123`，进入事项详情页
4. 详情页顶部有「返回列表」按钮，点击回到 `/#/todos`（保留列表形态与上次筛选/分页状态）

## 场景 2：从卡片墙进入事项详情

1. 用户在 `/#/todos` 切到卡片形态
2. 点击某张卡片 → URL 变为 `/#/todos/123`（不再临时切到列表形态）
3. 详情页「返回」回到 `/#/todos` 卡片形态

## 场景 3：刷新/分享事项详情

1. 用户在事项详情页 `/#/todos/123`，按 F5 刷新
2. 页面直接恢复 `/#/todos/123` 的详情内容，不跳回列表
3. 用户复制 URL 发给同事，同事打开后直接看到事项 #123 的详情

## 场景 4：环路详情独立路由

1. 用户在 `/#/loops` 列表形态看到环路 table
2. 点击某行 → URL 变为 `/#/loops/456`，进入环路详情页
3. 详情页「返回」回到 `/#/loops`

## 场景 5：帖子详情页（带参执行记录）

1. 用户在事项详情页 `/#/todos/123` 的执行历史中点击某条记录
2. URL 变为 `/#/todos/123/posts/3581`，进入帖子详情页（即现有 `TodoPostPage`）
3. 该页可直接刷新恢复

## 场景 6：批量操作

1. 用户在 `/#/todos` table 列表中通过行复选框选中多条
2. 顶部 `ActionToolbar` 显示批量操作按钮（更换执行器、复制到、移动到、暂停/恢复周期执行）
3. 点击「更换执行器」→ 弹窗选择 → 执行 → 列表刷新
4. 环路 table 同理，提供复制到、移动到、强停

# 6. 约束条件

## 6.1 技术约束

- 前端：React + TypeScript + Ant Design，`npx tsc --noEmit` 零错误
- 跨目录导入用 `@/` 别名，禁止 `../` `../../`
- 单函数体 ≤ 30 行；每个公开函数有单元测试
- 前端 UI 改动必须 Playwright 验证（脚本放 `frontend/tests/`）
- 后端无改动，`cargo clippy` / `cargo test` 不在本期范围

## 6.2 架构约束

- 路由方案沿用项目现有 hash 路由机制（`useViewState` + `window.history.pushState`），不引入 react-router
- path 段参数解析扩展 `getHashPath()`，与现有 query 参数解析共存
- table 组件统一用 Ant Design `Table`，不引入第三方表格库
- 详情页容器统一用 `PageCard`（与卡片墙、设置页等保持视觉一致）
- **不做旧 URL 兼容**：所有内部代码与外部入口统一使用新路由，旧 `/#/items` 系列 URL 不再做自动重定向

## 6.3 安全约束

- 无新增 API，无新数据暴露
- 现有 workspace 层级权限校验不变

## 6.4 性能约束

- table 默认前端分页 20 条/页，避免一次渲染大量行
- 详情页打开时不预加载列表数据（独立页面，无左右联动开销）
- 卡片墙性能不变

# 8. 接口与数据约定

## 8.1 路由扩展（统一命名空间）

```text
/#/todos                          事项列表（卡片/列表形态切换，默认 localStorage）
/#/todos/:id                      事项详情页（独立）
/#/todos/:id/posts/:recordId      事项的某次执行记录帖子页
/#/loops                          环路列表（table 形态）
/#/loops/:id                      环路详情页（独立）
/#/loops/config                   环路工作空间配置页（保留入口，可选）
```

> **统一原则**：`/#/todos` 是事项命名空间根路径，列表与详情共用 View 类型 `todos`，靠 path 段区分。`/#/items` 旧命名废弃，所有内部跳转、导航、书签统一迁移到 `/#/todos`。

## 8.2 数据接口

无新增接口。复用：

- `db.getTodoCenter(workspaceId)` — 列表数据（已返回 `last_execution_status` / `last_execution_at` / `referencing_loops` 等聚合字段）
- `db.getTodo(workspaceId, todoId)` — 详情数据（如已加载则从 `state.todos` 取）
- `dbLoops.listLoops(workspaceId)` — 环路列表
- 现有执行历史、批量操作接口

# 9. 验收标准（Acceptance Criteria）

## 9.1 路由验收

- 访问 `/#/todos/123` 直接进入事项 #123 详情页，刷新后仍在
- 访问 `/#/loops/456` 直接进入环路 #456 详情页，刷新后仍在
- 访问 `/#/todos/123/posts/456` 进入帖子详情页，刷新后仍在
- 访问 `/#/todos` 进入事项列表（卡片或列表形态按 localStorage 恢复）
- 访问 `/#/loops` 进入环路列表
- 全站无任何位置仍使用 `/#/items` 或 `?panel=detail|post` 形态的 URL（grep 验证）

## 9.2 列表 table 验收

- `/#/todos` 列表形态显示为单栏 table（不再有左侧列表 + 右侧详情的双栏）
- table 列顺序与 §8.3 一致，每列数据正确
- 单击行（除操作列、复选框）跳转 `/#/todos/:id`
- 行复选框多选触发 `ActionToolbar`，批量操作可用
- 搜索框、刷新按钮工作正常
- 分页器存在，默认 20 条/页

- `/#/loops` 显示为单栏 table，列顺序与 §8.4 一致
- 单击行跳转 `/#/loops/:id`
