## 1. 背景（Why）

环路（Loop）在异常终止（超步数 `capped_step` / 超 Token `capped_token` / 执行失败 `failed`）时，会触发一段「异常处理」逻辑做补救或清理。经代码调查，当前异常处理存在**双入口且互相割裂**的问题：

- **工艺（Process YAML）侧**：`AbnormalHandlerConfig` 只定义了 `todo_template`（文本）+ `trigger_on`（数组）。但 `installer.rs` 安装时**根本不解析 `todo_template`**（用 `..Default::default()` 留空），`loops.abnormal_handler_todo_id` 始终为 NULL。**即工艺中配置异常处理实际上不生效。**
- **环路（Loop）侧**：异常处理靠用户在 `LoopFormModal` 弹窗里**手动选一个已存在的 Todo**（`abnormal_handler_todo_id`），运行时 `loop_runner.rs::trigger_abnormal_handler` 加载该 Todo、取其 `prompt` 执行。

这违背了「环路忠实于工艺 YAML 定义」的原则——工艺应是唯一权威来源，环路是工艺的具体运行实例，其属性与逻辑应忠于工艺定义。当前环路却用一个工艺里不存在的「外部 Todo 引用」来承载异常处理，导致：

1. 工艺里的异常处理配置是死字段，用户写了不生效；
2. 异常处理提示词散落在某个 Todo 的 `prompt` 里，与工艺定义脱节，无法随工艺导出/版本跟踪；
3. 概念上有两套来源，维护成本高。

此外，当前运行时注入异常上下文用的是 `format!` **硬编码拼接** `## 异常上下文` 段落，用户在 prompt 里写 `{{loop_name}}` 等**占位符不会被替换**，无法主动引用变量；且未注入「失败原因」等错误信息，异常处理 prompt 信息不足。

本需求将异常处理**统一为工艺驱动**：在工艺 YAML 中直接定义异常处理提示词（`prompt`），安装时写入环路，触发时执行该提示词并**用占位符替换注入异常上下文与错误信息**；**彻底废弃环路弹窗中选择已有 Todo 兜底的方式**。

> 背景：项目尚未上线、无用户，**不需要处理存量数据兼容**。

## 3. 非目标（Explicitly Out of Scope）

- ❌ 不删除 `loops.abnormal_handler_todo_id` 数据库列——运行时仍读取它（指向安装时创建的载体 Todo）；增量迁移框架不做 DROP
- ❌ **不处理存量数据**——项目未上线、无用户；migration 只加列不回填，不做存量兼容
- ❌ **不动环路导入导出功能**——后期会整体移除环路导入导出；本次不主动改造（仅当字段变更导致编译错误时做最小适配）
- ❌ 不改异常处理的**触发时机**——仍是 4 个触发点（run 失败 / capped_step / capped_token / 主循环结束 failed|partial）
- ❌ 不改 `abnormal_handler_trigger_on` 的取值集合——仍是 `capped_step` / `capped_token` / `failed`
- ❌ 不改异常处理执行的特殊步骤记录机制——仍用 `step_id = -1`、`sequence_index = 999` 标识，绕过 FK 的原始 SQL 插入保留
- ❌ 不改触发条件运行时过滤逻辑——`trigger_on` 不含当前状态则跳过的判断保留
- ❌ 不把异常处理 prompt 拆成独立表——内联存储在 `loops`，与工艺定义同处
- ❌ 不改底层 `run_todo_execution_with_params` executor 接口签名

## 4. 使用场景 / 用户路径

### 场景 A：在工艺中定义异常处理（主路径）

1. 用户在工艺编辑器打开全局面板（`GlobalPropertyForm`）
2. 在「异常处理」区域勾选触发条件（如：失败、Token 超限），并在「异常处理 Prompt」框填写提示词
   - 可点击下方**快捷变量条**插入占位符（如 `{{abnormal_status}}`、`{{error_detail}}`），在 prompt 中主动引用运行时上下文
3. 保存工艺
4. 安装或升级环路 → 自动创建 `todo_type=3` 载体 Todo + 写入 `loops.abnormal_handler_prompt` 与 `abnormal_handler_trigger_on`
5. 环路运行中触发任一选中条件 → `trigger_abnormal_handler` 执行载体 Todo 的 prompt，**占位符已被替换**为实际异常上下文与错误信息（并前置 workspace 共识）
6. 用户在环路编辑弹窗里能看到「触发条件」（只读，灰显），但无法修改——异常处理逻辑忠于工艺

### 场景 B：工艺未配置异常处理 prompt

1. 工艺的 `abnormal_handler.prompt` 为空（或缺省）
2. 安装后不创建载体 Todo，`loops.abnormal_handler_prompt` 为 NULL
3. 环路异常终止时，`trigger_abnormal_handler` 检测到无载体 Todo → 静默跳过，不执行任何异常处理
4. 环路弹窗触发条件只读区展示「未配置」

## 6. 约束条件

- **工艺为唯一权威来源**：异常处理的 prompt 与触发条件都由工艺 YAML 定义，安装写入环路。环路运行时只读执行，不可偏离工艺定义。
- **触发条件在环路层只读**：环路编辑弹窗展示 `trigger_on`，但用户不可修改——修改异常处理逻辑必须回到工艺编辑器。
- **占位符替换一致性**：占位符统一用 **`{{双花括号}}`**（与评审 prompt `compose_review_prompt` 一致，单花括号不替换）。运行时对异常处理 prompt 做占位符替换后，再前置 workspace 共识、末尾兜底追加 `## 异常上下文` 段落（确保不写占位符也能看到上下文）。
- **错误信息注入**：异常处理 prompt 可用 `{{error_detail}}` 引用失败原因。来源：run 致命失败时为 `Err` 信息；超步数/超 Token 时为超限描述；无具体错误时为空。
- **向后兼容（YAML）**：旧工艺 YAML 的 `abnormal_handler.todo_template` 字段——serde 反序列化时忽略未知字段（`AbnormalHandlerConfig` 不 `deny_unknown_fields`），不报错；`prompt` 缺省为 None。
- **不处理存量数据**：migration 只加 `abnormal_handler_prompt` 列，不回填、不做存量兼容。
- **安全**：异常处理 prompt 由工艺作者定义，信任级别与 `acceptance_criteria` / `review_prompt` 相同，不做内容过滤（与现状一致）。

## 8. 接口与数据约定

| 层 | 位置 | 约定 |
|----|------|------|
| YAML | `abnormal_handler.prompt` | string，可选，多行；空/缺省 = 未配置异常处理 |
| YAML | `abnormal_handler.trigger_on` | string 数组，取值 `capped_step` / `capped_token` / `failed` |
| YAML | `abnormal_handler.todo_template` | **已废弃**，serde 忽略 |
| DB | `loops.abnormal_handler_prompt` | `TEXT NULL`；NULL = 未配置 |
| DB | `loops.abnormal_handler_todo_id` | 保留列；运行时指向安装时创建的 `todo_type=3` 载体 Todo |
| DB | `todos.todo_type = 3` | 异常处理载体 Todo |
| 运行时 | 异常 prompt 合成顺序 | `workspace 共识 → 占位符替换后的 prompt 正文 → ## 异常上下文（兜底段落）` |
| 运行时 | 占位符变量 | `{{loop_name}}` `{{loop_execution_id}}` `{{abnormal_status}}` `{{total_executed_steps}}` `{{total_tokens_used}}` `{{error_detail}}` |
| 运行时 | 触发判断 | `trigger_on` 含当前状态 且 载体 Todo 存在（prompt 非空）→ 执行 |

## 9. 验收标准

1. 工艺 YAML 写 `abnormal_handler.prompt` + `trigger_on`，安装后 `loops.abnormal_handler_prompt` 有对应值，且存在一个 `todo_type=3` 载体 Todo
2. 环路异常触发时，AI 实际收到的执行 prompt = 用户写的 `prompt`，其中 `{{abnormal_status}}` `{{error_detail}}` 等占位符已被替换为运行时实际值（并前置 workspace 共识 + 末尾异常上下文段落）
3. `abnormal_handler_prompt` 为空的环路，异常终止时静默跳过，不执行、不报错
4. 环路编辑弹窗无「异常处理 Todo」选择器；「触发条件」Checkbox 为只读（灰显，值=工艺定义）
5. 工艺编辑器「异常处理 Prompt」框下方有快捷变量条，点击可把 `{{key}}` 追加到 prompt，保存后重新打开值保留
6. 含旧字段 `todo_template` 的工艺 YAML 可正常保存、安装、执行，不报错（serde 忽略未知字段）
7. `cd backend && cargo test` 全量通过；`cargo clippy --all-targets -- -D warnings` 零告警
8. `cd frontend && npx tsc --noEmit` 零错误
9. Playwright 验证：工艺编辑器编辑异常处理 prompt + 快捷变量插入；环路弹窗触发条件只读；事项列表异常处理 Todo 显示「异常处理」标签

## 10. 风险与已知不确定点

- **占位符替换机制变更**：当前运行时用 `format!` 硬编码拼接异常上下文，本次改为占位符替换 + 兜底段落。未上线无用户，行为变更无负担；但需确保替换工具与评审 prompt 一致（双花括号），避免再次出现「占位符原样发给 AI」的历史问题。
- **错误信息来源不一致**：4 个触发点中，run 失败能拿到 `Err` 信息，超限触发点能拿到超限描述，主循环结束 failed/partial 可能无具体错误。`{{error_detail}}` 在无具体错误时为空，prompt 应能容忍空值（兜底段落也会带异常状态）。
- **导入导出最小适配**：若 `LoopDto` 移除 `abnormal_handler_todo_id` 导致导入导出编译错误，做最小适配（导入导出读 loop model entity，entity 保留该列，通常不受影响）；不主动重构导入导出。

- 不处理存量数据（未上线无用户）
