| 修改人 | 修改时间 | 修改内容 |
|--------|---------|---------|

## 1. 背景（Why）

任务（`tasks`）目前只有一种执行形态：**绑定一个工艺环路（Loop）**，按工艺模板预设的阶段/环节/门禁编排执行。用户在「新建任务」时必须选一个环路，提交后由环路的多环节推进。

但很多需求**不需要、也无法预设流程**——它只是「把这条需求交给某个专家或执行器跑一次」，甚至希望由一个**协调者专家（任务管家）**自己看着办、动态 `@` 合适的人接力推进，直到完成。

事实上，这套「分配处理人去执行」的机制在 060（任务讨论区）里已经存在：讨论区的 `@专家`/`@执行器` 会建一个隐藏载体 Todo 并触发执行、结论回帖。本需求做的，是**把讨论区已有的「指派执行」能力，提升到任务创建的入口**，并新增「自动接力」让管家型专家能自主调度。

最终任务的执行方式从「只能选环路」扩展为二选一：
- **工艺环路**（现有，不变）
- **委派**（新）：交给一个专家或执行器；可选开启「自动接力」交给管家型专家自主调度。

**关键事实**（沿用 060，影响整个设计）：
- 执行系统是 **Todo 中心**的，所有执行都走 `run_todo_execution`，必须有 Todo 作载体；Task 本身不直接执行。
- 060 已实现「发含 `@` 的讨论帖 → 建隐藏载体 Todo → 触发执行 → 结论回帖」的完整闭环，本需求**复用它**，不造新执行引擎。
- **专家（Expert）与执行器（Executor）正交**：专家是人设/角色包，自己不执行，靠 `inject_expert_context` 注入后交给执行器跑；执行器是 CLI（Claude Code/Codex 等）。

## 2. 目标（What，可验证）

- [ ] **T1** 「新建任务」弹窗增加「执行方式」单选：**工艺环路** / **委派**。
- [ ] **T2** 选「委派」时，可显式选择一个**专家**或一个**执行器**作为处理人；同时填写需求文本。
- [ ] **T3** 委派任务创建后**立即触发首次执行**：自动在讨论区落地一条含 `@处理人` 的需求帖 + 一条 `running` 智能体占位帖（复用 060 的 `@` 触发与回写机制）。
- [ ] **T4** 选「工艺环路」时，行为与现状完全一致（向后兼容，回归不破）。
- [ ] **T5** 委派带「自动接力」开关（默认关）；**仅当选「专家」时可开启**（执行器是 CLI，无调度能力）。
- [ ] **T6** 自动接力开启后：每次执行完成，系统自动以该专家身份发一条接力帖（喂入任务状态 + 讨论历史），由专家决定下一步；专家若在接力帖中 `@` 了别人则触发下一轮执行，形成循环，**直到专家不再 `@` 任何人或触达护栏**。
- [ ] **T7** 自动接力**护栏**：接力轮数计数，达到上限（默认 **10**）强制停止；用户可随时在讨论区删帖/停执行终止接力。
- [ ] **T8** 委派任务详情页以**讨论 Tab 为主视图**（无环路环节视图）；自动接力进行中时展示调度状态。
- [ ] **T9** 全流程零编译告警：后端 `cargo clippy --all-targets -- -D warnings`、`cargo test` 通过；前端 `npx tsc --noEmit`、`npm run build` 通过。

## 3. 非目标（Explicitly Out of Scope）

- **不**设置「工作空间级默认管家」——委派目标在任务级指定即可（YAGNI）。
- **不**引入「管家」为独立实体类型——管家就是被开启自动接力的那个协调者专家。
- **不**改动工艺环路（Loop）的任何既有行为与表结构。
- **不**改动 060 讨论区的 `task_posts` 表结构、`@` 解析逻辑、回写状态机。
- **不**改动执行器适配器契约（`CodeExecutor` trait）与专家 plugin.json 格式。
- **不**引入新的执行引擎；执行仍走现有 `run_todo_execution` 管线。
- 第一版**不**做自动接力的「成本/Token 上限」与「人类检查点自动停顿」，仅以轮数上限兜底；二者另立增强需求。
- 第一版**不**做 `@任务管家` 这类快捷别名提及（用户直接 `@` 具体专家名即可）。

## 4. 使用场景 / 用户路径

**场景 A（按工艺环路，不变）**
新建任务 → 执行方式选「工艺环路」→ 选环路 → 填需求 → 提交 → 按预设流程多环节执行。

**场景 B（委派执行器，一次性）**
新建任务 → 执行方式选「委派」→ 处理人选「执行器 codex」→ 填需求「分析这段日志报错根因」→ 自动接力保持关 → 提交 → 讨论区出现需求帖 + codex 执行占位帖 → 执行完结论回帖，任务到此为止（后续靠人手动在讨论区追问）。

**场景 C（委派专家，一次性）**
新建任务 → 执行方式选「委派」→ 处理人选「专家·前端架构师」→ 填需求 → 自动接力关 → 提交 → 用默认执行器套该专家人设跑一次，结论以专家身份回帖。

**场景 D（委派管家专家，自动接力/托管）**
新建任务 → 执行方式选「委派」→ 处理人选一个协调者型专家「专家·任务管家」→ 填需求 → **开启自动接力** → 提交 → 管家被唤醒，看任务状态后发 `@codex 做X` 帖 → codex 执行完回帖 → 系统再次唤醒管家 → 管家发 `@某专家 做Y` → ……循环，直到管家判定完成（不再 `@`）或达到 10 轮上限。

**场景 E（随时人工接管）**
任意时刻，用户可在讨论区手动 `@专家`/`@执行器` 继续推进；也可删除 running 占位帖终止进行中的执行。

## 6. 约束条件

- **技术约束**：复用现有执行管线 `run_todo_execution` 与 060 讨论区 `@` 机制，零新执行引擎；生产代码禁止 `.unwrap()`/`.expect()`/`panic!`（`#[cfg(test)]` 除外）；单函数体 ≤50 行（超需豁免理由）；每个公开函数有单元测试并覆盖正常/边界/错误分支。
- **架构约束**：后端分层 Entity(`db/entity`) → DAO(`db`) → Handler(`handlers`)；前端跨目录导入统一用 `@/` 绝对路径，禁止 `../` 回退。
- **安全约束**：处理人（专家/执行器名）必须服务端校验真实存在（防伪造任意名执行）；执行受既有并发上限与 workspace 隔离约束；接力帖不得绕过 `@` 校验直接触发执行。
- **性能约束**：自动接力是异步事件驱动（执行完成回调触发），不得同步阻塞 HTTP 请求；接力轮数有硬上限，不得无限循环。
- **兼容约束**：`execution_mode` 缺省值 `loop`，旧客户端/旧数据零影响；`loop` 模式回归不破。

## 8. 接口与数据约定

### 8.1 `tasks` 表新增列

| 字段 | 类型 | 默认 | 说明 |
|------|------|------|------|
| `execution_mode` | TEXT | `'loop'` | `'loop'`（工艺环路）/ `'delegate'`（委派） |
| `assignee_kind` | TEXT | NULL | 委派对象类型：`'executor'` / `'expert'`（仅 delegate 模式有值） |
| `assignee_name` | TEXT | NULL | 委派处理人名（执行器名或专家名） |
| `auto_continue` | INTEGER | `0` | 自动接力开关：`0`关 / `1`开；仅 `assignee_kind='expert'` 时允许为 `1` |
| `continue_rounds` | INTEGER | `0` | 自动接力已轮数计数（护栏用，到 `max_continue_rounds` 停止） |

`delegate` 模式下 `loop_id` 为 NULL（现有 `loop_id` 已是 `Option`，兼容）。

### 8.2 API

扩展 `POST /api/v1/workspaces/{ws}/tasks`（`create_task`）请求体：

```json
{
  "requirement": "需求文本",
  "loop_id": 12,
  "execution_mode": "delegate",
  "assignee_kind": "expert",
  "assignee_name": "任务管家",
  "auto_continue": true
}
```

- `execution_mode='loop'`（或缺省）：必须带 `loop_id`，行为同现状；忽略委派字段。
- `execution_mode='delegate'`：不带 `loop_id`；必须带 `assignee_kind` + `assignee_name`；`auto_continue` 仅在 `assignee_kind='expert'` 时允许 `true`，否则 400。
- 响应沿用现有 `{ task_id, loop_id, execution_id }`（delegate 模式 `loop_id` 为 `null`，`execution_id` 为首次执行的记录 id）。

自动接力为后端事件驱动，**不新增 HTTP 接口**；接力帖就是一条普通的 `task_posts`（`kind='agent'`、`trigger_type='discussion_auto'` 由执行记录体现），前端复用 060 的讨论帖渲染与轮询/事件更新。

### 8.3 错误码语义

| HTTP | 场景 |
|------|------|
| 400 | `execution_mode='delegate'` 但缺 `assignee_kind`/`assignee_name`；`assignee_kind='executor'` 且 `auto_continue=true`；`assignee_name` 指向不存在的专家/执行器；`execution_mode='loop'` 但缺 `loop_id` |
| 404 | `loop_id` 或 workspace 不存在、不属于当前 workspace |

## 9. 验收标准（Acceptance Criteria）

1. **若**打开「新建任务」弹窗，**则**看到「执行方式」单选（工艺环路 / 委派），默认工艺环路。
2. **若**选「工艺环路」并提交，**则**任务按现状绑定环路执行，行为与改动前完全一致（回归通过）。
3. **若**选「委派」+ 处理人「执行器 codex」+ 自动接力关并提交，**则**任务创建成功（`loop_id=NULL`），讨论区出现一条含 `@codex` 的需求帖和一条 `running` 智能体占位帖；执行完成后占位帖变为结论、状态 `success`/`failed`，任务不再自动推进。
4. **若**选「委派」+ 处理人「专家·前端架构师」+ 自动接力关并提交，**则**用默认执行器套该专家人设执行一次，结论以专家身份回帖。
5. **若**在委派 UI 中把处理人选为「执行器」，**则**「自动接力」开关被禁用且不可开启，并有文案说明原因。
6. **若**选「委派」+ 专家 + **开启自动接力**并提交，**则**首次执行完成后，系统自动以该专家身份发一条接力帖；专家若在接力帖 `@` 了别人，则触发下一轮执行；如此循环。
7. **若**自动接力某轮专家不再 `@` 任何人，**则**循环自然终止，任务进入完成态/等待态。
8. **若**自动接力轮数累计达到 10（默认上限），**则**强制停止接力，并留下一条说明帖。
9. **若**用户在讨论区删除某个 `running` 智能体帖，**则**联动取消对应执行（沿用 060 已有能力），进行中的接力随之停止。
10. **若**运行 `cargo clippy --all-targets -- -D warnings`、`cargo test`、`npx tsc --noEmit`、`npm run build`，**则**全部通过。

## 10. 风险与已知不确定点

- **自动接力失控（成本/死循环）**：缓解 = 硬轮数上限（默认 10）+ 用户可随时删帖停执行兜底；第一版不做 Token 上限与人类检查点，列入后续增强。AI 不得移除护栏。
- **非协调者专家开自动接力**：被指派的专家若人设是「自己干活」而非「调度」，开启自动接力可能自我重复空转——护栏仍会兜底停止；UI 在开启自动接力时提示「建议选用协调者型专家」。AI 不替用户判断专家是否为协调者，由用户选择负责。
- **接力帖递归触发**：接力帖用专用 `trigger_type='discussion_auto'`，completion 据此识别「自身这一跳」，避免把接力帖的执行完成又误判为新的接力触发而无限递归。
- **载体 Todo 累积**：每次执行（含接力每轮）产生一个隐藏载体 Todo，与 060 同量级；如需清理另立需求，不在本次范围。
- **专家名与执行器名冲突（同名）**：沿用 060 的「先专家后执行器」消歧；遇到无法消歧的同名时，AI 停止并请求人工确认。
- **执行失败后的接力**：某轮执行 `failed` 时是否继续唤醒管家——第一版**仍唤醒**（让管家决定重试或换人），由护栏兜底；若需「失败即停」策略，另立需求明确。

## 11. 非目标（再次明确）

- 本需求**不**实现：工作空间默认管家、管家独立实体类型、工艺环路行为变更、060 讨论区机制重写、新执行引擎、执行器/专家配置体系改动、Token 成本上限、人类检查点、`@管家` 别名。
- 上述能力若后续需要，另立 L1 需求，不在 092 范围内推进。
