> 需求文档：`docs/requirements/092-任务委派执行-需求.md`；设计文档：`docs/design/092-任务委派执行-设计.md`。
> 本 PR 为 **P1（委派地基，auto_continue 仅入库不消费的手动单跑模式）**；P2（自动接力/管家调度 + 护栏）另立 PR。

---

## 范围与分期

需求 092 拆为两个 PR，本 PR 只交付 P1：

- **P1（本 PR）** —— 对应需求 T1/T2/T3/T4/T8(UI)/T9、验收 AC1/2/3/4/5/10：
  - 「新建任务」可选执行方式（工艺环路 / 委派），默认工艺环路且行为与现状完全一致（回归不破）。
  - 委派模式：显式选处理人（专家 / 执行器）+ 填需求 → 建无环路 task（`loop_id=NULL`）+ 在讨论区落 `@处理人` 首帖触发首次执行（复用 060 的 `@` 机制，零新执行引擎）。
  - 委派 UI 的「自动接力」开关已就位（仅专家可开、执行器禁用并提示），但 **P1 后端不消费 `auto_continue`**（仅存库），即每次委派都是「手动单跑」。
- **P2（后续 PR）** —— 对应需求 T6/T7、F5/F6/F7、验收 AC6/7/8/9：
  - `executor_service/completion.rs` 新增 `trigger_type='discussion_auto'` 自动接力分支：执行完成后以 assignee 专家身份发接力帖，专家在帖中 `@` 别人则触发下一轮，循环至完成或护栏。
  - `continue_rounds` 每轮 +1，达 `MAX_DELEGATE_ROUNDS=10` 强制停止 + 留说明帖。
  - 详情页/讨论区展示「管家调度中（第 N/10 轮）」状态。

> 把 P1 的开关 UI 先做好、行为留 P2，是为了让 P1 成为「可独立验证、不引入失控循环」的最小安全切片；P2 在此之上叠加事件驱动的自动接力。

## P1 改动清单

### 后端

- **`db/entity/tasks.rs`**：`Model` 新增 5 字段 `execution_mode / assignee_kind / assignee_name / auto_continue(i64) / continue_rounds(i64)`，与迁移列一一对应。
- **`db/migration/v91.rs`（新增 `V91TaskDelegateExecution`）**：用 `add_column_if_missing` ×5 幂等追加列（`execution_mode TEXT NOT NULL DEFAULT 'loop'`、`assignee_kind TEXT`、`assignee_name TEXT`、`auto_continue INTEGER NOT NULL DEFAULT 0`、`continue_rounds INTEGER NOT NULL DEFAULT 0`）。附「重复执行幂等」「列已存在幂等」两条单测。
- **`db/migration/mod.rs`**：注册 `v91`（`mod v91;` + `all_migrations()` vec 末尾追加 `Box::new(v91::V91TaskDelegateExecution)`）。
- **`db/migration/consolidated_schema.rs`**：`tasks` 建表语句追加 5 列，严格复刻 SQLite `ALTER TABLE ADD COLUMN` 的单行 `, coldef` 输出格式（与 `agent_bots`/`executors` 模板一致，列定义内不放 SQL 注释），`test_consolidated_schema_matches_incremental` 漂移守卫通过。
- **`db/task.rs`**：新增独立 DAO `create_delegate_task(title, workspace_id, assignee_kind, assignee_name, auto_continue)`——设 `execution_mode="delegate"`、`loop_id=None`、`continue_rounds=0`。独立方法（非重载 `create_task`）避免影响既有环路调用方。
- **`handlers/task_posts.rs`**：
  - 抽出 `pub(crate) async fn land_mention_post(state, task, content, parent_post_id, author, trigger_type)`——封装 060 的「提取 `@` → 解析处理人 → 写人类帖 → 触发执行建占位帖」闭环，供 `create_post` 与委派首帖共用，消除逻辑漂移。
  - `trigger_discussion_execution` / `create_agent_post` 增加 `trigger_type: &str` 入参（替换原硬编码 `TRIGGER_DISCUSSION`），为 P2 传入 `discussion_auto` 预留；`TRIGGER_DISCUSSION` 提为 `pub(crate)`。
- **`handlers/tasks.rs`**：
  - `CreateTaskRequest`：`loop_id` 改 `Option<i64>`，新增 `execution_mode`（`#[serde(default)]`）、`assignee_kind` / `assignee_name`（`Option`）、`auto_continue`（`#[serde(default)] bool`）。
  - `create_task` 按 `execution_mode` 分发：`delegate` → `create_delegate_task`，否则 → `create_loop_task`（原环路逻辑，`loop_id` 缺失返回 400）。
  - `create_delegate_task`：校验处理人（kind ∈ {executor,expert}、name 非空、executor+auto_continue→400、`validate_assignee_exists` 查真实存在）→ 拼 `task_title_from_requirement`（CJK 安全截断 ≤60）→ DAO 建 task → 写需求描述 → `land_mention_post` 落 `@处理人 需求` 首帖 → 返回 `{task_id, loop_id:null, execution_id}`。
  - `validate_assignee_exists`：专家走 `expert_manager.get_expert_by_name`、执行器走 `find_executor`，防伪造任意名执行。
  - `TaskItem` / `build_task_item` / `get_task_detail` 的任务 JSON 补委派字段，`auto_continue` 以 `!= 0` 序列化为 `bool`。
  - 新增 4 条单测：`test_create_delegate_rejects_executor_with_auto_continue`、`_rejects_missing_assignee`、`_rejects_unknown_assignee`（均 400 且不触发真实执行）、`test_dao_create_delegate_task_fields`（DAO 字段正确）。

### 前端

- **`components/tasks/constants.tsx`**：`TaskItem` 增 5 个可选委派字段。
- **`api/bundled.ts`**：`createTask` 改对象参数签名（`{ requirement, loopId?, executionMode?, assigneeKind?, assigneeName?, autoContinue? }`），按模式组装；`listTasks` 返回补委派字段。
- **`components/tasks/CreateTaskModal.tsx`**（重写）：执行方式 `Radio`（工艺环路 / 委派，默认环路）；`Form.useWatch` 监听 `executionMode`/`assigneeKind` 联动——环路模式显环路下拉，委派模式显 `Segmented`（专家/执行器）+ 处理人 `Select`（专家来自 `getAllExperts`、执行器来自 `EXECUTORS_FOR_PICKER`）+ 自动接力 `Switch`（执行器时禁用并提示）。`data-testid` 覆盖关键字段供 E2E 定位。
- **`components/tasks/TaskDetailPanel.tsx`**：`TaskDetailData.task` 补委派字段；委派任务默认落到「讨论」Tab（无环路环节视图）；委派任务隐藏「再次执行」按钮（执行发生在讨论区，靠 `@` 推进）。

## 安全反思

- **处理人真实性**：`assignee_name` 服务端经 `validate_assignee_exists` 校验（专家查 `expert_manager`、执行器查 `find_executor`），拒绝伪造任意名执行。
- **双重护栏**：`executor + auto_continue=true` 前端禁用开关 + 后端 400，防绕过。
- **零新执行引擎**：委派首帖完全复用 060 的 `@` 触发链路（`land_mention_post` 共用），执行仍走 `run_todo_execution`，未引入新的越权面或并发模型。
- **workspace 隔离**：委派 task 带 `workspace_id`，讨论区帖与载体 Todo 沿用 060 既有归属校验。
- **生产代码**：无 `.unwrap()`/`.expect()`/`panic!`（仅 `#[cfg(test)]`）。

## 已知限制 / P2 待办

- `auto_continue` **P1 仅入库不消费**：委派任务目前都是「手动单跑」，执行完即停（用户可在讨论区手动 `@` 继续）。自动接力行为见 P2。
- `continue_rounds` **P1 不递增**：护栏计数与「达 10 轮强制停」逻辑在 P2。
- 调度状态展示（「管家调度中 第 N/10 轮」）在 P2。
- 与 060 一致：委派成功路径会真实 spawn 执行器，故未做端到端提交测试，仅覆盖 400 校验分支 + DAO 层（与 060 的测试策略对齐）。
