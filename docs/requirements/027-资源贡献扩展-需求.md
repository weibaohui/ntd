# 027-资源贡献扩展-需求

| 修改人 | 修改时间 | 修改内容 |
|--------|---------|---------|
| AI | 2026-08-14 | 初始版本：专家贡献（026）扩展到事项模板 / 技能 / 工艺三类资源 |

---

# 1. 背景（Why）

026「专家贡献」已为专家建立「分享到官方仓库」通道：用户点「分享」→ ActionButton 唤起 AI 执行器 → AI 读取本地 PAT、调用 GitCode API 把资源打包为 PR 提交到官方仓库 `weibaohui/ntd-resource`，由维护者 review 合入。

远端仓库 `ntd-resource` 可单向同步 **4 类资源**（目录结构已确认）：

```
ntd-resource/
├── experts/      # 专家定义（WorkBuddy 格式，每专家一个目录）
├── processes/    # 工艺模板（按分类子目录，如 processes/software/*.yaml）
├── skills/       # 内置技能（按来源集合分组，如 skills/{source_collection}/{skill}/）
└── todos/        # Todo 事项模板（YAML 文件，如 todos/{title}.yaml）
```

当前只有专家有贡献通道，事项模板 / 技能 / 工艺三类资源**无法回传远端**。本需求将 026 的贡献通道按同一套机制扩展到这三类资源。

# 2. 目标（What，必须可验证）

- [ ] 事项模板 / 技能 / 工艺三类资源在对应 UI 提供「分享到官方仓库」入口。
- [ ] 分享入口沿用专家的来源原则：**工艺 / 事项模板只对用户自己的资源（`is_system=false`）渲染**；**技能不区分来源，全部可分享**（用户明确要求）。
- [ ] 后端为事项模板新增「导出为 YAML 文件」能力（模板存 DB，AI 执行器只能读文件，必须先导出落盘）。
- [ ] 分享提示词按资源类型区分，明确把资源提交到远端仓库的对应子目录（`processes/`、`skills/`、`todos/`），格式与远端已有文件对齐。
- [ ] 复用 026 已建成的 PAT 管理（设置→第三方授权→GitCode）与 ActionButton 执行链路，不重复建设。

# 3. 非目标（Explicitly Out of Scope）

- 不做后端确定性 fork / 建分支 / 写文件 / 建 PR 调用（沿用 ActionButton + AI 提示词驱动）。
- 不做 PR 后续进度跟踪与多账号管理（沿用 026 单 PAT 方案）。
- 不改变现有单向同步（git reset --hard）的只读语义。
- 技能类不做「用户/系统」来源守卫（用户明确要求全量可分享）；用户自己编写的技能若不在 `~/.ntd/bundled/skills/` 目录下，本期不单独处理（入口覆盖 bundled 技能列表）。

# 4. 使用场景 / 用户路径

1. 用户在本地创建/修改了一个事项模板（或工艺、技能），觉得好用，希望分享给其他用户。
2. 在对应列表 Tab 的行操作区点「分享到官方仓库」（与专家模板 Tab 入口一致）。
3. 未配置 PAT → 跳转「设置 → 第三方授权 → GitCode」引导填写（与 026 一致）。
4. 已配置 PAT → ActionButton 打开 Drawer：提示词已按资源类型预填（含资源名/版本/文件路径参数），用户可编辑、选执行器。
5. 执行 → AI 读取本地 PAT、按提示词把资源提交为 PR（fork → 建分支 → 写文件 → 建 PR），完成后展示 PR 链接。

# 5. 功能需求清单（Checklist）

- [ ] **事项模板分享**：模板管理→事项模板 Tab 行操作区新增「分享」；仅 `is_system=false`（用户创建）行渲染；分享前后端把模板导出为 YAML（`title/category/prompt/sort_order` 字段，与远端 `todos/*.yaml` 对齐）到本地导出目录，提示词引用导出文件路径。
- [ ] **工艺分享**：模板管理→工艺模板 Tab 行操作区新增「分享」；仅用户工艺（`is_system=false`，位于 `~/.ntd/processes/`）行渲染；提示词把 YAML 文件提交到远端 `processes/`（按 YAML 内 category 决定分类子目录，无匹配分类则放根目录）。
- [ ] **技能分享**：模板管理→Skill 模板 Tab 行操作区新增「分享」；**不做来源守卫，全部可分享**；提示词把技能目录（`~/.ntd/bundled/skills/{source}/{skill}/`）提交到远端 `skills/{source}/{skill}/`。
- [ ] **分享入口一致性**：三个 Tab 的分享按钮交互与专家模板 Tab 完全一致（点击查 PAT → 未配置跳设置 / 已配置切 ActionButton）。
- [ ] **提示词按资源类型区分**：`contributePrompt.ts` 泛化——公共部分（PAT 读取、GitCode API 步骤、安全约束）抽公共模板，资源特有部分（资源名/版本/目录/远端路径/跳过规则）参数化。
- [ ] **后端导出接口**：`GET /api/v1/todo-templates/:id/export`：把 DB 模板转成 YAML 写入 `~/.ntd/contribution-export/todos/{title}.yaml`（安全文件名校验），返回导出文件路径；系统模板（`is_system=true`）拒绝导出。

# 6. 约束条件

- **安全**：
  - PAT 沿用 026 方案（`~/.ntd/contribution_pat.json` 0600，不内联进提示词）。
  - 导出文件名做路径安全校验（防 `..` / 分隔符逃逸）。
  - 提示词要求 AI 最终输出不回显 PAT 明文。
- **架构**：
  - 后端只新增「事项模板导出」接口；工艺/技能为纯前端改动。
  - 不修改现有单向同步语义。
- **技术**：
  - 前端 `npx tsc --noEmit` 零错误；`frontend/src` 内跨目录导入用 `@/` 别名。
  - 后端 `cargo clippy --all-targets -- -D warnings` 零告警；生产代码禁止 `.unwrap()` / `.expect()` / `panic!`。
  - 单函数体 ≤ 30 行；每个公开函数有单元测试。

# 7. 可修改 / 不可修改项

- ❌ 不可修改：PAT 存储与验证（026 已建）、单向同步只读语义、fork + PR 提交方式。
- ✅ 可调整：分享入口的具体位置与文案、导出目录路径与 YAML 字段细节、提示词措辞与分支名格式。

# 8. 接口与数据约定

## 8.1 新增接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/todo-templates/:id/export` | 导出事项模板为 YAML 文件（写入本地导出目录），返回 `{ path }`；仅 `is_system=false` 可导出 |

## 8.2 复用接口（026 已建）

- `GET /api/v1/contribution/auth/status`、`POST /api/v1/contribution/pat`、`POST /api/v1/contribution/logout`
- 提交动作复用 `POST /api/v1/actions/execute`（ActionButton 链路），`action_type` 按资源区分。

# 9. 验收标准（Acceptance Criteria）

- 事项模板 Tab：用户模板行有「分享」，系统模板行无；点击用户模板分享 → 后端导出 YAML 到本地 → ActionButton 提示词含导出文件路径与 `todos/` 远端路径。
- 工艺 Tab：用户工艺行有「分享」，系统工艺行无；提示词含 `~/.ntd/processes/` 文件路径与 `processes/` 远端路径。
- Skill 模板 Tab：所有技能行都有「分享」（不区分来源）；提示词含 `skills/{source}/{skill}/` 路径。
- 三类资源未配置 PAT 时均提示并跳转「设置 → 第三方授权 → GitCode」。
- 后端 `todo-templates/:id/export`：用户模板返回 YAML 文件路径；系统模板拒绝；非法文件名不产生越界写入。

# 10. 风险与已知不确定点

- **事项模板导出目录**：`~/.ntd/contribution-export/` 为新增目录，需处理已存在同名文件的覆盖/改名策略（建议同名直接覆盖，提示词让 AI 提交最新文件）。
- **工艺分类子目录**：远端 `processes/` 有分类子目录（software/conventions），用户工艺 YAML 内 `category` 字段与远端分类的映射可能不完全一致，无匹配时放根目录兜底。
- **技能全量分享的语义**：bundled 技能分享回去等于原样回传/更新，意义有限但用户明确要求全量可分享；PR 合入权在维护者，风险可控。
