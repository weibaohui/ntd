# 1. 背景（Why）

全仓库静态引用分析（编译器检查之外）发现前后端存在大量逻辑死代码：定义存在但全仓库零引用的文件、导出、函数与依赖。死代码增加阅读成本、误导重构方向、拖慢编译，且部分属于"移除了一半"的废弃功能（loop 导入导出、自定义模板同步），留在仓库中会让人误以为功能仍在岗。

历史扫描见 `docs/decisions/ADR-004-死代码扫描-决策.md`（2026-07-19），其中条目经本次逐项核对已基本清理完毕，本次为新一轮全量扫描结果。

# 2. 目标（What，必须可验证）

- [ ] 删除前端 5 个零引用孤儿组件文件
- [ ] 删除前端 37 个零引用导出（函数/常量/类型）
- [ ] 删除后端 60 个零引用 pub 项（handler/db 函数/DTO/SDK 方法等）
- [ ] 从 `backend/Cargo.toml` 移除 3 个未使用依赖（`yaml-rust2`、`rusqlite`、`http-body-util`）
- [ ] 清理后 `cargo clippy --all-targets -- -D warnings` 零告警、`cargo test` 全通过、`npx tsc --noEmit` 零错误、`npm run build` 成功

# 3. 非目标（Explicitly Out of Scope）

- 不做任何功能性修改、重构或行为变更，纯删除
- 不删除数据库迁移 SQL（历史迁移需保留以保证旧库可升级）
- 不处理"有引用但逻辑不可达"的代码（本次仅处理零引用项）
- 不删除测试文件（测试文件不被 import 属正常）
- 不处理 `feishu_group_whitelist`（已核实为在岗代码，ADR-004 误报）

# 4. 使用场景 / 用户路径

开发者阅读/重构代码时，不再被无调用方的死代码误导；CI 编译时间略微缩短。

# 6. 约束条件（非常关键）

- 纯删除，禁止顺手"优化"任何在岗代码逻辑
- 删除后必须通过：后端 `cargo clippy --all-targets -- -D warnings` + `cargo test`；前端 `npx tsc --noEmit` + `npm run build`
- 删除 feishu/sdk 方法时不得影响 sdk 其余在岗代码的编译
- 遵循分支开发：分支 `chore/remove-dead-code`，通过 PR 合入

# 7. 可修改 / 不可修改项

- ❌ 不可修改：在岗代码的任何行为、数据库迁移文件、API 路由表（v1 路由保持不变）
- ✅ 可调整：死代码的删除顺序、因删除产生的 import 清理、注释中失效引用的修正

# 8. 接口与数据约定（如适用）

删除的 `blackboard_routes`、`get_running_board`、`smart_create_handler` 均为**未挂载**的旧版路由，线上无任何流量（v1 路由在岗，路径不同），无接口兼容性影响。

# 9. 验收标准（Acceptance Criteria）

- 如果对仓库重新执行本次扫描脚本，则前端 37 项、后端 60 项、3 个依赖全部不再出现
- 如果执行 `cargo clippy --all-targets -- -D warnings`，则零告警零错误
- 如果执行 `cargo test`，则全部测试通过
- 如果执行 `npx tsc --noEmit` 与 `npm run build`，则零错误
- 如果 grep 被删项名称，则全仓库（含注释）无残留引用

# 10. 风险与已知不确定点

- 删除可能引发级联死代码（某函数的唯一调用方被删后自身变死）：处理方式是删除后重跑扫描脚本，发现的级联项一并删除
- 被删代码如需恢复：全部可从 git 历史恢复，删除按"前端/后端/依赖"分 commit 以便精确 revert
- 遇到"看似零引用但可能是预留给外部集成"的项时，AI 必须停下来请求确认，不得自行假设

# 11. 非目标

同第 3 节。本需求不包含任何新功能开发。
