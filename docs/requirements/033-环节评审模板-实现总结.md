## 1. 实现了什么

为工艺的每个环节（link）新增**环节级评审模板** `review_prompt`：在工艺 YAML 中可写一段完整的评审模板正文（含占位符），安装时写入 `loop_steps.review_prompt`，环路执行评审时按 **环节内联 → 环路级 `review_template_id` → 全局默认** 三级回退选取模板正文。评审触发条件从「有验收标准」扩展为「有验收标准 或 有 review_prompt」。

基于分支：`feat/recipe-editor` @ a8a5537b（已同步 main）。

## 3. 关键实现点

1. **存储与写入解耦**：`review_prompt` 内联存 `loop_steps`（不落入 `review_templates` 表，不污染全局模板）。`acceptance_criteria` 仍走 `todos`（原路径不变），两者各司其职。
2. **install + upgrade 共用写入点**：`upgrade_process_template_loop` 是「删除旧 steps/phases → 重建」模式，复用 `create_phases_and_steps`→`create_loop_step_for_link`，故升级时新模板的 `review_prompt` 自动同步，无需单独处理。
3. **三级回退抽成 `resolve_review_template`**：返回 `(模板正文, 归属 template_id, 归属 name, workspace_id)`。内联分支用哨兵 `template_id=0` 归属评审实例 todo（不与真实模板冲突，复用机制不变）。
4. **触发条件扩展**：`apply_rating_gate` 原仅 `acceptance_criteria` 非空才评审；现扩展为「验收标准 或 review_prompt」非空即评审。`min_rating` 仍为评分闸门阈值的外层前置（未改）。
5. **完整替代语义**：`review_prompt` 非空时整体替代默认模板正文；占位符替换照常，若用户未在 `review_prompt` 写 `{acceptance_criteria}` 则验收标准不注入（UI placeholder 已提示）。

## 5. 已知限制 / 待改进

- **Playwright 编辑持久化**：系统工艺（4p12s-delivery）只读，无法在 UI 验证「编辑→保存→重开保留」；该底层链路（`updateLinkField`→`yamlDump`）由 vitest `processDefinitionUpdater.test.ts`（19 用例）覆盖，手动验证需用户工艺。
- **pre-existing flaky**：`services::process::repair_log::tests::test_append_repair_entry_creates_file` 在多线程下偶发失败（单线程通过），与 033 无关，未在本次修复。
- **哨兵 id=0**：inline review_prompt 用 `review_template_id=0` 归属评审实例 todo；当前所有 inline 评审共享一条 todo（串行 reset prompt，与 loop 级共享机制一致）。
- **migration 编号**：本分支 v75 紧随 v74；若后续 main 新增 v75+ 再合并需重编号。
