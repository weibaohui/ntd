## 1. 背景（Why）

033「环节评审模板」在工艺 YAML 的每个环节（`LinkDefinition`）新增了 `review_prompt` 字段，安装时写入 `loop_steps.review_prompt`，设计上期望执行评审时按「环节内联 → 环路模板 → 默认」三级回退选取模板正文。

经代码审查发现，033 实现的**写入端正确、读取端断裂**：

- `installer.rs` 确认将 `link.review_prompt` 写入 `loop_steps.review_prompt`（L296-300）
- 但唯一读取 `step.review_prompt` 的代码路径是 `loop_runner.rs::apply_rating_gate`（L810/L944）
- `apply_rating_gate` 的触发条件是 `step.min_rating.is_some()`（L800/L908）
- `installer.rs` 将工艺步骤的 `min_rating` 硬编码为 `None`（L280）——因为工艺步骤使用 `gate_config` 体系，`min_rating` 列无意义
- 因此 `apply_rating_gate` **对工艺步骤永远不会触发**，`review_prompt` 形同虚设
- 工艺步骤的评审实际走 `completion.rs::maybe_run_auto_review` → `executor_service/auto_review.rs::run_auto_review_inner`，这一路径始终使用 `review_templates` 表的默认模板，**完全不知道** `review_prompt` 的存在

### 更深层的问题

自动评审存在**两条并行路径**：

| 路径 | 位置 | 触发条件 | 特点 |
|------|------|---------|------|
| **Todo 级** | `completion.rs:maybe_run_auto_review` → `auto_review.rs:run_auto_review_inner` | `todo.auto_review_enabled=true` | 用默认模板；为 `min_rating.is_some()` 的步骤提早返回 |
| **Step 级** | `loop_runner.rs:apply_rating_gate` | `step.min_rating.is_some()` | 支持三级回退（含 review_prompt）；工艺步骤永远不触发 |

两条路径共享相似的执行逻辑（创建评审实例 → 执行 → 轮询 → 写分），但 prompt 解析策略不同、触发条件不同，而且通过 `min_rating.is_some()` 相互耦合——todo 级路径为 `min_rating.is_some()` 的步骤返回，期望 `apply_rating_gate` 接手，但工艺步骤同时满足 `min_rating=None`（不进 step 级）和 `auto_review_enabled=true`（进 todo 级，但 prompt 不对）。

此外还有死代码：`ai_criteria_review.rs::build_review_prompt` 定义了但全仓库零调用；gate evaluate 返回 `needs_review` 标记但无人消费。

## 3. 非目标（Explicitly Out of Scope）

- ❌ 不改 `apply_rating_gate` 的评分闸门逻辑——它仍作为旧风格 `min_rating.is_some()` 步骤的门禁判断函数（但评审已在统一路径完成）
- ❌ 不改人工审批（`review_type == "human"`）路径——其 `auto_review_enabled=false`，不受影响
- ❌ 不改 `gate_evaluator`、`PhaseDriver` 的门禁评价逻辑
- ❌ 不改默认模板 `DEFAULT_REVIEWER_PROMPT` 的**实质内容**（评审人设/输出格式不变）；仅将其占位符由 `{单括号}` 统一为 `{{双括号}}`，与 `compose_review_prompt` / `apply_rating_gate` 的替换约定对齐——修复「默认模板占位符原样发给 AI」的回归（详见 033 实现总结）。
- ❌ 不改前端（`LinkPropertyForm`、`process.ts` 类型等）——033 已完成
- ❌ 不改 `installer.rs` 的写入逻辑——033 已正确实现

## 4. 使用场景

### 场景 A：环节有 `review_prompt` 的工艺步骤

1. 工艺 YAML 中某环节填写了 `review_prompt`（含 `{{original_prompt}}` 等占位符）
2. 安装到环路
3. 环路执行该环节 → todo 完成
4. 自动评审触发，使用该环节的 `review_prompt`（占位符替换后）作为评审 prompt
5. 评审结果写回，PhaseDriver 正常执行门禁判定

### 场景 B：环节无 `review_prompt`、环路设了 `review_template_id`

1. 环节 `review_prompt` 为空
2. 环路设了 `review_template_id`
3. 自动评审触发，使用环路级模板
4. 行为与现状完全一致

### 场景 C：普通 todo（非环路步骤）

1. 用户手动创建一个 todo，`auto_review_enabled=true`
2. todo 执行完成
3. 自动评审触发，使用默认模板
4. 行为与现状完全一致

### 场景 D：旧风格 loop 步骤（`min_rating.is_some()`）

1. 旧环路步骤（非工艺，`min_rating=60`）
2. 环路执行该步骤 → todo 完成
3. 统一路径触发评审（不再提早返回），评分写入 DB
4. `apply_rating_gate` 在门禁判断时发现评分已存在 → 短路为纯阈值检查
5. 行为与现状完全一致（无重复评审，评分/门禁结果正确）

## 6. 约束条件

- **无重复评审**：旧风格 `min_rating.is_some()` 步骤经统一路径评审后，`apply_rating_gate` 读到已有评分立即短路返回，不二次执行评审实例。
- **`auto_review_enabled` 语义不变**：`todo.auto_review_enabled=false` 的 todo 不触发评审（人工审批步骤和评审实例自身不受影响）。
- **向后兼容（旧风格 loop）**：旧风格 `min_rating.is_some()` 步骤从「跳过 todo 级、由 apply_rating_gate 评审」改为「todo 级统一评审、apply_rating_gate 仅门禁检查」，结果不变。
- **向后兼容（普通 todo）**：非环路 todo 行为与现状完全一致。
- **时序不变**：统一评审在 `run_todo_execution` 返回前完成（`block_on` 语义），评分在 loop runner 继续执行前已在 DB。

## 9. 风险与已知不确定点

- **评审实例复用（dedup）**：当前 `execute_review_instance` 以 `template.id` 为 key 判断是否复用已有评审 todo。环节内联 `review_prompt` 无对应 `review_templates` 行，需要使用哨兵 ID。设计文档需确认复用策略。
- **`resolve_review_template` 函数归属**：该函数当前在 `LoopRunner` impl 上，统一后需抽离为独立函数或迁至 `auto_review.rs`。
- **评审实例 todo 归属字段**：当前 `reuse_or_create_review_instance` 需要 `owning_template_id` 和 `owning_name`，内联 prompt 需提供合适的替代值。
