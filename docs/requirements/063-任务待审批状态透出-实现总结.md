对应需求：`docs/requirements/063-任务待审批状态透出-需求.md`；设计：`docs/design/063-任务待审批状态透出-设计.md`。

## 1. 实现了什么

任务页（TasksPage）列表 / 看板 / 卡片三态视图现在能直接看到「该任务有 N 条环节等待人工审批」，点击标记一步直达审批操作区，不再需要点进详情逐层翻找。

## 2. 与需求的对应关系

| 需求目标 | 实现 | 验证 |
|---------|------|------|
| 列表接口返回 `pending_approval_count` | `db.count_pending_approvals_by_task_ids`（新）+ `list_tasks` 注入 | 后端单测 3 条 + Playwright 063-1 |
| 看板「待审批」泳道 | `TASK_LANES` 首列 + `laneOfTask` 待审批优先分组 | Playwright 063-3 + vitest 4 条 |
| 列表「待审批」列 | 独立列（可排序）+ 状态筛选加「待审批」 | Playwright 063-2 |
| 卡片待审批标记 | 卡片头部红色「N 待审批」Tag + 筛选 | Playwright 063-4 |
| 点击直达审批 | `?tab=exec` + `LoopExecutionsPanel.autoExpandFirstPending` 自动展开首条待审批执行 | Playwright 063-5 |

## 3. 关键实现点

- **派生不落库**：统计口径复用 NTD-004（`approval_status='pending' OR status='pending_approval'`），无表结构变更、无状态机改动。
- **计数口径**：按任务**所有执行**累加（与 Loop 列表一致），避免旧执行滞留审批被新执行掩盖。
- **零 N+1**：列表接口在既有批量查询外仅新增 1 条 GROUP BY SQL。
- **回归防护**：自动展开用 `autoExpandedRef` 守卫只触发一次；`loadPage` 刻意不依赖 `handleExpand`，避免展开行把列表重置回第 1 页。
- **看板口径**：待审批任务只进「待审批」泳道，不重复出现在真实状态泳道，各列计数之和 = 任务总数。

- 前端：`npx tsc --noEmit` 零错误；vitest `src/components/tasks/` 43/43 通过（新增 4 条泳道/分组用例）。
- Playwright：`tests/063-task-pending-approval.spec.ts` 5/5 通过；回归 `044`（门禁审批全流程）/ `031` / `054` 共 18/18 通过。
- 排障记录：初版用例 5 断言 `/^通过$/` 失败——antd 对两汉字按钮自动插入空格（「通 过」），改宽松正则 `/通\s*过/` 后通过。

## 5. 安全反思

- SQL 拼接的 task_ids 来自后端内存中的数据库 id（i64），非用户输入，与既有兄弟方法同模式，无注入面。
- `list_tasks` 先按 workspace 过滤再统计，无跨工作空间数据泄漏。
- 前端仅渲染计数数字与固定文案，无 XSS 面；审批操作本身未改动，仍走既有鉴权接口。

## 6. 已知限制

- 执行历史分页大小为 5：若待审批执行不在第一页，自动展开不触发（行内红色标记仍可手动展开）。需求 §10 已声明，属预期取舍。
