## 1. 背景（Why）

任务页看板（URL `/#/tasks?view=kanban`）顶栏已提供「全部 / 6h / 12h / 24h / 3d / 7d」时间过滤分段
（公共组件 `TimeRangeSegmented`，按任务 `created_at` 过滤，默认「全部」）。
但**事项页**（`/#/todos`，卡片/列表形态）与**环路页**（`/#/loops`，看板/列表形态）没有同款时间过滤：

- 事项页列表/卡片是服务端分页数据，用户无法快速圈定「最近创建的事项」；
- 环路页列表是全量环路定义，找不到「最近新建的环路」；
- 环路页看板只有 6h~7d 五档、没有「全部」，想看全量执行历史必须先切回列表。

三个列表/看板形态共用同一套时间档位，用户心智模型不统一。

## 2. 目标（What，必须可验证）

- [ ] 事项页「卡片」「列表」两种形态的顶栏增加与任务页看板一致的时间过滤分段（全部/6h/12h/24h/3d/7d），按事项 `created_at` 过滤，默认「全部」。
- [ ] 环路页「列表」形态顶栏增加同款时间过滤分段，按环路 `created_at` 过滤，默认「全部」。
- [ ] 环路页「看板」形态现有时间分段增加「全部」选项，默认仍为 24h（执行历史维度不变）。
- [ ] 事项页两种形态共用一个时间过滤状态，切换形态不丢失；时间选择不持久化（与任务页一致）。
- [ ] 事项页的服务端分页在时间过滤下总数与页数口径正确（过滤下推 SQL，而非前端过滤当前页）。

## 3. 非目标（Explicitly Out of Scope）

- 事项页「执行监控」（running）形态：RunningBoard 自带统计栏与时间窗，不接入本过滤。
- 移动端 header：保持精简（搜索/过滤不展示），本需求不改变移动端布局。
- 环路看板执行历史的时间字段保持 `started_at`（现状），不改为 `created_at`。
- 时间选择持久化到 localStorage：不做（任务页现状即不持久化）。
- 修改「全部/6h/12h/24h/3d/7d」档位本身：不做，公共组件 `TimeRangeSegmented` 已是唯一事实源。

## 4. 使用场景 / 用户路径

1. 用户进入事项页列表形态，点击顶栏「24h」→ 列表只显示最近 24 小时创建的事项，分页总数同步收窄。
2. 用户切到卡片形态 → 时间过滤保持（同一页级状态），五个分类 Tab 的卡片与 Tab 角标均按时间窗收窄。
3. 用户点回「全部」→ 恢复全量数据。
4. 用户进入环路页列表形态，点击「7d」→ 只看最近 7 天创建的环路。
5. 用户切到环路看板形态，点击「全部」→ 执行历史不再按时间收窄，全部展示。

## 5. 功能需求清单（Checklist）

- [ ] 事项页顶栏（桌面端，card/list 两形态）渲染 `TimeRangeSegmented showAll`，置于搜索框与刷新按钮之间（与任务页顺序一致）。
- [ ] 事项页时间窗 state 提升到 `TodoListPage`，card 与 list 共用；running 形态不渲染该分段。
- [ ] `getTodoCenter` 前端 API 增加 `hours` 可选参数；`TodoCenterCardView` 增加 `hours` prop 并随其他筛选条件一起下推请求。
- [ ] 环路页列表形态渲染 `TimeRangeSegmented showAll`，按 `LoopListItem.created_at` 前端过滤（数据全量在前端）。
- [ ] 环路页看板形态时间分段升级为 showAll 形态；`hours=null` 时 `LoopKanban`/`useLoopExecutions` 不过滤（请求不带 hours 参数）。
- [ ] 环路页 list/kanban 各自独立的时间窗 state（数据维度不同：环路定义 vs 执行历史），默认值分别为 null（全部）与 24。
- [ ] 后端 `GET /api/v1/workspaces/{ws_id}/todos/center` 增加 `hours` 查询参数，SQL 层 `created_at >= cutoff` 过滤，分页 total、bucket_counts 同口径。
- [ ] 后端新增 hours 过滤单元测试（窗口内命中 / 窗口外排除 / hours=0 不过滤）。
- [ ] 前端更新既有组件测试（TodoListPage / TodoListPageParts / LoopListPageParts / TodoCenterCardView 相关）并通过。

## 6. 约束条件（非常关键）

- **技术约束**：后端时间比较用 `utc_timestamp_minus_hours(h)` 生成与写入格式一致的 T/Z ISO cutoff，
  参数绑定裸列比较（`created_at >= ?`），复用 093 既有模式，禁止列上套 REPLACE/datetime 函数（索引恒失效）。
- **架构约束**：时间档位选项不新增第二份常量，一律复用 `TIME_RANGE_OPTIONS`（`frontend/src/components/common/TimeRangeSegmented.tsx`）。
- **安全约束**：hours 仅接受非负整数，0/缺省视为不过滤；过滤只读不改变任何写入语义。
- **性能约束**：事项中心 hours 过滤必须在 SQL 层完成（分页场景前端过滤会漏数据）；环路列表前端过滤（数据量小、全量已在前端）。

## 7. 可修改 / 不可修改项

- ❌ 不可修改：任务页看板既有时间过滤行为（默认「全部」、created_at 口径、不持久化）。
- ❌ 不可修改：环路看板默认 24h 的历史行为（本次仅新增「全部」选项，不改变默认值）。
- ✅ 可调整：时间分段在 header 中的摆放位置（保持搜索→时间→刷新的大顺序）。
- ✅ 可调整：单测断言方式与用例组织（不影响对外行为即可）。

## 8. 接口与数据约定（如适用）

### 8.1 后端 `GET /api/v1/workspaces/{ws_id}/todos/center`（V1，修改）

新增查询参数：

| 参数 | 类型 | 缺省 | 语义 |
|------|------|------|------|
| `hours` | 非负整数（u32） | 缺省/0 = 不过滤 | 只返回 `created_at >= now - hours 小时` 的事项；作用于所有 bucket/status/action_type/search 组合之上 |

- 响应结构不变（`items/total/page/page_size/bucket_counts/action_types`）。
- `total` 与 `bucket_counts` 必须与 items 同口径（含 hours 条件）。

### 8.2 前端字段口径

- 事项页/环路列表：`created_at`（ISO 8601 UTC 字符串）。
- 环路看板：执行记录 `started_at`（现状不变）。

## 9. 验收标准（Acceptance Criteria）

- 如果用户在事项页列表形态选择「6h」，则表格只包含 `created_at` 距今 6 小时内的记录，且分页总数等于过滤后的总数。
- 如果用户在事项页卡片形态切换时间窗，则五个分类 Tab 的卡片与角标数量全部按同一时间窗收窄；切回「全部」恢复。
- 如果在事项页选择时间窗后切换到环路页再切回，则事项页时间窗回到默认「全部」（不持久化）。
- 如果用户在环路列表形态选择「7d」，则只显示最近 7 天创建的环路；「全部」恢复全量。
- 如果用户在环路看板形态选择「全部」，则展示全部执行历史；默认进入看板时仍为 24h。
- 如果后端收到 `hours=0` 或未传 `hours`，则返回结果与未过滤时完全一致。
- 如果 `cargo test`、`cargo clippy --all-targets -- -D warnings`、`npx tsc --noEmit` 全部通过，则质量门槛达标。

## 10. 风险与已知不确定点

- **时间格式混合**：存量数据可能同时存在毫秒级（应用层写入）与秒级（触发器兜底）T/Z ISO 字符串；
  与 cutoff 做字符串比较在秒级等价于时间比较（093 已论证），毫秒边界误差 <1s，对小时级过滤可忽略。
- **环路看板「全部」性能**：看板拉全量执行历史（每环路 limit=20 不受 hours 影响），
  取消 hours 过滤不会增加请求数量（每环路仍 20 条），风险低。
- **归档事项**：事项中心「已归档」Tab 同样受 created_at 时间窗过滤（统一口径），如需排除归档另行提需求。
