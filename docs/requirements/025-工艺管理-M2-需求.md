---

## 1. 背景

M1 已完成工艺模板市场、模板安装为 Loop、阶段建模、产物与门禁配置落库、前端工艺库页面与 Loop Studio 阶段色带。

M2 聚焦**运行时能力**：让 M1 落库的 `expected_artifacts`、`gate_config`、`max_rework`、`rework_count`、`loop_step_artifacts`、`loop_step_execution_gates`、`loop_phase_executions` 在 LoopRunner 执行时真正生效。

---

## 2. M2 目标（必须可验证）

M2 采用 **skill-centric 工艺模型**：结构化管控「环节 → skill → 产物 → 门禁」四元组，具体内容模板由 skill 文件承载。

- **G0** 每个环节绑定的 skill、产物位置、门禁规则必须在前端界面显性化展示；工艺模板安装时必须校验 skill 依赖存在。
- **G1** 环节执行完成后，系统按 `expected_artifacts` 自动捕获产物并写入 `loop_step_artifacts`；捕获时结合 skill 输出格式做内容提取。
- **G2** 门禁引擎按 `gate_config` 评价产物/输出：产物存在性、AI 评审（注入 skill 自检清单）、人工审批、脚本校验。
- **G3** 门禁结果决定环节流转：通过走 `on_success`，失败走 `on_gate_fail`（fallback `on_rating_fail`）。
- **G4** 失败回退到上游环节时视为返工，`rework_count` 递增；超过 `max_rework` 强制失败。
- **G5** 阶段生命周期 `loop_phase_executions` 自动维护。
- **G6** 标准产物 `delivery-state.md` / `repair-log.md` 自动维护。
- **G7** 提供工艺实例审计 API 与 CLI。
- **G8** 提供前端工艺执行看板，展示阶段进度、产物、门禁、返工、skill 列表。

**M2 不做**：工艺路由/推荐、模板版本 diff、指标度量、可视化编排器、并行网关等复杂控制流。

## 3. 功能需求清单

### 3.0 Skill-centric 工艺模型（新增）

- [ ] **F0.1** 工艺模板 YAML 中每个 `link` 必须能配置 `skills: [...]`，安装时校验这些 skill 是否已存在于 bundled 仓库并同步到本地；缺失时安装失败并提示。
- [ ] **F0.2** 工艺配套 skill 文件建议（不强求但默认遵守）包含以下章节：
  - 目标
  - 必须包含
  - 禁止
  - 输出产物
  - 自检清单
- [ ] **F0.3** 阶段级规范 `phase.spec` / `phase.acceptance_criteria` 支持 inline 文本或引用外部 markdown 文件（`spec_ref` / `acceptance_criteria_ref`）。
- [ ] **F0.4** 前端工艺库详情页、Loop Studio 详情页、工艺执行看板必须展示「环节 → skill → 产物 → 门禁」四元组。

### 3.1 产物捕获（F3）

- [ ] **F3.1** 新增 `loop_step_artifacts` 写入路径：环节执行完成后，根据 `loop_steps.expected_artifacts` 自动捕获。
- [ ] **F3.2** 支持类型：
  - `file`：检查相对工作目录的文件是否存在；
  - `text`：从 `execution_record.result` 中按标记提取；
  - `url`：用正则从结果中提取第一个 URL；
  - `json`：从结果中提取 JSON 块。
- [ ] **F3.3** 产物捕获结合 skill「输出产物」章节：skill 中规定的 marker、frontmatter、文件路径优先用于内容提取。
- [ ] **F3.4** 支持用户在前端手动补充产物（POST artifact API）。
- [ ] **F3.5** 产物路径必须做路径安全校验，禁止 `..` 与绝对路径逃逸。
- [ ] **F3.6** `delivery-state` / `repair-log` 作为系统维护的标准产物，不直接捕获，而由专用模块写入。
- [ ] **F3.7** 记录本次 step 使用的 skill 名称，便于审计链路追溯。

### 3.2 门禁引擎（F4）

- [ ] **F4.1** 新增 `loop_step_execution_gates` 写入路径：每项门禁执行后记录类型、配置、状态、结果、评价时间、评价来源。
- [ ] **F4.2** 支持四种门禁类型：
  - `artifact_present`：产物存在；
  - `ai_criteria_review`：AI 按产物 + 验收标准 + skill 自检清单给出 pass/fail/score/issues；
  - `human_approval`：人工审批，暂停 Loop；
  - `script_check`：运行指定脚本/命令校验产物。
- [ ] **F4.3** `ai_criteria_review` 的评审 prompt 自动注入当前环节绑定的 skill 文件中的「自检清单」。
- [ ] **F4.4** 门禁按顺序执行，全部通过则环节通过；任一必需门禁失败则环节失败。
- [ ] **F4.5** 兼容现有 `min_rating`：若 `gate_config` 为空但 `min_rating` 有值，隐式生成一条 `ai_criteria_review`。
- [ ] **F4.6** 兼容现有 `review_type=human`：若 `review_type=human` 且未显式配置 `human_approval`，隐式生成一条。
- [ ] **F4.7** 门禁失败时按 `on_gate_fail` 策略流转；未配置 `on_gate_fail` 时 fallback 到 `on_rating_fail`。

### 3.3 返工与流转（F5）

- [ ] **F5.1** `loop_step_executions.rework_count` 在返工时递增。
- [ ] **F5.2** 返工判定：门禁失败且策略为 `goto:<step_id>`，且目标环节索引 ≤ 当前索引。
- [ ] **F5.3** `rework_count >= max_rework` 时强制结束工艺实例，状态为 `failed`。
- [ ] **F5.4** 返工记录写入 `repair-log.md` 与 `loop_step_execution_gates`，供审计。

### 3.4 阶段执行记录（F6 部分）

- [ ] **F6.1** `loop_phase_executions` 在阶段开始、完成、失败、跳过时自动维护。
- [ ] **F6.2** 新增审计 API：`GET /api/v1/workspaces/{ws}/loops/{id}/executions/{eid}/audit`，返回阶段 → 环节 → 产物 → 门禁 → 返工的完整链。
- [ ] **F6.3** 新增 CLI：`ntd process execution status <id>` 以树形/表格展示审计信息。

### 3.5 标准产物维护

- [ ] **F6.4** `delivery-state.md` 在实例启动、进入新 phase、环节完成时自动重写，包含当前阶段、产物清单、门禁结果。
- [ ] **F6.5** `repair-log.md` 在门禁失败、返工、人工审批拒绝时追加条目。

### 3.6 前端与 CLI（F7 部分）

- [ ] **F7.1** 新增「工艺执行看板」：按阶段分组展示环节状态、skill 列表、产物列表、门禁结果、返工次数。
- [ ] **F7.2** 工艺库详情页展示每个环节的四元组（环节名、skill、产物、门禁）。
- [ ] **F7.3** Loop Studio 详情页在节点上增加 skill/产物/门禁/返工徽章。
- [ ] **F7.4** CLI 命令：`ntd process run <name> --workspace /path/to/project`（安装并触发执行）。
- [ ] **F7.5** CLI 命令：`ntd process execution status <id>`。

## 5. 验收标准

| 编号 | 验收标准 | 验证方式 |
|------|---------|---------|
| AC1 | 配置 `expected_artifacts` 的环节执行后，`loop_step_artifacts` 中至少出现对应记录；缺失时对应 `artifact_present` 门禁失败 | 集成测试 |
| AC2 | 配置 `ai_criteria_review` 门禁的环节，AI 评审结果包含 `pass`（bool）、`score`（0-100）、`issues`（数组），并写入 `loop_step_execution_gates` | 集成测试 |
| AC3 | `min_rating` 有值但 `gate_config` 为空时，自动触发 AI 评审并兼容旧 Loop | 单元测试 + 集成测试 |
| AC4 | 门禁失败且 `on_gate_fail: goto:<step_id>` 时，LoopRunner 跳转到指定环节并递增 `rework_count` | 集成测试 |
| AC5 | `rework_count` 达到 `max_rework` 时工艺实例状态变为 `failed` | 集成测试 |
| AC6 | `human_approval` 门禁暂停 Loop，审批 API 更新 gate 状态后 Loop 继续 | Playwright + 集成测试 |
| AC7 | 工艺实例审计 API 返回阶段、环节、产物、门禁、返工的完整数据 | 单元测试 + API 测试 |
| AC8 | 前端工艺执行看板正确展示阶段进度、skill 列表、产物清单、门禁结果、返工次数 | Playwright |
| AC9 | 工艺库详情页能清晰展示每个环节的四元组（环节 → skill → 产物 → 门禁） | Playwright |
| AC10 | 安装工艺模板时若引用的 skill 不存在，安装失败并给出明确错误 | 单元测试 |
| AC11 | `ntd process run` 能安装并触发执行；`ntd process execution status` 能展示审计 | CLI 手动验证 |
| AC12 | 所有新增公开函数有单元测试；`cargo clippy --all-targets -- -D warnings` 与 `npx tsc --noEmit` 零告警 | CI |

## 7. 接口约定

### 7.1 新增 API

```text
GET    /api/v1/workspaces/{ws}/loops/{id}/phases
GET    /api/v1/workspaces/{ws}/loops/{id}/executions/{eid}/audit
POST   /api/v1/workspaces/{ws}/loops/{id}/executions/{eid}/steps/{seid}/artifacts
       body: {name, artifact_type, locator, content_text}
POST   /api/v1/workspaces/{ws}/loops/{id}/executions/{eid}/steps/{seid}/gates/{gid}/approve
       body: {approved: bool, comment: String}
```

### 7.2 新增 CLI

```bash
ntd process run <name> --workspace /path/to/project
ntd process execution status <loop_execution_id>
```

## 8. 风险与处理

| 风险 | 影响 | 处理 |
|------|------|------|
| 改造 LoopRunner 影响旧 Loop | 回归 | 旧 Loop（无 phase/artifact/gate）走兼容路径 |
| AI 门禁结果不稳定 | 反复返工 | 可配置 min_score，人工审批兜底 |
| script_check 安全风险 | 任意命令执行 | 白名单 + 路径校验，首期只支持项目内已存在脚本 |
| 产物捕获依赖 AI 输出格式 | 提取失败 | 多策略提取 + 允许手动补充 |
