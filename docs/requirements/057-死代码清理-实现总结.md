## 关键发现

- **`#[allow(dead_code)]` 是死代码的强信号**：旧版 handler（`get_running_board`/`smart_create_handler`）带此标记，说明前人已知其死亡但保留。本次按 YAGNI 删除，需要时可从 git 恢复。
- **loop 导入导出是整套废弃功能**：前后端共 19 项相互引用的死代码（DTO、预览函数、建库函数），疑似功能下线时只拆了调用方。
- **级联死代码占总量的 22%**（前端 12/53，后端 13/73）：第一轮删除后重跑扫描脚本才发现，印证了"删除→重扫→收敛"流程的必要性。
- **测试失败 1 例为存量环境问题**：`git_sync::tests::test_sync_repo_restores_deleted_file` 依赖 `git init -b`（git ≥ 2.28），本机 git 2.20.1 不支持，与本次删除无关（main 上同样失败）。

# 4. 安全反思

- 删除的 3 个路由 handler **从未挂载**，线上无流量，删除无接口兼容性影响（v1 路由在岗且路径不同）。
- 未触碰任何鉴权、白名单、输入校验逻辑；飞书群白名单 `is_sender_in_whitelist`（fail-closed 语义）经核实为在岗代码，未受影响。
- 未删除任何数据库迁移 SQL，旧库升级路径不受影响。
- 依赖移除（yaml-rust2/rusqlite/http-body-util）缩小了供应链攻击面，属于正向收益。

# 5. 已知限制

- 自研扫描脚本对"字符串拼接调用""反射式引用"无法覆盖，但本项目无此类模式（Rust 宏是 hygienic 的，名字必在源码中出现；前端已额外检查动态 import/lazy）。
- 前端 18 个保留项如未来其宿主代码下线，可能变为真正的死代码，建议下次扫描时复核。

# 6. 评审复盘（PR #979 自评审，2026-08-03）

按 pr-review 方法论自评审，发现 **2 条 Critical 误删**并修复（commit 见 PR）：

1. **扫描盲区**：初版扫描仅覆盖 `frontend/src`，遗漏 `frontend/tests/`（Playwright 测试）。导致误删：
   - `commandExtractor.ts` 的 `__test__` 测试钩子 — 被 `tests/issue-648-command-extractor.spec.ts` 使用（10+ 处）
   - `settings/assistant/PushStatusCard.tsx` — 被 `tests/push-target-mount.ts` mount harness 使用
   - 两项均已从 main 恢复（字节一致），恢复后 issue-648 spec 13/13 通过
2. **帮助系统脱节**：`help/index.ts` 注册表与 `help/pages/onboarding*.md` 仍描述已下线的「快速开始」功能（QuickStartFlow）。已移除注册项、删除过时帮助页、修正 onboarding.md 的 mermaid 图与索引
3. **存量失败（非本 PR 引入）**：`check_push_target_card.spec.ts` 在 main 上同样失败（断言与 #891 后的 PushStatusCard 实现漂移）；`git_sync` 还原测试依赖 git ≥ 2.28

**流程教训**：后续死代码扫描必须覆盖 `frontend/tests/` 与 `backend/tests/` 双测试目录；级联删除整棵子树（如 settings/assistant）前需对每棵子树单独跑测试引用检查。
