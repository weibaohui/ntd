## 1. 实现了什么

| 变化 | 位置 |
|------|------|
| `ExecutionEvent::should_broadcast()`（WS 广播过滤唯一事实源） | `execution_events/event.rs` |
| `ExecutionEvent::is_direct_stream_worthy()`（飞书私聊收集过滤唯一事实源） | `execution_events/event.rs` |
| `EventPipeline::feed_stdout_new()`（feed 骨架：空行守卫+簿记收口） | `execution_events/pipeline.rs` |
| `parse_and_broadcast` 瘦身为「回授 + should_broadcast」薄循环（~90→~25 行） | `log_capture.rs` |
| `parse_for_direct_stream` 瘦身为 is_direct_stream_worthy 薄循环（~55→~15 行） | `message_debounce.rs` |

顺带更正扫描报告的一处误差：`parse_for_direct_stream` 实为 ~55 行（扫描脚本受原始字符串括号干扰误测 708 行）；本批次的真实问题是规则三处重复而非函数超长。

## 2. 与设计/旧实现的语义对齐

- 全 18 个事件变体 × 2 维判定写成枚举断言表（`test_broadcast_and_direct_stream_matrix`）——即原两处 match 的逐分支对照，防未来新增变体语义漂移；
- Info 内容规则（纯 JSON 行/空串不转发）封装在两个判定方法内部；
- SessionEnd 维持「逐行路径不转发、finalize 统一产出」的既有语义；
- NTD-012 回授保持「全部新事件先回授再过滤」的顺序（StepStart 重置依赖）。
- `emit_direct_stream` 的 log_type 二级过滤与 stderr 的 atomcode 特判路径按计划未动。

## 4. 已知限制

- `finalize_pipeline_by_path` 内的 direct 分支过滤（Thinking/ToolCall/... 直推）与
  `is_direct_stream_worthy` 语义重叠但未复用（该分支是 finalize 收尾特判，留待 B4 体系合并时一并处理）；
- 双解析体系合并（B4）与 emit_direct_stream 的 log_type 层过滤保持现状。

## 5. 安全反思

纯过滤规则搬移，无增删；无事件 schema/接口/权限变化；判定矩阵单测防止静默语义漂移。
