## 1. 背景（Why）

任务（`tasks`）目前是单向链路：一段需求文本 + 关联工艺环路（Loop）+ 执行历史。用户只能「发起 → 跑全流程 → 看结果」，**缺少围绕一个任务的多轮协作讨论**。

用户希望像论坛一样在任务下**跟帖讨论**，并能在帖子里 **@专家 / @执行器**，让 AI 直接出来「干一段活」，干活的**结论以跟帖形式自动回复**到讨论流，形成「人 + AI」混合的协作论坛。

现有 `todo-post/` 论坛 UI 是「执行记录对话流」，其「回复」= 与 AI 续聊（resume），语义是 AI 对话流，不是「人对任务的人工讨论 + 按需调用 AI」，无法满足本需求。

**范围界定**：本需求只落在**任务（tasks）**上，不在事项（todos）上做。

**关键事实**（影响整个设计）：
- 执行系统是 **Todo 中心**的，所有「让执行器干活」都走同一条管线 `run_todo_execution`，**必须有一个 Todo 作为载体**（Todo 提供 `executor`/`prompt`/`expert_name`）。Task 本身没有执行器概念。
- **专家（Expert）与执行器（Executor）正交**：专家是人设/角色包（`expert/`，plugin.json + agent.md + 技能），**自己不会执行**，靠 `inject_expert_context` 把人设拼到 message 前面、再交给某个执行器跑。

## 2. 目标（What，可验证）

- [ ] **T1** 任务详情页新增「讨论」Tab，展示该任务的跟帖流（人帖 + 智能体帖混合，按时间排序）。
- [ ] **T2** 用户可在讨论区发 Markdown 人帖；支持对某楼层回复（扁平主楼层 + 一层楼中楼）。
- [ ] **T3** 人帖中可 `@专家` 和/或 `@执行器`；发帖即触发对应执行器跑一段活；若 @ 了专家，则套用该专家人设执行。
- [ ] **T4** 触发后**立刻生成一条「正在干活…」智能体占位帖**；执行完成后，结论自动回写为该帖正文，状态变为成功/失败。
- [ ] **T5** `@专家` 时，用系统默认执行器（可配置，默认 Claude Code）承载该专家人设执行。
- [ ] **T6** 讨论触发的执行**不污染事项中心**：载体 Todo 对用户不可见。
- [ ] **T7** 全流程零编译告警：后端 `cargo clippy --all-targets -- -D warnings`、前端 `npx tsc --noEmit` 通过；后端 `cargo test` 通过。

## 3. 非目标（Explicitly Out of Scope）

- 不在事项（todo）上做讨论（本需求只针对任务）。
- 第一版**不支持 @真人成员**（项目无用户系统，引入成员概念超出范围）。
- 不做任意深度嵌套回复（仅主楼层 + 一层楼中楼）。
- 不引入新的执行引擎；执行仍走现有 `run_todo_execution` 管线，零重写。
- 不改动执行器适配器契约（`CodeExecutor` trait）与专家 plugin.json 格式。
- 不替换现有 `todo-post/` 论坛组件（它服务事项的执行对话流，保持不动）。

## 4. 使用场景 / 用户路径

**场景 A（纯人工讨论）**
打开任务 → 点「讨论」Tab → 在输入器写 Markdown → 发送 → 帖子按楼层出现在流里。

**场景 B（@执行器干活）**
在帖子里写「@codex 帮我分析这段日志的报错根因」→ 发送 → 流里立刻出现「codex 正在干活…」占位帖 → 执行完成后，该帖正文变为 codex 的结论，状态标记成功/失败。

**场景 C（@专家）**
写「@前端架构师 评审一下这个组件拆分方案」→ 用默认执行器套该专家人设执行 → 结论以专家身份回帖。

**场景 D（楼中楼）**
对某楼层点「回复」→ 输入回复 → 该回复挂在目标楼层下方（一层嵌套）。

## 6. 约束条件

- **技术约束**：复用现有执行管线；生产代码禁止 `.unwrap()`/`.expect()`/`panic!`；单函数体 ≤50 行（超需豁免理由）；每个公开函数有单元测试。
- **架构约束**：后端分层 Entity(`db/entity`) → DAO(`db/`) → Handler(`handlers/`)；前端跨目录导入统一用 `@/` 绝对路径。
- **安全约束**：`mentions` 必须服务端校验（防伪造任意 expert/executor 名执行）；执行受既有并发上限与 workspace 隔离约束；删帖暂不鉴权（项目无用户系统，单用户/本地场景；待用户系统引入后再补「仅创建者可删」）。
- **性能约束**：帖子列表分页（不一次性拉全量）；`running` 帖轮询节流（不低于 3s/次），优先复用执行事件管道而非盲轮询。

## 8. 接口与数据约定

### 8.1 `task_posts` 表

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER PK | 主键 |
| `task_id` | INTEGER NOT NULL | FK→`tasks.id`，ON DELETE CASCADE |
| `parent_post_id` | INTEGER | 楼中楼：指向被回复楼层；NULL=主楼层。FK→`task_posts.id`，ON DELETE CASCADE |
| `kind` | TEXT NOT NULL | `'human'`（人帖）/ `'agent'`（智能体帖） |
| `author_name` | TEXT NOT NULL | 显示名（人 / 专家 / 执行器） |
| `executor` | TEXT | 智能体帖：执行器名（逻辑引用 `executors.name`） |
| `expert_name` | TEXT | 智能体帖：被@的专家名 |
| `content` | TEXT NOT NULL DEFAULT '' | Markdown 正文（人帖=用户输入；智能体帖=执行结论） |
| `mentions` | TEXT NOT NULL DEFAULT '[]' | JSON：`[{type:'expert'|'executor', name, display}]`，结构化，触发与徽标渲染均依赖它 |
| `status` | TEXT NOT NULL DEFAULT 'sent' | 人帖恒 `'sent'`；智能体帖 `'running'`/`'success'`/`'failed'` |
| `source_execution_id` | INTEGER | 智能体帖：来源 `execution_records.id` |
| `source_todo_id` | INTEGER | 承载本次执行的隐藏载体 `todos.id` |
| `created_at` / `updated_at` | TEXT | 时间戳（UTC ISO8601，沿用现有约定） |

索引：`idx_task_posts_task_id(task_id)`。

### 8.2 API

挂在任务路由下：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/workspaces/{ws}/tasks/{id}/posts` | 帖子列表（分页，`?page=&limit=&parent_id=`） |
| POST | `/api/v1/workspaces/{ws}/tasks/{id}/posts` | 创建人帖（body: `content`, `parent_post_id?`）；含 mention 时触发执行 |
| GET | `/api/v1/workspaces/{ws}/tasks/{id}/posts/{pid}` | 单帖（轮询占位帖状态用） |
| DELETE | `/api/v1/workspaces/{ws}/tasks/{id}/posts/{pid}` | 删帖（暂不鉴权：无用户系统；running 帖删除同时取消执行） |

`@` 对象数据源**复用现有接口**：`GET /api/v1/experts`（专家）、执行器列表接口（执行器）。

### 8.3 错误码语义

| HTTP | 场景 |
|------|------|
| 404 | task 不存在 |
| 400 | `content` 为空；`mentions` 指向不存在的专家/执行器；`parent_post_id` 不属于本任务 |
| 403 | （暂不启用）删帖鉴权——项目无用户系统，当前任何人可删；待用户系统引入后改为「仅创建者」 |
| 409 | 该任务下已有同执行器·专家组合的 `running` 智能体帖（可选：防重复触发） |

## 9. 验收标准（Acceptance Criteria）

1. **若**打开任意任务的详情页，**则**能看到「讨论」Tab，且初始为空状态引导。
2. **若**用户发送一条不含 `@` 的人帖，**则**它作为主楼层出现在流里，正文按 Markdown 渲染。
3. **若**用户发送一条含 `@codex` 的帖子，**则**流里立刻出现一条 `status=running` 的智能体占位帖（显示「codex 正在干活…」）；执行完成后该帖 `status` 变为 `success`/`failed`、正文变为执行结论。
4. **若**用户发送一条含 `@某专家`（不带执行器）的帖子，**则**用系统默认执行器套该专家人设执行，结论以专家身份回帖。
5. **若**执行失败，**则**占位帖状态为 `failed`，正文展示错误摘要，并可点进对应执行记录查看明细。
6. **若**对某楼层点「回复」并发送，**则**回复挂在目标楼层下方（一层嵌套）。
7. **若**讨论触发了执行，**则**该执行对应的载体 Todo **不出现**在事项中心与 todo 列表。
8. **若**运行 `cargo clippy --all-targets -- -D warnings`、`cargo test`、`npx tsc --noEmit`，**则**全部通过。

## 10. 风险与已知不确定点

- **长任务期间占位帖停留过久**：缓解=占位帖实时显示「正在干活…」+ 轮询/事件管道更新；AI 遇到执行器无响应时不静默，帖子标记 `failed`。
- **默认执行器未配置或未启用**：降级到 `ExecutorType::default()`（Claude Code），并在智能体帖里提示所用执行器；AI 不得擅自挑选未启用的执行器。
- **专家名与执行器名冲突（同名）**：解析优先级=先匹配专家、再匹配执行器；`@选择器` 显式带类型时以选择器类型为准，避免歧义。AI 遇到无法消歧的同名时**停止并请求人工确认**。
- **多人并发发帖**：帖子按 `created_at` 排序；各 `@` 触发的执行互不阻塞（各建各的载体 Todo），受既有并发上限约束。
- **载体 Todo 累积**：每条 `@` 触发产生一个隐藏 Todo（与现有「每次执行一个 Todo」量级一致）；如后续需清理，另立需求，不在本次范围。
