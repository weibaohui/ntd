## 1. 实现了什么

executor_service 完成/终态路径的 6 个大参数列表函数塌缩（纯签名重构，逻辑零改动）：

| 函数 | 参数数 | 新签名 |
|------|-------|--------|
| `finalize_normal_completion` | 19 → **2** | `(ctx: &SpawnContext, outcome: CompletionOutcome)` |
| `emit_completion_events` | 15 → **4** | `(ctx, &outcome, duration_secs, total_tokens)` |
| `handle_timeout_branch` | 14 → **1** | `(runtime: &SpawnRuntime)`（timeout_str 移入函数内现算，Replace Parameter with Query） |
| `handle_cancellation_branch` | 12 → **1** | `(runtime: &SpawnRuntime)` |
| `handle_spawn_failure` | 12 → **2** | `(runtime, error)` |
| `run_cancellation_path` / `run_timeout_path` | 17 → **2** | `(teardown: ProcessTeardown, runtime)` |

新增参数对象（`types.rs`）：`CompletionOutcome`（success/exit_code/result_str 数据团）、
`ProcessTeardown`（kill+drain 所需的 5 个进程句柄簇）。

同时删除：
- `dispatch_cancellation` / `dispatch_timeout` 纯转发壳（**Remove Middle Man**，match 臂直接装配 ProcessTeardown）；
- 3 处已失效的 `#[allow(clippy::too_many_arguments)]`——clippy 对该路径恢复守卫。

## 2. 实施要点

- 各函数体**零改动**：开头解出与原参数同名的局部量（Arc clone 或引用），下游代码不变；
- 唯一编译期插曲：`outcome.result_str` 提前 move 触发部分移动错误 → 改 clone（一次 String 克隆可忽略）；
- 死引用清理：`todo_title`/`exit_code`/`feishu_*` 在 emit 收口后不再单独解包。

## 3. 测试与验证结果

- `cargo clippy --all-targets -- -D warnings`：零告警（删 allow 后仍零告警，证明参数数达标）✅
- `cargo test --no-fail-fast`：1629 通过（executor_service 区 71 例全绿；唯一失败为预存量环境问题 git_sync）✅
- 假执行器端到端冒烟：任务执行成功，完成路径（含 emit_completion_events / finalize）正常落定 ✅

## 4. 已知限制 / 后续候选

- `db/usage.rs` 的 `create_usage_daily_stat`（16 参）/`replace_daily_stats_for_date`（14 参）与
  `message_debounce.rs` 的 12/10 参函数是同族候选，留后续 PR（设计 §3 已声明）；
- 全仓仍有 ~45 处 `too_many_arguments` allow 压制，按本批次的模式逐簇清理。

## 5. 安全反思

纯参数传递结构变化；字段来源不变；无接口/行为变化；编译器全程护航（部分移动错误即证明类型检查在有效工作）。
