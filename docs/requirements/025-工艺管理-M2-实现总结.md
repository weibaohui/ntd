## 3. 关键实现点

### 3.1 产物捕获模块（`artifact_capture.rs`）

- **四种捕获类型**：
  - `file`：安全路径校验 → `tokio::fs::read` 限 64KB 快照；
  - `text`：从 `execution_record.result` 中按 marker 提取（skill 可定义 marker 约定）；
  - `url`：正则 `https?://...` 提取第一个 URL；
  - `json`：Markdown ````json` 代码块 → 括号匹配回退。
- **路径安全**：`resolve_within_workspace` 双保险——字符串层绝对路径拒 +
  IO 层 `canonicalize` 截击符号链接逃逸；文件不存在时 fallback 到 normalize 路径前缀检查。
- **ArtifactSpec 与安装器互联**：`from_expected` 将 `services/process::ExpectedArtifact` 转为产物捕获规格。

### 3.2 门禁引擎（`gate_evaluator.rs` + `gates/`）

- **四类型分派**：`gate_evaluator.rs::evaluate_single_gate` 按 `gate_type` 分发：
  - `artifact_present` → 直接内存判断；
  - `human_approval` → 返回 pending；
  - `script_check` → `tokio::process::Command` 执行，白名单 + 路径校验；
  - `ai_criteria_review` → 检查已有评分（`execution_rating`），无评分时返回 `needs_review` 标记。
- **AI 评审 prompt 拼接**：`ai_criteria_review::build_review_prompt` 按序拼接 workspace 共识 prompt → 工艺验收标准 → skill 自检清单 → 被评审产物内容。
- **隐式门禁降级**：`infer_gates_from_fallback` 在 `gate_config` 为空时，从 `min_rating` / `review_type` 自动生成门禁配置，保证存量 Loop 零改动。

### 3.3 流转解析器（`transition_resolver.rs`）

- 纯函数，无 IO 依赖，便于单元测试。
- `resolve_next` 按 `gates_passed` 选 `on_success` / `on_rating_fail` 策略。
- `resolve_by_policy` 处理 `next/goto/end/break/skip` 五种策略及 fallback。
- 共识：不关心 `on_gate_fail` vs `on_rating_fail` 的区别——安装器已做 failback 解析写入 `fail_goto_step_id`。

### 3.4 返工追踪器（`rework_tracker.rs`）

- `evaluate_rework` 判定：目标索引 ≤ 当前索引 → 返工。
- `ReworkDecision` 三状态枚举：`Allowed(i32)` / `MaxedOut` / `NotRework`。
- `MaxedOut` 时由 `PhaseDriver` 终止流转（返回 `next_idx = None`）。

### 3.5 阶段驱动器（`phase_driver.rs`）

阶段驱动器是 M2 的核心编排器，其 `execute_step` 函数按序执行：

```
1. 解析 expected_artifacts JSON → ArtifactSpec 列表
2. ArtifactCapture::capture_step_artifacts   → 写入 loop_step_artifacts
3. infer_gates_from_fallback（兼容旧 min_rating / review_type）
4. GateEvaluator::evaluate_step_gates         → 写入 loop_step_execution_gates
5. TransitionResolver::resolve_next           → 计算 next_idx
6. ReworkTracker::evaluate_rework              → 检查 max_rework
7. db.set_step_execution_rework_count           → 更新返工计数（如需）
8. db.finish_step_execution                     → 更新 status / rating / error_message
9. update_phase_execution                       → 维护 loop_phase_executions
```

返回值 `StepOutcome` 包含：`gate_passed` / `rating` / `error_message` / `next_idx` / `paused` / `rework_count` / `artifacts` / `gate_summary`。

### 3.6 LoopRunner 接入

`loop_runner.rs` 的 `run_inner_from` 方法中，在 4h（评分闸门）入口处新增检测：

```rust
let has_process_config = (!step.gate_config.is_empty() && step.gate_config != "[]")
    || (!step.expected_artifacts.is_empty() && step.expected_artifacts != "[]");

if has_process_config {
    // 加载 execution_record
    // 调用 PhaseDriver::execute_step
    // 使用 StepOutcome 更新计数器 + 确定 current_idx
    // 跳过旧流程
    continue;
}
```

**设计要点**：
- 旧 Loop 步骤（`gate_config = "[]"`）走原路径，零影响；
- PhaseDriver 写入产物表、门禁表、阶段执行表，完成 step_execution 终态化；
- LoopRunner 仅需根据 `outcome.gate_passed` 更新 `completed/failed` 计数、`last_output`、`current_idx` 和黑版推送。

## 4. Skill-centric 工艺模型在实践中

M2 实现的 skill-centric 模型确保：

| 你的四类 | 实现方式 | 当前状态 |
|---------|---------|---------|
| 1. 干什么（约束条件） | `link.skills[...]` → skill「目标 + 必须包含 + 禁止」章节 | ✅ 结构化绑定 + skill 文件约定 |
| 2. 用什么模板 | skill 文件「输出产物 + 格式」章节 | ✅ skill 文件约定 |
| 3. 产物放哪儿 | `expected_artifacts[]` | ✅ 结构化 `loop_steps` |
| 4. 怎么校验 | `gates[]` + AI 按 skill 自检清单评审 | ✅ 3/4 门禁类型已实现 |

### 3.7 DeliveryState / RepairLog

- **`delivery_state.rs`**：生成 `.ntd/delivery-state.md`，Markdown 表格展示 Loop 元信息、产物清单、门禁结果。每次 step 完成时由 PhaseDriver 调用重写。
- **`repair_log.rs`**：追加 `.ntd/repair-log.md` 条目，包含时间、环节名、失败原因、返工次数/上限、目标环节。追加不覆盖，保留完整修复历史。
- 文件路径均为 `{workspace_path}/.ntd/` 下。

**关键设计原则**：结构化框架（环节/skill/产物/门禁）作为一等公民，具体内容模板由 skill 文件承载，AI 智能推理。
