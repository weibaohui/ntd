## 1. 设计目标

在概念导航首页关系图（`/#/onboarding` 的 `ConceptRelationGraph`）中新增「黑板」「看板」两个支线小圆节点，补齐「定义 → 执行 → 观察」概念地图的观察层。改动严格限制在 2 个前端文件内，零后端改动、零新依赖。

对应需求：`docs/requirements/030-导航关系图黑板看板节点-需求.md`

---

## 2. 架构总览

```text
用户点击节点
   │
   ▼
ConceptRelationGraph.tsx          concepts.tsx（纯静态数据，本次主战场）
   │ 读取                            ├─ GRAPH_NODES  +2 节点（blackboard/kanban）
   │                                 ├─ GRAPH_EDGES   +4 条边
   │                                 └─ GraphNode     +3 可选字段
   ▼
GraphNodeDrawerFallback（增强）
   │ node.drawerDesc → 说明文案
   │ node.navTarget  → 「去 XX 页」按钮
   ▼
useViewState().pushUrl(view, { mode })   ← 028 既定的嵌套组件独立实例模式
   │
   ▼
/#/blackboard   或   /#/memorial?mode=kanban
```

**核心设计原则：渲染逻辑零改动。** `ConceptRelationGraph` 的节点圆、连线、hover 高亮、流动动画全部数据驱动，新增节点/边只需改 `concepts.tsx` 的数据；组件层唯一改动是增强 fallback Drawer（说明文案 + 跳转按钮）。

## 4. 关键设计决策

### 4.1 黑板/看板定位为「支线节点」，不进 CONCEPTS

- **决策**：复用现有支线节点机制（无 `conceptId`），不扩展 `ConceptNode['id']` 联合类型。
- **理由**：经 grill-me 确认用户选择「支线小圆 + Drawer 说明 + 跳转按钮」。若升级为正式概念，`ConceptCounts = Record<ConceptNode['id'], ...>` 强类型映射会强制联动 ConceptCardGrid / useConceptCounts / ConceptDetailSection 共 5+ 文件，违反 YAGNI 与需求非目标。

### 4.2 跳转能力挂在 GraphNode 数据上，而非组件分支硬编码

- **决策**：`GraphNode` 新增 `drawerDesc?` / `navTarget?` / `navMode?` 三个可选字段，fallback Drawer 按字段渲染。
- **理由**：现有 fallback 是固定通用文案；若为新节点写 `if (node.id === 'blackboard')` 分支，第三个观察类节点出现时还得再改组件。数据驱动后，未来任何支线节点要加说明/跳转只需改数据。
- **兼容性**：三字段全部可选，既有 4 个 fallback 节点（执行记录/触发器/技能/模型）不填，行为逐字节不回归。

### 4.3 跳转用 useViewState().pushUrl，不用 window.location.hash

- **决策**：`ConceptRelationGraph` 内 `const { pushUrl } = useViewState()`，按钮点击调 `pushUrl(node.navTarget, { mode: node.navMode })`。
- **理由**：028 注释明确记载——`history.pushState` 不触发 popstate，裸写 `location.hash` 会绕过 `ntd-nav-change` 事件广播，导致 App 根实例状态不同步。嵌套组件各自实例化 useViewState 是全站既定模式（MemorialBoard/BlackboardPage 均如此）。
- **URL 产出**：`pushUrl('blackboard')` → `/#/blackboard`；`pushUrl('memorial', { mode: 'kanban' })` → `/#/memorial?mode=kanban`（`buildHashUrl` 与 `BoardMode` 白名单原生支持，零改动）。

### 4.4 新节点坐标（viewBox 1000×400 不变）

| 节点 | 坐标 | 选位理由 |
|------|------|---------|
| 黑板 blackboard | **(900, 60)** | 与执行记录 (900,200) 同列正上方，「执行记录→黑板」成垂直短边；顶行既有触发器(440)/执行器(680)，右侧空位正好 |
| 看板 kanban | **(960, 340)** | 底行最右端；与模型 (860,340) 圆心距 100（=专家↔模型既有间距，视觉节奏统一）；右缘 996 ≤ 1000 不出界 |

**几何安全验证**（圆心距须 ≥ 半径和 72；连线不得进入第三方节点圆）：

- 黑板(900,60) vs 执行器(680,60)：距离 220 ✓；vs 执行记录(900,200)：140 ✓
- 看板(960,340) vs 模型(860,340)：100 ✓；vs 执行记录(900,200)：约 152 ✓
- `环路→黑板` 连线 (400,200)→(900,60)：x=680 处 y≈122，执行器圆 (680,60) r=36 的 y 范围 24~96，不进入 ✓；x=440 处 y≈189，远离触发器(440,60) ✓
- `事项→黑板` (680,200)→(900,60)、`执行记录→看板` (900,200)→(960,340)：路径上无第三方节点 ✓

### 4.5 连线语义与标签

| 边 | label | 语义出处（用户原话） |
|----|-------|---------------------|
| 事项 → 黑板 | 持续分析 | 「黑板是根据事项、执行记录不断的自动分析得出的观察报告」 |
| 执行记录 → 黑板 | 持续分析 | 同上 |
| 环路 → 黑板 | 环节结论 | 「黑板在环路里面还有小黑板，记录了环路上各个环节的执行结论」 |
| 执行记录 → 看板 | 进度展示 | 「看板是执行进度进展的展示方式」 |

两条「持续分析」边 label 相同但 `from-to` key 不同（`todo-blackboard` / `execution-blackboard`），React key 无冲突。

### 4.6 highlights 双向同步

高亮机制是单向声明（A 的 highlights 含 B，hover B 时 A 才亮），因此双向可见需两侧都声明：

- 新节点自声明：`blackboard.highlights=['todo','execution','loop']`、`kanban.highlights=['execution']`
- 既有节点追加：`loop` +`'blackboard'`；`todo` +`'blackboard'`；`execution` +`'blackboard','kanban'`

效果：hover 黑板 ↔ 事项/执行记录/环路互亮；hover 看板 ↔ 执行记录互亮；hover 执行记录时黑板看板同时亮（场景 C）。

## 5. 组件设计

### 5.1 `concepts.tsx` 改动明细

```ts
// GraphNode 接口新增（全部可选，向后兼容）：
/** Drawer 说明文案（仅无 conceptId 的支线节点用）；缺省走通用 fallback 文案。 */
drawerDesc?: string;
/** Drawer 底部「去 XX 页」按钮的跳转目标；缺省则无按钮。 */
navTarget?: View;
/** 跳转 query 的 mode（看板 ?mode=kanban 用）；其他视图缺省。 */
navMode?: BoardMode;
```

- 需新增 `import type { BoardMode } from '@/hooks/useViewState'`（已有 `View` 的同源导入，合并为一行）
- GRAPH_NODES 追加 2 条、既有 3 条 highlights 原地追加 id
- GRAPH_EDGES 追加 4 条（注释标明语义出处）

### 5.2 `ConceptRelationGraph.tsx` 改动明细

**GraphNodeDrawerFallback 增强**（函数体控制在 50 行内）：

```text
输入：node: GraphNode + onNavigate: (node) => void
1. 标题：node.label（现有）
2. 文案：node.drawerDesc ?? 现有通用文案
3. 若 node.navTarget 存在 → 渲染 Button（type=primary，「去{node.label}页」）
   点击 → onNavigate(node)
```

**主组件**：

- 新增 `const { pushUrl } = useViewState();`
- 新增 `handleNodeNavigate(node)`：先 `setDrawerNode(null)` 关 Drawer，再 `pushUrl(node.navTarget!, { mode: node.navMode })`
  - 先关 Drawer 再跳转：跳转后 onboarding 视图卸载，避免 Drawer 残留遮罩在新页面上
  - `node.navTarget!` 的非空断言由调用处 `navTarget` 存在性检查保证（仅在按钮存在时触发，按钮渲染条件即 navTarget 非空）——改为在 handleNodeNavigate 内做 early-return 判空，彻底避免非空断言
- Drawer 处把 `handleNodeNavigate` 透传给 fallback

**不改的部分**：Edge / GraphNodeCircle / usePrefersReducedMotion / edgePath / nodeRadius / 主组件 SVG 结构，一行不动。

## 7. 错误处理与边界

| 场景 | 处理 |
|------|------|
| `navTarget` 未定义 | 不渲染按钮（条件渲染），纯文案 Drawer |
| `drawerDesc` 未定义 | 回退现有通用文案「这是关系图的支线节点……」 |
| handleNodeNavigate 收到 navTarget 为空的节点 | early return，不跳转（防御性，正常路径触达不到） |
| `prefers-reduced-motion` | 新连线自动继承既有降级逻辑（无动画仅高亮） |
| 小屏横向溢出 | 容器既有 `overflow-x: auto` + svg `minWidth: 600`，新节点在 viewBox 内自动适配 |

---

## 8. 安全反思

- 纯静态数据 + 前端路由跳转：无用户输入、无网络请求、无存储写入、无权限面变化
- 跳转目标为白名单 View 字面量（TS 编译期约束），不存在开放式 URL 注入
- Drawer 文案为硬编码中文字符串，不经 HTML 注入路径（React 文本节点转义）

---

## 9. 已知限制

- 图节点增至 12 个后，宽度 < 700px 的屏幕需横向滚动（既有 `overflow-x: auto` 兜底，移动端本就非常规使用路径，026 已声明不做移动端独立适配）
- 「环节小黑板」仅在 Drawer 文案中提及，图内无可点节点（经确认的取舍）
- 黑板/看板不出现在概念卡网格与详细说明区（非目标）
