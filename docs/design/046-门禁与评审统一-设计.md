## 1. 背景

### 1.1 触发场景

任务 37（loop「口头需求工艺」#72）的环节 1「补写 PRD」连续失败 6 次。
诊断发现根因不是评分流程，而是**门禁判定的职责划分存在概念混乱**：

- `expected_artifacts[].path` 含占位符 `{process_name}`，这是**给 AI 结合上下文理解的占位符**。
  AI 写文件时根据自己的理解填充这个占位符（需求名称、任务 slug 等），具有主观性。
- 但 `artifact_present` 门禁用程序 `fs::exists` 判定文件存在性，根本不知道该把
  `{process_name}` 替换成什么，导致路径字面上不存在，门禁 fail。
- 用户提问："判定文件是否存在，让文件系统去判断有点问题……这些占位符是给 AI 结合上下文
  理解的……我们不应该用程序去做文件的存在性的判断，而是应该统一的把这些门禁的判定规则
  交给这个 AI 去做。"

### 1.2 现状门禁类型

当前 `gate_config` 支持 4 类门禁，机械判定与 AI 评审混判：

| 门禁类型 | 判定什么 | 谁来判 | 是否启动 AI | 是否启动评分程序 |
|---|---|---|---|---|
| `artifact_present` | 文件/产物是否存在 | 文件系统（`fs::exists`） | 否 | 否 |
| `script_check` | 脚本执行结果 | 脚本执行器（`tokio::process::Command`） | 否 | 否 |
| `human_approval` | 人工审批 | 人 | 否 | 否 |
| `ai_criteria_review` | AI 评审产物质量 | AI | 是 | 是（产出 rating） |

### 1.3 概念混乱点

1. **占位符语义不归程序推断**：`{process_name}` 这类占位符是给 AI 上下文理解的，程序做
   `fs::exists` 时不知道该替换成什么，割裂了评审流程。
2. **文件存在性校验应归 AI**：AI 写了文件，AI 最清楚自己写到了哪里；文件路径里的占位符
   本来就是 AI 上下文的一部分。
3. **打分程序归属混乱**：`ai_criteria_review` 启动打分程序，文件是否存在没有单独处理，
   验收标准里也用打分——三套体系打架。

## 2. 决策汇总

经与用户确认，最终决策如下：

| 问题 | 决策 |
|---|---|
| 门禁判定主体 | 只有 `human_approval` 不归 AI；`artifact_present`/`script_check`/`ai_criteria_review` 全归 AI |
| script_check 归属 | **全归 AI** —— AI 自己决定是否跑脚本、怎么跑，拿到完整工作空间访问权限自行判定 |
| 产物捕获去留 | **保留**（用于前端展示、审计追溯）；但门禁判定不再依赖 `loop_step_artifacts` 表，改由 AI 评审判定 |
| min_score 来源 | **gate_config.min_score** —— 仍从 gate_config 里的 ai_criteria_review 门禁配置读取 |
| 验收标准与门禁关系 | **合并为单一评审** —— AI 一次性判定产物存在性、内容质量、脚本执行结果，返回综合 rating |
| artifact_present 处理 | **废弃** —— 产物存在性检查改由 AI 在评审环节判定 |
| 门禁要求写入评审模板 | **是** —— 把门禁判定要求写进评审模板，执行前字符串替换（`{{loop_name}}`/`{{expected_artifacts}}`/`{{gates}}` 等） |
| 破坏性变更处理 | **直接破坏性变更** —— 修改代码和 DB schema，提供数据迁移脚本，不兼容旧 gate_config |
| AI 评审载体 | **复用 auto_review** —— 复用现有 auto_review 流程（已有评分解析 `RATING: N`、产出 `execution_record.rating`）；门禁判定改为读这个 rating 与 min_score 比较 |

## 3. 目标架构

### 3.1 门禁类型收敛（4 类 → 2 类）

**之前：**
```json
gate_config: [
  {"name": "PRD存在", "type": "artifact_present", "artifact": "PRD"},
  {"name": "测试通过", "type": "script_check", "script": "run_tests.sh"},
  {"name": "AI评审", "type": "ai_criteria_review", "min_score": 80},
  {"name": "人工审批", "type": "human_approval"}
]
```

**之后：**
```json
gate_config: [
  {"name": "AI评审", "type": "ai_criteria_review", "min_score": 80},
  {"name": "人工审批", "type": "human_approval"}
]
```

- `artifact_present`、`script_check` **废弃**
- 产物存在性、脚本执行结果 → **全部归入 ai_criteria_review 的评审范围**
- AI 评审时拿到：产物内容 + 验收标准 + 门禁要求（已替换占位符）+ 工作空间访问权限
- AI 给出综合 rating（0-100），与 `min_score` 比较 → 门禁 pass/fail

### 3.2 评审模板：门禁要求写入，执行前字符串替换

评审模板（`review_prompt` 或环路级 `review_template_id`）中，把门禁判定要求作为评审指令
的一部分写进去。执行前用 `replace_placeholders` 做字符串替换：

| 占位符 | 替换值来源 |
|---|---|
| `{{loop_name}}` | loop.name（工艺名称） |
| `{{process_name}}` | 同上（语义别名） |
| `{{requirement}}` | todo.prompt（任务需求） |
| `{{expected_artifacts}}` | loop_steps.expected_artifacts JSON（原样，不预替换占位符） |
| `{{gates}}` | loop_steps.gate_config JSON |
| `{{acceptance_criteria}}` | todo.acceptance_criteria / 环节级 |
| `{{workspace_path}}` | loop.workspace_path |

**关键设计**：`expected_artifacts[].path` 里的 `{process_name}` 占位符**不预替换**，原样
传给 AI 评审上下文。AI 评审时根据占位符语义和上下文，自行判定文件是否存在于正确路径。

### 3.3 产物捕获：保留但语义变化

- `loop_step_artifacts` 表保留（前端展示、审计追溯用）
- 产物捕获不再预替换占位符 —— `expected_artifacts[].path` 原样记录
- 门禁判定**不再依赖** `loop_step_artifacts` 表 —— 改由 AI 评审时自行判定
- `artifact_present` 门禁评估逻辑废弃

### 3.4 script_check 归 AI

- **脚本执行本身** → AI 自己决定（AI 有完整工作空间访问权限）
- **脚本执行结果判定** → AI 评审时自行跑脚本、看输出、判 pass/fail
- 旧的 `script_check` 门禁类型废弃，并入 `ai_criteria_review`

### 3.5 min_score 来源

- 仍从 `gate_config` 里的 `ai_criteria_review` 门禁配置读取
- AI 评审给出 rating，`rating >= min_score` → 门禁 pass

### 3.6 AI 评审载体：复用 auto_review

复用现有 `auto_review` 流程：

- 已有评分解析 `RATING: N` 格式
- 已有产出 `execution_record.rating`
- 门禁判定改为读这个 rating 与 `min_score` 比较

## 4. 详细设计

### 4.1 代码改动点

#### 4.1.1 `gate_evaluator.rs`

移除 `artifact_present` 和 `script_check` 分支，只保留 `ai_criteria_review` 和
`human_approval`：

```rust
async fn evaluate_single_gate(
    ctx: &GateContext<'_>,
    execution_rating: Option<i32>,
) -> Result<GateResult, crate::services::process::ProcessError> {
    match ctx.config.gate_type.as_str() {
        "human_approval" => {
            let result = human_approval::evaluate(ctx)?;
            Ok(result)
        }
        "ai_criteria_review" => {
            let result = ai_criteria_review::evaluate(ctx, execution_rating)?;
            Ok(result)
        }
        // 废弃类型：artifact_present、script_check 不再支持
        _ => Err(crate::services::process::ProcessError::Config(format!(
            "不支持的门禁类型「{}」，已废弃的类型：artifact_present、script_check",
            ctx.config.gate_type
        ))),
    }
}
```

#### 4.1.2 废弃文件

- `backend/src/services/process/gates/artifact_present.rs` → 删除
- `backend/src/services/process/gates/script_check.rs` → 删除
- `backend/src/services/process/gates/mod.rs` → 移除对应 mod 声明

#### 4.1.3 `phase_driver.rs`

简化评分等待逻辑：

- 移除 `ai_review_wait_timeout` 和 `poll_rating` 的复杂等待逻辑
- 改为：环节执行完成后，直接读 `execution_record.rating`（auto_review 已产出）
- 如果 rating 为 None（auto_review 未跑或未出分），门禁 fail

```rust
// 简化后的评分获取
let execution_rating = execution_record.and_then(|r| r.rating);

// 如果配置了 ai_criteria_review 门禁但没有 rating，直接 fail
let has_ai_gate = effective_gate_config
    .iter()
    .any(|g| g.gate_type == "ai_criteria_review");
if has_ai_gate && execution_rating.is_none() {
    // AI 评审未出分，门禁 fail
    return Ok(StepOutcome {
        gate_passed: false,
        rating: None,
        // ...
    });
}
```

#### 4.1.4 评审模板：门禁要求写入

在 `compose_review_prompt`（或等效函数）中，把门禁判定要求写入评审模板：

```rust
fn compose_review_prompt(
    base_template: &str,
    loop_name: &str,
    requirement: &str,
    expected_artifacts: &str,  // JSON 原样
    gates: &str,               // JSON 原样
    acceptance_criteria: &str,
    workspace_path: &str,
) -> String {
    base_template
        .replace("{{loop_name}}", loop_name)
        .replace("{{process_name}}", loop_name)  // 语义别名
        .replace("{{requirement}}", requirement)
        .replace("{{expected_artifacts}}", expected_artifacts)
        .replace("{{gates}}", gates)
        .replace("{{acceptance_criteria}}", acceptance_criteria)
        .replace("{{workspace_path}}", workspace_path)
}
```

#### 4.1.5 `loop_step_execution_gates` 表

- 废弃 `artifact_present` 和 `script_check` 类型的记录写入
- 表结构不变（兼容历史数据），但新数据只会有 `ai_criteria_review` 和 `human_approval`

### 4.2 数据迁移

#### 4.2.1 DB 迁移

提供 SQL 迁移脚本 `backend/src/db/migrations/046_unify_gates.sql`：

```sql
-- 1. 把 artifact_present 门禁迁移为 ai_criteria_review
--    （产物存在性检查改由 AI 评审时自行判定）
UPDATE loop_steps
SET gate_config = REPLACE(
    gate_config,
    '"type":"artifact_present"',
    '"type":"ai_criteria_review","min_score":60'
)
WHERE gate_config LIKE '%artifact_present%';

-- 2. 把 script_check 门禁迁移为 ai_criteria_review
--    （脚本执行结果判定改由 AI 评审时自行判定）
UPDATE loop_steps
SET gate_config = REPLACE(
    gate_config,
    '"type":"script_check"',
    '"type":"ai_criteria_review","min_score":60'
)
WHERE gate_config LIKE '%script_check%';

-- 3. 把 loop_step_execution_gates 表中历史 artifact_present/script_check 记录
--    迁移为 ai_criteria_review（保留历史评分数据）
UPDATE loop_step_execution_gates
SET gate_type = 'ai_criteria_review'
WHERE gate_type IN ('artifact_present', 'script_check');
```

#### 4.2.2 工艺 YAML 源文件迁移

提供脚本 `backend/src/services/process/migrate_gates_046.rs`：

- 扫描所有 `bundled://` 和 `user://` 工艺 YAML 文件
- 把 `artifact_present` 和 `script_check` 门禁类型迁移为 `ai_criteria_review`
- 更新评审模板，把门禁判定要求写入

## 6. 风险与回滚

### 6.1 风险

- **破坏性变更**：废弃门禁类型不兼容旧 gate_config，需要数据迁移
- **AI 评审依赖**：门禁判定完全依赖 AI 评审出分，AI 评审失败会导致门禁 fail
- **评审模板变更**：评审模板需要增加门禁判定要求，可能影响现有 AI 评审质量

### 6.2 回滚

- DB 迁移脚本提供回滚 SQL
- 工艺 YAML 迁移脚本提供回滚逻辑
- 代码改动可通过 git revert 回滚
