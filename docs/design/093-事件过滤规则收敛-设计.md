> 093 专项 B2（重构批次 2）。源自 skill 扫描诊断第 3 条：Duplicated Code——
> 「哪些 ExecutionEvent 该往哪发」的知识在三处重复书写。

## 1. 背景与证据

同一套事件过滤知识当前写三遍（注释自承「过滤规则一致」）：

| 位置 | 规则（逐分支核对） |
|------|------|
| `log_capture.rs::parse_and_broadcast`（WS Output 广播） | 转发：Info(非JSON非空)、Error、Thinking、ToolCall、ToolResult、Assistant、Result、SessionStart、Tokens、Cost、Duration、StepStart、StepFinish、ModelSwitch；跳过：SessionEnd、Progress、User、System |
| `message_debounce.rs::parse_for_direct_stream`（飞书私聊收集） | 收集：Info(同上规则)、Thinking、ToolCall、ToolResult、Assistant、Result；其余全跳过 |
| `message_debounce.rs::emit_direct_stream`（私聊发送） | 按 log_type 再过滤一道（覆盖非 pipeline 来源条目，**不在本次范围**） |

外加两处骨架重复：「trim 空行守卫 → len_before → feed → 取新增切片」在 parse_and_broadcast 与 parse_for_direct_stream 各写一遍。

> 更正：扫描阶段我的脚本把 `parse_for_direct_stream` 误测为 708 行（原始字符串括号干扰计数），实测 ~55 行——本批次的真实问题是**规则三处重复**，不是函数超长。

## 2. 设计

### C1：分类判定上移为事件自身的方法（`execution_events/event.rs`）

沿用该文件已有的 `to_log_type()` / `is_interactive()` / `is_message()` 风格：

```rust
impl ExecutionEvent {
    /// WS Output 广播过滤（原 parse_and_broadcast 的 match 分支规则上移）
    pub fn should_broadcast(&self) -> bool;
    /// 飞书私聊直推收集过滤（原 parse_for_direct_stream 的分支规则上移）
    pub fn is_direct_stream_worthy(&self) -> bool;
}
```

- Info 的内容规则（`starts_with('{') || is_empty()` 跳过）封装进方法内部；
- SessionEnd 仍返回 false（逐行路径不转发，由 finalize 路径统一发——现状语义不变）。

### C2：feed 骨架收口（`execution_events/pipeline.rs`）

```rust
impl EventPipeline {
    /// 喂入一行 stdout 并返回本次新增事件切片（空行守卫 + len_before 簿记内化）
    pub fn feed_stdout_new(&mut self, line: &str) -> &[ExecutionEvent];
}
```

stderr 路径（`try_parse_stderr_with_pipeline`）因 atomcode 特判选择 feed/feed_stderr，骨架不同构，**不动**。

### C3：两个调用方改写为薄循环

- `parse_and_broadcast`：NTD-012 回授（`on_pipeline_event` 对**全部**新事件调用）保持不动；过滤改用 `should_broadcast()`；函数体从 ~90 行降到 ~25 行；
- `parse_for_direct_stream`：过滤改用 `is_direct_stream_worthy()`；~55 行降到 ~25 行。

### C4：单测

`event.rs` 内新增分类方法测试：全 18 个变体的两维判定矩阵 + Info 内容规则三态（JSON 行/空串/普通文本）。

## 3. 影响模块

| 文件 | 变化 |
|------|------|
| `execution_events/event.rs` | +2 方法 +单测 |
| `execution_events/pipeline.rs` | +1 骨架方法 |

| `services/message_debounce.rs` | parse_for_direct_stream 收窄 |

## 4. 不做的事

- `emit_direct_stream` 的 log_type 二级过滤保留（它过滤的是 ParsedLogEntry，覆盖 executor 旧解析路径来源的条目，与事件级过滤不同层）；
- finalize 路径的无差别 `emit_broadcast_event`（SessionEnd 由此发出）保持现状；
- 双解析体系本身的合并属 B4。

## 5. 验证方案

1. 分类方法单测：18 变体 × 2 判定全枚举断言；
2. 既有测试全绿（parse_and_broadcast 有 NTD-012 回归与 log_capture 测试覆盖；message_debounce 有 services_tests）；
3. clippy 零告警；
4. `make dev` 冒烟：执行一个任务，执行面板日志流正常（WS 广播路径回归）。

## 6. 安全反思

- 过滤规则只做搬移不做增删，逐分支对照表即核对清单（§1 表）；
- 无事件 schema / 接口 / 权限变化。
