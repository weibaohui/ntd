# NTD-013 任务列表委派工艺状态修复 — 设计

| 修改人 | 修改时间 | 修改内容 |
|--------|---------|---------|
| TraeAI | 2026-08-10 | 初始版本 |

---

## 1. 设计目标

修复任务列表三关联问题（工艺列 `#0-#0--` 格式、委派状态不同步、委派任务列表无委派信息透出），保持环路任务既有行为零改动。

## 2. 非目标

- 不扩状态枚举（暂不引入 `cancelled`，用现有 4 态）
- 不改动事项 / 环路列表页除 `formatProcessText` 防御性判空外的其他逻辑
- 不新增列表列：委派信息复用「工艺」列位置，类型徽标 inline 在状态列

## 3. 后端改动

### 3.1 文件：`backend/src/db/task.rs` — `create_delegate_task`

| 原代码 | 新代码 | 说明 |
|--------|--------|------|
| `template_id: ActiveValue::Set(Some(0))` | `template_id: ActiveValue::Set(None)` | 语义明确：委派无工艺 |
| （缺失） | `status: ActiveValue::Set("running".to_string())` | 首帖立即触发，状态同步为运行中 |

### 3.2 文件：`backend/src/handlers/task_posts.rs` & `executor_service/completion.rs` — task.status 回写

**回写路径搜索与补全**：
- 凡写 `task_posts.status = success/failed/running` 的位置，同时调用 `db.update_task_status(task_id, same_status)`
- 特别注意：
  - 讨论帖回写结论（`success` / `failed`）
  - 人工审批续跑后的状态变化
  - `continue_delegated_task`（接力路径）：新一轮触发时 task.status 保持 `running`

### 3.3 TaskItem 字段

无需改动 — `execution_mode`、`assignee_*`、`auto_continue` 已在 `build_task_item` 中原样透传。

## 4. 前端改动

### 4.1 文件：`frontend/src/utils/processText.ts` — `formatProcessText`

```typescript
// 扩展 id 判空：null / undefined / 0 / 负数都视为无工艺来源
if (id == null || id <= 0) return '-';
```

### 4.2 文件：`frontend/src/components/tasks/TasksTableView.tsx`

**改动点 1 — 状态列 render**（`buildColumns` 第 78-80 行）：
- 原：只渲染状态 Tag
- 新：状态 Tag 后追加一个小号灰色类型徽标（`环路` / `委派`），`execution_mode` 为 `delegate` 时显示「委派」，否则「环路」

```tsx
render: (status: string, task) => (
  <>
    <Tag color={statusColor(status)}>{STATUS_LABEL[status] ?? status}</Tag>
    <Text type="secondary" style={{ fontSize: 10, marginLeft: 4 }}>
      {task.execution_mode === 'delegate' ? '委派' : '环路'}
    </Text>
  </>
),
```

**改动点 2 — 工艺列 render**（第 119-122 行）：
- 分支：`execution_mode === 'delegate'` → 委派信息 Tag
- 否则 → 原工艺三段式（`formatProcessText` + 判 `-` 输出灰色 `—`）

```tsx
render: (_, task) => {
  if (task.execution_mode === 'delegate') {
    // 委派任务：显示委派处理人信息 + 自动接力标记
    const kindLabel = task.assignee_kind === 'expert' ? '专家' : '执行器';
    const name = task.assignee_name ?? '未知';
    const base = `委派给：${name}（${kindLabel}）`;
    const suffix = task.auto_continue ? ' 🚀自动接力' : '';
    return <Tag color="blue">{base}{suffix}</Tag>;
  }
  // 环路任务：原工艺列逻辑不变
  const text = formatProcessText(task.template_id, task.template_name, task.template_version);
  return text === '-' ? <Text type="secondary">—</Text> : <Tag>{text}</Tag>;
},
```

### 4.3 其他视图（Card / Kanban）

作为同口径扩展（可一并调整，保持三视图一致）：
- **TasksCardView**：若卡片头部有工艺展示位，同步改为委派分支
- **TasksKanbanView**：卡片头状态 Tag 后加徽标，卡片内工艺位同步委派分支

（如改动过大可先只修 Table 视图，其余视图在 PR 中备注后续跟进；本方案默认 Table 必改、Card/Kanban 同步修改确保口径一致。）

## 5. 兼容性

- 存量数据：老委派任务 `template_id=Some(0)` → 前端 `id <= 0` 兜底 → 显示 `—`（正确）
- 新建数据：后端 `template_id=None` → 前端 `id == null` → 同路径 → 显示 `—`（环路模式）或委派 Tag（委派模式）
- STATUS_LABEL 未扩展：`cancelled` 暂不复用 `failed`，不引入新枚举值

## 6. 风险与回退

| 风险 | 对策 |
|------|------|
| 回写 task.status 时漏某路径 → 状态仍不同步 | 代码审查 + 集成测试覆盖成功 / 失败两路径；手工点一遍 |
| 看板泳道分组按 `task.status`，若改状态时机过早 → 卡片跳列抖动 | 只在「创建→running」「完成→success/failed」两处变，与环路任务同节奏 |
| 委派信息 Tag 过长挤爆工艺列（列宽 220） | `ellipsis: true` 已配置；若 assignee_name 超长可 Tooltip 补充 |
