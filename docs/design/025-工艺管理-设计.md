# 025-工艺管理-设计

> 日期：2026-07-24  
> 分支：`feat/process-management`（建议）  
> 对应需求：`docs/requirements/025-工艺管理-需求.md`

---

## 1. 设计目标

在不推翻现有 Loop Studio 的基础上，把"重复性工作的标准套路"显式建模为**工艺（Process）**，并与学习材料中的 **SDD（规格驱动开发）+ Harness（受控执行链）+ 4 阶 12 步工艺** 思想对齐：

1. **阶段化**：Loop 内的环节按阶段分组，阶段有自己的规范、产物要求、验收标准。
2. **可复用/可裁剪**：工艺模板可内置、可同步、可一键实例化为 Loop；支持按复杂度、风险、环境做有原则的裁剪（如 Superpowers / 4P12S / GienSpec）。
3. **产物化**：每个环节产出什么被显式定义、捕获、留存；形成 `delivery-state`、`repair-log` 等标准交付证据链。
4. **客观门禁**：产物必须按验收标准被评价，评价通过才能流转；不通过则返工；关键节点必须人工确认。
5. **可审计/可度量**：一次工艺实例的每个阶段、环节、产物、门禁、返工都被记录，并为后续指标闭环提供数据。

---

## 2. 已确认关键决策

经 2026-07-24 与需求方确认，以下设计选择已锁定：

| 决策项 | 选择 | 理由 |
|---|---|---|
| 工艺模板与 Loop 关系 | **模板实例化为 Loop** | 复用现有执行引擎、触发器、评审、黑板，改动最小 |
| 文件类产物留存 | **只存路径快照** | 降低 DB 体积，真实文件留在工作目录 |
| AI 门禁评审方式 | **同步调用 LLM** | 流程直观，可复用现有 `auto_review` runtime |
| 首期范围 | **M1：模板 + 阶段** | 先验证工艺模板市场与阶段分组，门禁/产物放到 M2 |

## 3. 核心概念与映射

| 工艺管理概念 | ntd 现有概念 | 说明 |
|---|---|---|
| 工艺模板（Process Template） | 新增 `process_templates` | 只读/版本化的标准套路定义，如 Superpowers / 4P12S / GienSpec |
| 工艺实例（Process Instance） | `loops` + `loop_executions` | 模板被实例化后变成可执行的 Loop |
| 阶段（Phase） | 新增 `loop_phases` | Loop 内环节的聚合，如需求/设计/编码/验证交付 |
| 环节（Link） | `loop_steps` | 已存在；新增阶段、产物、门禁、返工属性 |
| 专家/Skill | `todos.expert_name` / skill 文件 | 绑定到环节的 todo 上执行时注入 |
| 产物（Artifact） | 新增 `loop_step_artifacts` | 文件/文本/URL/JSON 的运行时快照；标准产物如 `delivery-state`、`repair-log` |
| 门禁（Gate） | 新增 `loop_step_execution_gates` | 产物验收的客观评价记录 |
| 返工（Rework） | `loop_step_executions.rework_count` | 失败回退到上游环节并计数，生成 `repair-log` |
| 工艺裁剪/路由 | 新增 `process_templates.tags` / 复杂度字段 | 按复杂度、风险、工作量推荐模板 |

**关键决策**：工艺管理不是独立系统，而是 Loop Studio 的增强。这样：

- 复用触发器、执行器、自动评审、黑板等全部现有能力；
- 现有 Loop 无阶段、无产物也能继续运行；
- 工艺模板只是 Loop 的"结构化来源"。

## 5. 工艺模板定义（YAML Schema）

工艺模板用 YAML 描述，便于在 bundled 仓库中版本管理、人工审阅、Git diff。

```yaml
process:
  name: 4p12s-delivery
  display_name: 标准需求交付工艺
  description: 4 阶 12 步裁剪版：PRD → 故事 → 设计 → 计划 → Tasking → TDD → 测试 → 提交
  category: software
  complexity: standard          # light / standard / complex，用于工艺路由
  version: 1.0.0
limits:
  max_step_executions: 80
  max_total_tokens: 200000
abnormal_handler:
  todo_template: abnormal-handler
  trigger_on: [capped_step, capped_token, failed]
phases:
  - id: requirement
    name: 需求
    spec: |
      先统一输入，再定义如何证明完成。
      输出 PRD，明确功能清单、验收标准、非目标。
    acceptance_criteria: |
      1. PRD.md 存在且包含验收标准章节。
      2. 所有功能点可测试或可验证。
    links:
      - id: req-01
        name: 生成 PRD
        todo_template: write-prd
        expert: product-manager
        skills: [4p12s-prd]
        executor: claudecode
        expected_artifacts:
          - name: PRD
            type: file
            path: docs/requirements/{process_name}-PRD.md
          - name: delivery-state
            type: file
            path: .ntd/delivery-state.md
        gates:
          - name: PRD 存在
            type: artifact_present
            artifact: PRD
          - name: AI 验收评审
            type: ai_criteria_review
            criteria_ref: phase.acceptance_criteria
            min_score: 80
        on_success: next
        on_gate_fail: goto:req-01
        max_rework: 3
      - id: req-02
        name: 人工确认 PRD
        review_type: human
        expected_artifacts: []
        gates:
          - name: 产品负责人审批
            type: human_approval
        on_success: next
        on_gate_fail: goto:req-01
  - id: design
    name: 设计
    ...
```

### 关键约定

- `phase.id` 与 `link.id` 在模板内唯一，用于 `goto` 目标。
- `todo_template` 引用 `todo_templates.name`；实例化时复制为 `kind='step'` 的 todo。
- `{process_name}` 等占位符在实例化时替换。
- `gate_config` 中的 `criteria_ref: phase.acceptance_criteria` 表示取所在阶段的验收标准文本。

## 6. 工艺实例化流程

1. 用户选择模板，调用 `POST /api/v1/bundled/processes/{name}/install`。
2. 后端解析 `process_templates.definition`：
   - 创建 `loops` 行，设置 `process_template_id`；
   - 按 `limits` 设置 `loops.limits_config`；
   - 按 `abnormal_handler` 设置 `loops.abnormal_handler_todo_id`；
   - 为每个 `phase` 创建 `loop_phases`；
   - 为每个 `link`：
     - 查找或创建 `todo`（`kind='step'`，prompt/title/expert/skills 来自 `todo_template` 与 link 覆盖字段）；
     - 创建 `loop_steps`，填入 `phase_id`、`expected_artifacts`、`gate_config`、`max_rework` 等。
3. 返回新 Loop 的 ID，用户可直接在 Loop Studio 查看或触发执行。

## 7. 执行引擎增强

### 7.1 运行时再分层

现有 `LoopRunner` 执行一个环节后做"评分门禁"。新工艺门禁替换为更通用的"门禁引擎"，并与 XXCoder 的 **Harness 受控执行链** 对齐：

```
执行环节 todo
    │
    ▼
捕获产物 (ArtifactCapture)
    │
    ▼
评价门禁 (GateEvaluator)
    │
    ├─ artifact_present
    ├─ ai_criteria_review
    ├─ human_approval
    └─ script_check
    │
    ▼
决定流转 (TransitionResolver)
    ├─ 全通过 → on_success
    └─ 有失败 → on_gate_fail / 返工计数 / repair-log
```

与 Harness Runtime 四阶段的映射：

| Harness 阶段 | ntd 实现 |
|---|---|
| 上下文组装 | `pre_spawn` 渐进加载项目规范、专家、Skill、上一轮结论 |
| Skills 与工具调度 | `loop_steps` 选择对应 `todo`/Skill，调用 `executor_service` |
| 受控执行 | `LoopRunner` 执行环节，捕获产物，运行门禁 |
| 修复与人工升级 | `on_gate_fail` 返工、生成 `repair-log`、人工审批后继续 |

### 7.2 产物捕获（ArtifactCapture）

对每个 `expected_artifact`：

| type | 捕获策略 |
|---|---|
| `file` | 把 `locator` 解析为工作空间相对路径，调用 `std::fs::metadata` 检查存在性；若存在，可读则把前 N 字符存入 `content_text` 快照。 |
| `text` | 从 `execution_record.result` 中按 `marker` 提取；无 marker 时取整个 result。 |
| `url` | 用正则从 result 中匹配第一个 URL。 |
| `json` | 从 result 中提取第一个 JSON 代码块或整段 JSON。 |
| `delivery-state` | 特殊 file 类型：指向 `.ntd/delivery-state.md`，由流程初始化步骤创建并持续更新。 |
| `repair-log` | 特殊 text 类型：当环节失败/返工时，把错误信息、修复动作、人工意见追加到 `.ntd/repair-log.md`。

捕获失败的产物也创建记录，状态为 missing，供 `artifact_present` 门禁识别。

### 7.3 门禁引擎（GateEvaluator）

#### `artifact_present`

- 逻辑：检查同名 `loop_step_artifacts` 是否存在且非 missing。
- 结果：`{"pass": true/false}`。

#### `ai_criteria_review`

- 逻辑：把产物内容 + 验收标准文本注入评审 prompt，调用 LLM 生成结构化 JSON：

```json
{
  "pass": true,
  "score": 85,
  "issues": ["缺少非目标章节"]
}
```

- 实现：复用 `executor_service/auto_review.rs` 的评审模板与解析机制，但目标改为"产物 vs 验收标准"。
- 若 `score >= min_score` 且 `pass=true` 则通过。

#### `human_approval`

- 逻辑：把 `loop_step_execution` 状态置为 `pending_approval`，暂停 Loop；
- 用户调用审批接口后写入 `loop_step_execution_gates` 结果，并继续流转。

#### `script_check`

- 逻辑：在工作空间内执行白名单脚本/命令（如 `cargo clippy -- -D warnings`），根据退出码判断。
- 结果：`{"exit_code": 0, "stdout": "...", "stderr": "..."}`。
- 安全：命令必须来自项目内文件或配置白名单，禁止任意 shell 拼接。

### 7.4 兼容现有 `min_rating`

为向后兼容，把 `loop_steps.min_rating` 隐式转换为一条 `ai_criteria_review` 门禁：

```json
{
  "type": "ai_criteria_review",
  "criteria": "{{todos.acceptance_criteria}}",
  "min_score": "{{min_rating}}"
}
```

### 7.5 返工与最大返工次数

- `TransitionResolver` 发现当前环节门禁失败且 `on_gate_fail` 为 `goto <target_step_id>` 时：
  - 如果目标环节等于当前环节或按 `order_index` 位于当前环节之前，视为返工；
  - 新创建的 `loop_step_execution` 继承前一次的 `rework_count + 1`。
- 当 `rework_count >= max_rework` 时，忽略 `on_gate_fail`，强制按 `end/break` 处理，Loop 终态为 `failed`。

### 7.6 阶段执行记录

- `LoopRunner` 在第一次进入某阶段时创建 `loop_phase_executions`（status=running）。
- 当阶段内最后一个非跳过环节到达终态时，更新阶段 status 为 success/failed/skipped。
- 阶段状态仅用于展示与审计，不参与流转逻辑（流转仍由环节边决定）。

## 8. 内置工艺市场

复用现有 `bundled_sync` + `handlers/bundled.rs` 机制：

1. 在 bundled 仓库中新增 `processes/` 目录；
2. `bundled_sync` 把 `processes/` 同步到 `~/.ntd/bundled/processes/`；
3. 后端在同步完成后扫描 `~/.ntd/bundled/processes/**/*.yaml`，解析并 upsert 到 `process_templates` 表；
4. 前端"工艺库"调用 `GET /api/v1/bundled/processes` 展示列表；
5. 安装时调用 `POST /api/v1/bundled/processes/{name}/install`。

### 内置工艺建议（首期，对应材料工艺裁剪思想）

| 工艺 | 来源思想 | 阶段示例 | 适用场景 |
|---|---|---|---|
| `superpowers-task` | Superpowers（P13） | brainstorming → writing-plans → TDD → code-review → verification → reflect | 小需求、缺陷修复、个人快速任务 |
| `4p12s-delivery` | 4 阶 12 步裁剪（P09–P12） | PRD → 用户故事 → 技术设计 → 验证计划 → Tasking → TDD → API/E2E 测试 → Git 提交 | 常规功能交付 |
| `gienspec-complex` | GienSpec（P14） | Constitution → Specify → Clarify → Plan → Checklist → Tasks → Analyze → Implement → Converge | 复杂系统、重构、强治理项目 |

> 工艺路由原则（P15）：可裁剪的是流程长度，不可裁剪的是质量标准；规格、验证和证据闭环必须保留。

## 11. 安全与权限

- **Workspace 隔离**：所有工艺实例 API 经过 `workspace_guard` 校验；
- **路径安全**：产物路径解析必须使用 `resolve_within_workspace`（禁止 `..`、绝对路径、符号链接逃逸）；
- **脚本白名单**：`script_check` 只能执行项目目录内已存在的脚本文件，或全局配置白名单中的命令；
- **人工审批权限**：仅工作空间成员可审批；
- **AI 评审限额**：`ai_criteria_review` 受 `limits_config.max_total_tokens` 限制，避免 token 爆涨。

## 14. 分阶段实施建议

由于工艺管理涉及 DB、后端、前端、CLI、模板市场，建议分三期落地：

### M1：模板与阶段（可独立交付）

- 新增 `process_templates`、`loop_phases`、`loops.process_template_id`、`loop_steps.phase_id`；

- 前端工艺库 + Loop Studio 阶段分组展示；
- 内置 3 条工艺模板，但仅复用现有 `min_rating` / `human` 门禁，**暂不实现产物与通用门禁引擎**。

### M2：产物与门禁（核心能力）

- 新增 `loop_step_artifacts`、`loop_step_execution_gates`、`loop_phase_executions`、`loop_step_executions.rework_count`；
- 实现 `ArtifactCapture` 与 `GateEvaluator`；

### M3：市场、度量与持续进化

- 工艺使用统计与 Dashboard 卡片（结果 / 过程 / 使用三层指标）；
- 四流闭环：把执行数据反哺为工艺优化和 Skill 进化。
