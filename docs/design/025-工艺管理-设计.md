> 日期：2026-07-24  
> 分支：`feat/process-management`（建议）  
> 对应需求：`docs/requirements/025-工艺管理-需求.md`

---

## 1. 设计目标

在不推翻现有 Loop Studio 的基础上，把"重复性工作的标准套路"显式建模为**工艺（Process）**，并与学习材料中的 **SDD（规格驱动开发）+ Harness（受控执行链）+ 4 阶 12 步工艺** 思想对齐：

1. **阶段化**：Loop 内的环节按阶段分组，阶段有自己的规范、产物要求、验收标准。
2. **可复用/可裁剪**：工艺模板可内置、可同步、可一键实例化为 Loop；支持按复杂度、风险、环境做有原则的裁剪（如 Superpowers / 4P12S / GienSpec）。
3. **产物化**：每个环节产出什么被显式定义、捕获、留存；形成 `delivery-state`、`repair-log` 等标准交付证据链。
4. **客观门禁**：产物必须按验收标准被评价，评价通过才能流转；不通过则返工；关键节点必须人工确认。
5. **可审计/可度量**：一次工艺实例的每个阶段、环节、产物、门禁、返工都被记录，并为后续指标闭环提供数据。

---

## 2. 已确认关键决策

| 决策项 | 选择 | 理由 |
|---|---|---|
| 工艺模板与 Loop 关系 | **模板实例化为 Loop** | 复用现有执行引擎、触发器、评审、黑板，改动最小 |
| 文件类产物留存 | **只存路径快照** | 降低 DB 体积，真实文件留在工作目录 |
| AI 门禁评审方式 | **同步调用 LLM** | 流程直观，可复用现有 `auto_review` runtime |
| 首期范围 | **M1：模板 + 阶段 + 产物捕获 + 基础门禁 + 返工** | 没有产物和门禁，工艺管理只是 Loop 的阶段分组，无法验证 4P12S 每步完成 |
| 模板版本更新 | **快照语义** | 已安装 Loop 保持不变，仅提示新版本可用，保证审计链完整 |

## 3. 核心概念与映射

| 工艺管理概念 | ntd 现有概念 | 说明 |
|---|---|---|
| 工艺模板（Process Template） | 新增 `process_templates` | 只读/版本化的标准套路定义，如 Superpowers / 4P12S / GienSpec |
| 工艺实例（Process Instance） | `loops` + `loop_executions` | 模板被实例化后变成可执行的 Loop |
| 阶段（Phase） | 新增 `loop_phases` | Loop 内环节的聚合，如需求/设计/编码/验证交付 |
| 环节（Link） | `loop_steps` | 已存在；新增阶段、产物、门禁、返工属性 |
| 专家/Skill | `todos.expert_name` / skill 文件 | 绑定到环节的 todo 上执行时注入 |
| 产物（Artifact） | 新增 `loop_step_artifacts` | 文件/文本/URL/JSON 的运行时快照；标准产物如 `delivery-state`、`repair-log` |
| 门禁（Gate） | 新增 `loop_step_execution_gates` | 产物验收的客观评价记录 |
| 返工（Rework） | `loop_step_executions.rework_count` | 失败回退到上游环节并计数，生成 `repair-log` |
| 工艺裁剪/路由 | `process_templates.complexity` / tags | 按复杂度、风险、工作量推荐模板 |

**关键决策**：工艺管理不是独立系统，而是 Loop Studio 的增强。这样：

- 复用触发器、执行器、自动评审、黑板等全部现有能力；
- 现有 Loop 无阶段、无产物也能继续运行；
- 工艺模板只是 Loop 的"结构化来源"。

## 4. ntd 现状与 XXCoder 的差距

### 4.1 已具备的可复用能力

| ntd 现有能力 | 对应 XXCoder 概念 |
|---|---|
| Loop Studio / LoopRunner | Harness Runtime 的「Skills 与工具调度」+「受控执行」 |
| Todo + Expert + Skill 注入 | 上下文组装 |
| Auto Review（`min_rating`） | 质量门禁雏形 |
| Blackboard / Wiki | 渐进式上下文加载 / 资产流 |
| Bundled Sync | 企业资产融合 / 工艺模板市场 |
| Worktree | 受控执行环境 |
| Execution Events + `loop_step_executions` | 审计链底层 |

### 4.2 最大 5 个能力缺口

1. **没有工艺模板层**：Loop 是单个可执行对象，没有来源模板、版本、可裁剪的市场。
2. **`loop_steps` 扁平，没有阶段（Phase）**：无法表达 4P12S 的 P1/P2/P3/P4。
3. **没有产物捕获与通用门禁引擎**：只有 `min_rating` 和人工审批，无法自动校验 PRD.md / design.md / 测试报告。
4. **Skill 调用是文本插入式**：`skills: [4p12s-prd]` 只能提示 AI，不能保证调用、拿不到结构化结果。
5. **没有返工语义与 `repair-log`**：只有死循环检测，没有显式返工计数和修复日志。

### 4.3 会成为包袱的现有设计

| 包袱 | 问题 | 处理策略 |
|---|---|---|
| `loop_steps` 与 `todos` 强耦合 | 每个环节必须创建一个 todo，人工审批/纯门禁环节也要伪造 todo | 短期保留 `todo_id`，长期允许某些 step 类型不绑定 todo |
| Skill 以 `/skill_name` 文本插入 | 调用不可校验、不可追踪 | M1 先文本调用 + 产物提取兜底；M2 再考虑结构化 Skill 入口 |
| `min_rating` 硬编码在 LoopRunner | 扩展为通用门禁会让 LoopRunner 更臃肿 | 拆分为 `GateEvaluator`；`min_rating` 隐式转换为 `ai_criteria_review` 门禁 |
| LoopRunner 已 ~1600 行 | 再加入产物/门禁/返工会超过可维护阈值 | 把"step 执行后的评分-流转"逻辑下沉到新模块 |
| 前端 `LoopFlowGraph` 扁平布局 | 没有 phase 分组概念 | M1 先列表式阶段分组 + 节点色带；M2 再考虑 phase-aware 布局 |
| Blackboard 是 LLM 编辑 Wiki | 不够结构化，程序难读 | `delivery-state` 由系统按 frontmatter 自动维护 |

## 5. 总体改造架构

### 5.1 不变的原则

- **不推翻 Loop Studio**：工艺管理是 Loop 的增强，不是替代。
- **向后兼容**：现有 Loop 零改动继续运行。
- **可裁剪的是流程长度，不可裁剪的是质量标准**：阶段可以少，但产物、门禁、证据闭环必须保留。
- **模板实例化为 Loop**：模板是只读来源，Loop 是可执行快照。

### 5.2 新增后端模块

建议在 `backend/src/services/process/` 下新增运行时引擎：

```
backend/src/services/process/
├── mod.rs                  # 类型与错误定义
├── phase_driver.rs         # 阶段生命周期、loop_phase_executions、delivery-state
├── artifact_capture.rs     # 按 expected_artifacts 捕获产物
├── gate_evaluator.rs       # 门禁编排
├── gates/
│   ├── gate_artifact_present.rs
│   ├── gate_ai_criteria_review.rs   # 复用 auto_review
│   ├── gate_human_approval.rs
│   └── gate_script_check.rs
├── transition_resolver.rs  # 根据门禁结果决定流转
├── rework_tracker.rs       # 返工判定与 rework_count
├── repair_log.rs           # .ntd/repair-log.md 维护
└── delivery_state.rs       # .ntd/delivery-state.md 维护
```

### 5.3 LoopRunner 的最小改动点

不要重写 `LoopRunner`，只替换 **"step 执行完成 → 评分/审批/流转"** 这一段内联逻辑：

```rust
// 改造前（内联在 loop_runner.rs）
let (gate_passed, step_rating, error_msg) = ...;
current_idx = if gate_passed { resolve_next(on_success) } else { resolve_next(on_rating_fail) };

// 改造后
let step_outcome = phase_driver
    .execute_step(ctx, loop_exec, step, step_exec, record_id, last_conclusion)
    .await?;
// LoopRunner 只负责：应用 outcome、更新全局计数器、处理暂停、推进 current_idx
```

### 5.4 与现有机制自然衔接

| 现有机制 | 衔接方式 |
|---|---|
| `min_rating` | 隐式生成一条 `ai_criteria_review` 门禁 |
| `review_type = "human"` | 隐式生成一条 `human_approval` 门禁 |
| `on_success / on_rating_fail` | 保留为默认流转策略；新增 `on_gate_fail` 优先 |
| `blackboard` | 仍在环节通过门禁后更新 |
| `abnormal_handler` | 仍在 loop 终态异常 / 返工超限时触发 |
| `limits_config` | 继续作为全局 step/token 上限 |

### 6.3 关于环节原型表的决策

**推荐新增独立的 `process_step_templates` 表**，不扩展现有 `todo_templates`：

- `todo_templates` 面向用户创建 todo 时的 prompt 片段，字段过轻。
- 工艺环节原型需要 `name / title / prompt / executor / expert_name / skill_names / model / acceptance_criteria`。
- 分离后，用户模板与系统环节原型互不污染。

若 M1 工期紧张，可临时扩展 `todo_templates`（加 `name/executor/expert_name/skill_names/model`），但必须标记为技术债。

## 7. 工艺模板市场与实例化

### 7.1 模板位置

放在 bundled 仓库的 `processes/` 目录，与 `experts/`、`todos/`、`skills/` 平级：

```
bundled-repo/
├── experts/
├── todos/
├── skills/
└── processes/
    ├── software/
    │   ├── 4p12s-delivery.yaml
    │   └── superpowers-task.yaml
    └── migration/
        └── py2java.yaml
```

### 7.2 同步机制

复用 `run_bundled_sync`，新增 `Subdir::Processes`：

```
POST /api/v1/bundled/sync { subdir: "processes" }
    → git_sync::sync_repo
    → import_process_templates_from_bundled
    → 扫描 ~/.ntd/bundled/processes/**/*.yaml
    → 解析、校验、upsert 到 process_templates
```

### 7.3 实例化流程

```
POST /api/v1/bundled/processes/{name}/install { workspace_id }
    → 解析 process_templates.definition
    → create_loop（带 process_template_id + template_version）
    → create_loop_phases
    → 第一遍：为每个 link 创建 todo(kind='step') + loop_step（goto 暂空）
    → 第二遍：解析 goto，把模板 link.id 映射到真实 loop_step.id
    → 安装缺失 skills 到目标执行器
    → 返回 { loop_id }
```

### 7.4 版本更新策略

**快照语义**：工艺模板更新后，已有 Loop 实例保持不变，只记录 `process_template_version`；前端提示"新版本可用"，用户可一键用最新模板创建新 Loop。

## 8. 工艺模板 YAML Schema

```yaml
process:
  name: 4p12s-delivery
  display_name: 标准需求交付工艺
  description: 4 阶 12 步裁剪版：PRD → 故事 → 设计 → 计划 → Tasking → TDD → 测试 → 提交
  category: software
  complexity: standard          # light / standard / complex
  version: 1.0.0
limits:
  max_step_executions: 80
  max_total_tokens: 200000
abnormal_handler:
  todo_template: abnormal-handler
  trigger_on: [capped_step, capped_token, failed]
phases:
  - id: requirement
    name: 需求
    spec: |
      先统一输入，再定义如何证明完成。
      输出 PRD，明确功能清单、验收标准、非目标。
    acceptance_criteria: |
      1. PRD.md 存在且包含验收标准章节。
      2. 所有功能点可测试或可验证。
    links:
      - id: req-01
        name: 生成 PRD
        step_template: write-prd
        expert: product-manager
        skills: [4p12s-prd]
        executor: claudecode
        expected_artifacts:
          - name: PRD
            type: file
            path: docs/requirements/{process_name}-PRD.md
          - name: delivery-state
            type: file
            path: .ntd/delivery-state.md
        gates:
          - name: PRD 存在
            type: artifact_present
            artifact: PRD
          - name: AI 验收评审
            type: ai_criteria_review
            criteria_ref: phase.acceptance_criteria
            min_score: 80
        on_success: next
        on_gate_fail: goto:req-01
        max_rework: 3
      - id: req-02
        name: 人工确认 PRD
        review_type: human
        gates:
          - name: 产品负责人审批
            type: human_approval
        on_success: next
        on_gate_fail: goto:req-01
  - id: design
    name: 技术设计
    ...
```

### 关键约定

- `phase.id` 与 `link.id` 在模板内唯一，用于 `goto` 目标。
- `step_template` 指向 `process_step_templates.name`。
- `{process_name}` 等占位符在实例化时替换。
- `gate_config` 中的 `criteria_ref: phase.acceptance_criteria` 表示取所在阶段的验收标准文本。

## 9. 执行引擎改造

### 9.1 一次环节执行的完整流程

```
LoopRunner 执行 step
    │
    ▼
执行 todo（调用 executor_service）
    │
    ▼
ArtifactCapture::capture_step_artifacts
    ├─ file → 检查 workspace 相对路径
    ├─ text → 从 result 按 marker 提取
    ├─ url  → 正则匹配
    ├─ json → 提取 JSON 块
    └─ delivery-state / repair-log → 特殊维护
    │
    ▼
写入 loop_step_artifacts
    │
    ▼
GateEvaluator::evaluate_gates
    ├─ artifact_present
    ├─ ai_criteria_review（复用 auto_review）
    ├─ human_approval（可能返回 Pending）
    └─ script_check
    │
    ▼
写入 loop_step_execution_gates
    │
    ▼
TransitionResolver::resolve
    ├─ 全通过 → on_success
    └─ 有失败 → on_gate_fail（fallback on_rating_fail）
    │
    ▼
ReworkTracker::track_rework
    ├─ 返工计数 +1
    ├─ 最大返工检查
    └─ RepairLog::append_repair_entry
```

### 9.2 返工判定

- `on_gate_fail = goto:<target_step_id>` 且目标 step 索引 ≤ 当前 step 索引 → 视为返工。
- 新 step_execution 的 `rework_count = predecessor.rework_count + 1`。
- `rework_count >= max_rework` → 强制失败，触发 `abnormal_handler`。

### 9.3 标准产物维护

- `delivery-state`：实例启动、进入新 phase、环节完成时由 `DeliveryState` 自动重写，包含当前阶段、产物清单、门禁结果。
- `repair-log`：门禁失败、返工、人工审批时追加。

## 12. 安全与权限

- **Workspace 隔离**：所有工艺实例 API 经过 `workspace_guard` 校验。
- **路径安全**：产物路径解析必须使用 `resolve_within_workspace`（禁止 `..`、绝对路径、符号链接逃逸）。
- **脚本白名单**：`script_check` 只能执行项目目录内已存在的脚本文件，或全局配置白名单中的命令。
- **人工审批权限**：仅工作空间成员可审批。
- **AI 评审限额**：`ai_criteria_review` 受 `limits_config.max_total_tokens` 限制。
- **Skill 路径安全**：复用 `handlers/skills.rs` 的 `resolve_skill_path_for_read` 防止逃逸。
