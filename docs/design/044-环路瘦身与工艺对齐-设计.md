## 0. 调研背景与设计思考

本节记录方案形成前的完整调研结论与推理过程，说明「为什么这么做」，便于日后回溯决策依据。

### 0.1 现状调研结论

**环路侧（先出现）**：

- 后端体量失控：`handlers/loop_.rs` 3268 行、`services/loop_runner.rs` 2766 行、`db/loop_.rs` 2704 行，远超项目 300 行规范；
- v0 / v1 双套路由并存（注释写明 "keeps both until migration is complete"，但迁移始终未完成）；
- 触发入口多达 7 种：手动触发按钮、cron、webhook、飞书消息、飞书命令、事项完成、标签添加，分别散落在 `loop_trigger.rs` 的 6 个 dispatch 方法 + `loop_scheduler.rs` 的 cron 调度器；
- 人工审批存在新旧两套接口并存：旧评分制 `approve_step_execution`（loop_.rs）与新门禁制 `approve_gate`（process.rs），前端 `StepExecList.tsx` 至今调的仍是旧接口；
- `pending_approval` 是事实上的第 6 种 step_execution 状态，但 entity 注释未列出——说明环路模型已经历多轮打补丁式演进。

**工艺侧（后出现）**：

- 工艺定义（`ProcessDefinition`）以 YAML 文件为唯一权威，DB 只存 `process_templates` 元数据 + `source_path` 索引（需求 038 已把 definition 列迁出数据库）；
- 前端已有完整的 React Flow 可视化编辑器 + Monaco YAML 编辑器 + 双向联动（需求 029 M3~M6），编辑能力远超环路的表单式编辑；
- 安装时 `installer.rs` 把 YAML 实例化为 loops / loop_phases / loop_steps / todo——**环路已经是工艺的实例化产物**，只是系统还假装它可以独立存在；
- 执行链路（loop_runner → phase_driver → gate_evaluator → transition_resolver → 审批续跑）是完全工艺化的，旧评分闸门 `apply_rating_gate` 只是为手工环路保留的兼容路径。

### 0.2 字段差异分析（双轨的证据）

环路表与工艺 YAML 的出入分三类：

1. **YAML 已无对应概念的旧字段**：`loop_steps.min_rating` / `unrated_policy`（旧评分闸门，YAML 已用 gates 取代）、`run_mode`、`skip_on_source_failed`、`loops.webhook_enabled`、`loops.review_template_id`（评审已归环节，需求 033/036）——这些是双轨冗余，删除；
2. **工艺实例的运行时属性**：`loops.status`（enabled/paused 运行开关）、workspace 归属、`process_template_id` + `process_template_version`（来源快照）——YAML 是静态定义不管运行态，这些保留；
3. **安装期的合理快照**：`limits_config`、`abnormal_handler_*`、`gate_config`、`expected_artifacts`、`skill_names` 等 JSON 列——YAML 升级后历史实例不能跟着变，快照是审计链的必要设计，保留。

YAML 有而 DB 丢弃的（phase id、link id 等）仅在安装期用于 goto 映射，属正常设计，无需对齐。

### 0.3 为什么是「降级承载」而不是「删除环路表」

曾考虑更激进的方案：环路执行时直接读 YAML，不再落库。否决理由：

- 工艺 YAML 会被编辑和升级，而执行历史（哪一步、哪个门禁、谁审批的）必须锚定一个不可变的实例快照，否则审计链断裂；
- `loop_executions` / `loop_step_executions` / gates / artifacts 等运行时表全部挂在 loop 实例上，去掉实例层等于重写整个执行层；
- 工艺升级时的 `upgrade` 语义（老实例跑老版本、新任务用新版本）天然依赖实例层。

因此正确定位是：**YAML 管定义，loop 表管实例与运行**——环路不删，只砍掉它越界承担的「定义」和「入口」职责。

### 0.4 关键决策与理由

| 决策点 | 结论 | 理由 |
|---|---|---|
| 存量手工环路 | 直接删除（级联） | 手工环路本就是要淘汰的双轨产物；保留只读会长期拖着两套模型，自动转 YAML 则迁移成本高且质量不可控。用户确认可丢历史 |
| 触发器 | 彻底下线（删表删调度器） | YAML 无触发器概念，7 种触发入口是执行路径分散的根源；唯一入口「创建任务」语义最清晰：人提需求 → 工艺执行 |
| 环路菜单 | 保留只读化 | 执行记录查看、人工审批、看板仍需要一个落点；并入工艺页 Tab 改动大且收益小，后续可再做 |
| 导入导出备份 | 全部删除 | 工艺时代迁移 / 分享由 YAML 文件承担；环路级导入等于绕过工艺创建环路，与 R1 定位直接冲突 |
| 旧评分制审批 | 删除，前端切门禁制 | 两套审批并存是 bug 温床（近期多个审批相关 fix 都源于此）；门禁制语义（通过 / 拒绝 + 门禁记录）比评分制更完整 |
| `loop_tags` | 保留 | 标签是列表筛选维度，与触发器无关；仅 tag_added 触发类型随触发器下线 |
| 历史快照列 | `loop_step_executions.min_rating/rating` 等保留 | 历史记录不可变；且存量手工环路的执行历史随级联删除一并清除后，剩余快照全部来自工艺实例 |

### 0.5 实施顺序的考虑

「先删调用方，再删实现，最后动数据库」是为了让每一步都独立可编译、可验证：

1. 前端删入口 + v0 路由下线——用户感知层先收敛；
2. 后端删 handler / service 实现——此时 DB 列还在，只是无人写；
3. 迁移 v80 删表删列——结构最后定型，避免代码还在写某列时列先没了。

级联删除先于结构变更执行（先清数据再 DROP），是因为删除语句引用的列（如 `process_template_id`）在结构变更后仍必须可用；单事务保证中途失败整体回滚，不留半截状态。

## 1. 总体思路

环路（Loop）从「独立功能」降级为「工艺的运行时承载」：

- **定义层**：工艺 YAML + 可视化编辑器是唯一来源（已有，不变）；
- **实例层**：`loops` / `loop_phases` / `loop_steps` 仅由工艺 install / upgrade 写入，不再有手工写入路径；
- **运行层**：loop_runner 主循环、phase_driver、门禁、审批续跑保持不变；
- **入口层**：唯一执行入口 = 创建任务选择工艺环路。

实施顺序：**先删调用方（前端 + v0 路由），再删后端实现，最后迁移删表删列**，保证每一步都可编译。

## 4. 数据库迁移 v80（`db/migration/v80.rs`）

分两步，顺序不能反（先清数据再动结构，保证删列时不依赖已删行）：

### 4.1 存量手工环路级联删除

对 `process_template_id IS NULL` 的每个 loop id，按外键依赖顺序删除：

1. `loop_step_execution_gates`（经 loop_step_executions → loop_executions 关联）
2. `loop_step_artifacts`（同上）
3. `loop_step_executions`
4. `loop_phase_executions`
5. `loop_executions`
6. `loop_triggers`
7. `loop_tags`
8. `loop_steps`
9. `loop_phases`
10. `loops`

> 用子查询按 loop_id 一批删除，避免逐行循环；全程单事务。

### 4.2 结构变更

- `DROP TABLE loop_triggers`；
- `loops`：`DROP COLUMN webhook_enabled / review_template_id / color / icon`；
- `loop_steps`：`DROP COLUMN min_rating / unrated_policy / run_mode / skip_on_source_failed`。

> SQLite 支持 `DROP COLUMN`（3.35+）。迁移注册到 migration runner，与 v71~v79 风格一致；迁移后跑既有迁移测试。

## 6. 安全反思

- **数据删除风险**：v80 级联删除手工环路是不可逆操作。缓解：迁移前在日志输出将删除的环路数量与 id 清单；迁移单事务，失败整体回滚。
- **越权**：删除的 API 同时删除了对应 handler 权限检查代码，无新增端点，不扩大攻击面；保留端点的 workspace 校验逻辑不动。
- **兼容**：飞书机器人若仍推送消息，webhook 端点删除后返回 404，属预期行为，需在实现总结中注明。

### 7.4 已知的坑（调研发现，别踩）

1. **`pending_approval` 是事实上的第 6 种 step_execution 状态**，但 `entity/loop_step_executions.rs` 注释未列出——删改状态相关代码时以 `loop_runner.rs` 实际写入的字符串为准；
2. **飞书 / webhook 的 handler 里还有调用 dispatch 的地方**，删 `loop_trigger.rs` 方法时必须全局排查调用点，否则编译失败；
3. **`loop_scheduler.rs` 在启动流程中有初始化和配置变更时的 reload 调用**，删文件时一并清理，注意 daemon 启动路径；
4. **installer 写 loop_steps 时目前会写 `min_rating` 等列**，迁移删列后 installer 必须同步停止写这些列，顺序上建议代码改动与迁移在同一 PR；
5. 删除 v0 路由后，检查是否有前端 / 测试 / 文档仍引用 `/api/loops`（不带 v1）的路径；
6. 后端 handler / service / db 三个 loop 文件都近 3000 行，删除时注意关联的 helper 函数是否变成死代码（clippy -D warnings 会报）。
