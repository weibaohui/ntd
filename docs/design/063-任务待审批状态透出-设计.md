# 063-任务待审批状态透出-设计

| 修改人 | 修改时间 | 修改内容 |

对应需求：`docs/requirements/063-任务待审批状态透出-需求.md`（用户已确认 `1a2a3a4b5a`）。

## 1. 总体思路

派生不落库：任务列表接口批量统计每个任务的待审批环节数（复用 NTD-004 口径），随列表项下发；前端三态视图据此展示「待审批」标记，看板增加独立泳道；点击标记经既有 `?tab=exec` 机制进详情执行历史 Tab，并由 `LoopExecutionsPanel` 自动展开首条待审批执行。

不改动 `tasks.status` 状态机，不做数据库迁移。

## 2. 后端改动

### 2.1 `backend/src/db/loop_.rs` — 新增批量统计方法

```rust
/// 按 task 批量统计待审批环节数，返回 task_id → count 映射。
/// 口径与 count_pending_approvals_by_execution_ids 一致（NTD-004）：
/// approval_status='pending' OR status='pending_approval'，两条暂停路径互斥不重复计数。
/// 计数范围是该 task 所有执行（不限最近一次），与 Loop 列表口径对齐。
pub async fn count_pending_approvals_by_task_ids(
    &self,
    task_ids: &[i64],
) -> Result<HashMap<i64, i32>, sea_orm::DbErr>
```

实现：单条 SQL —— `loop_step_executions lse INNER JOIN loop_executions le ON le.id = lse.loop_execution_id`，`WHERE le.task_id IN (...) AND (lse.approval_status='pending' OR lse.status='pending_approval')`，`GROUP BY le.task_id`。空入参直接返回空 map（与既有方法同防御模式）。

### 2.2 `backend/src/handlers/tasks.rs` — `list_tasks` 注入字段

- 在既有 `get_latest_execution_by_task_ids` 批量调用之后，追加一次 `count_pending_approvals_by_task_ids(&task_ids)`（`task_ids` 已收集，复用变量）。
- `build_task_item` 签名追加 `pending_approval_count: i32`，JSON 输出新增 `"pending_approval_count": ...`；无记录任务为 0（`map.get().copied().unwrap_or(0)`）。
- 全程 2 次批量查询，无 N+1。

### 2.3 测试

`db/loop_.rs` 测试模块新增用例（参照既有 `test_count_pending_approvals_by_execution_ids_*` 模式）：
- `test_count_pending_approvals_by_task_ids_aggregates_across_executions`：同一 task 两条执行各 1 条 pending → count=2（验证跨执行累加）
- `test_count_pending_approvals_by_task_ids_covers_both_paths`：`approval_status='pending'` 与 `status='pending_approval'` 各一条 → 均被计入
- `test_count_pending_approvals_by_task_ids_empty_input`：空入参 → 空 map

## 3. 前端改动

### 3.1 `frontend/src/api/bundled.ts` + `components/tasks/constants.tsx`

- `listTasks` 返回类型与 `TaskItem` 均新增 `pending_approval_count?: number`。
- `TASK_LANES` 首部插入 `{ status: 'pending_approval', label: '待审批', color: '#fa8c16' }`。该 status 值为虚拟泳道键，不会出现在 `task.status` 中。
- 新增共享渲染辅助 `renderPendingApprovalTag(count, onClick?)`：红色 Tag + `ExclamationCircleOutlined` + `N 待审批`，与执行历史行内标记同款；`onClick` 存在时表现为可点击（cursor:pointer + stopPropagation 由调用方处理）。

### 3.2 看板 `TasksKanbanView.tsx`

- `groupByLane` 调整：`pending_approval_count > 0` 的任务优先归入 `pending_approval` 泳道，**不再**落入其真实 status 泳道（注释说明取舍：避免一卡两列、看板计数翻倍）。
- `KanbanTaskCard` 头部行（`#id` 旁）渲染待审批 Tag，点击 → `onSelectTask(task.id, 'exec')`。
- 泳道空态文案「暂无待审批任务」沿用既有模式自动成立（`暂无{label}任务`）。

### 3.3 列表 `TasksTableView.tsx`

- `buildColumns` 在「状态」列后插入「待审批」列（width 90，`sorter: makeSorter<TaskItem>('pending_approval_count')` 对齐 054 模式）：`>0` 渲染可点击红色 Tag，否则 `—`。
- `STATUS_FILTER_OPTIONS` 追加 `{ value: 'pending_approval', label: '待审批' }`；过滤逻辑加分支：选中时按 `pending_approval_count > 0` 过滤（而非匹配 `task.status`）。
- 行点击不变；待审批 Tag 点击 `e.stopPropagation()` 后 `onSelectTask(record.id, 'exec')`。

### 3.4 卡片 `TasksCardView.tsx`

- 头部行状态 Tag 旁渲染可点击待审批 Tag。
- `STATUS_FILTER_OPTIONS` 与过滤逻辑同 3.3。

### 3.5 跳转与自动展开

- `TasksPage.tsx`：`handleSelectTask(taskId, tab?)` 追加可选 tab 参数，透传给 URL（`useViewState.showView/replaceUrl` 已支持 `opts.tab`），生成 `/#/tasks?id=123&tab=exec`。三态视图的 `onSelectTask` 签名同步扩展（第二参可选，普通点击不传，行为不变）。
- `TaskDetailTabs.tsx` `ExecHistoryTab` → `LoopExecutionsPanel` 透传新 prop `autoExpandFirstPending?: boolean`（任务详情固定传 true）。
- `loop-studio/executions/index.tsx` `LoopExecutionsPanel`：
  - 新增 prop `autoExpandFirstPending?: boolean`（默认 false，Loop 侧既有调用点不受影响）。
  - 首屏 `loadPage(1)` 成功后，若开启且存在 `pending_approval_count > 0` 的行，取第一条调 `handleExpand(e.id)`。
  - 用 `autoExpandedRef = useRef(false)` 守卫：仅首次触发一次；WebSocket 刷新（`doRefresh`）不再触发自动展开，不打扰用户手动收起。
  - 若第一页无待审批行（分页 5 条限制），不跨页查找（需求 §10 已声明）。

## 4. 影响面与兼容

- 接口仅新增字段，向下兼容；`bundled.listTasks` 仅 TasksPage 一处消费。
- `LoopExecutionsPanel` 新 prop 可选，Loop 详情等既有调用点零改动。
- 看板泳道从 4 列变 5 列，`flex:1 + minWidth:220` 布局自然适配，窄屏横向滚动行为不变。
