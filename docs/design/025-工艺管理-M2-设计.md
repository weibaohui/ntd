## 1. 设计目标

M1 已经把「工艺模板」实例化为 Loop（阶段、环节、产物配置、门禁配置全部落库）。
M2 的目标是让这些配置在 **LoopRunner 运行时真正生效**，并确立 **skill-centric 工艺模型**：

1. 每个环节必须显性化绑定 skill（怎么做、按什么模板做）；
2. 产物位置结构化（`expected_artifacts`），产物内容模板由 skill 承载；
3. 门禁校验引用 skill 自检清单 + 工艺验收标准；
4. 前端把「环节 → skill → 产物 → 门禁」四元组完整展示；
5. 环节执行完成后自动捕获产物；
6. 按配置的门禁逐项评价产物/输出；
7. 门禁结果决定下一步流转（通过 / 返工 / 中止）；
8. 返工时递增 `rework_count`，超过 `max_rework` 强制失败；
9. 阶段生命周期（`loop_phase_executions`）自动维护；
10. 标准产物 `delivery-state` / `repair-log` 自动维护；
11. 提供审计 API、CLI 与前端工艺执行看板。

**非目标**：工艺路由/推荐、模板版本 diff、指标度量、可视化编排器 —— 这些放到 M3。

## 3. 总体架构

### 3.1 新增后端模块

全部放在 `backend/src/services/process/` 下，与 M1 的 `installer.rs` 同目录：

```
backend/src/services/process/
├── mod.rs                  # 已有：类型定义
├── installer.rs            # 已有：模板 → Loop 实例化
├── phase_driver.rs         # 新增：阶段生命周期 + step 执行后总控
├── artifact_capture.rs     # 新增：按 expected_artifacts 捕获产物
├── gate_evaluator.rs       # 新增：门禁编排与执行
├── gates/
│   ├── mod.rs              # Gate trait / 错误类型
│   ├── artifact_present.rs
│   ├── ai_criteria_review.rs
│   ├── human_approval.rs
│   └── script_check.rs
├── transition_resolver.rs  # 新增：根据门禁结果决定下一步
├── rework_tracker.rs       # 新增：返工判定与 rework_count
├── delivery_state.rs       # 新增：.ntd/delivery-state.md 维护
└── repair_log.rs           # 新增：.ntd/repair-log.md 维护
```

### 3.2 LoopRunner 的最小改动

不推翻 `loop_runner.rs`，只把 **4h「评分闸门」+ 4l「确定下一步」** 这一段替换为调用 `PhaseDriver`。

改造前：

```rust
let (gate_passed, step_rating, error_msg) = if step_status == "success" && step.min_rating.is_some() {
    // ... apply_rating_gate 内联逻辑 ...
} else {
    (step_status == "success", None, None)
};
// ...
current_idx = if gate_passed {
    self.resolve_next(step, &step.on_success, &step_id_to_idx, idx)
} else {
    self.resolve_next(step, &step.on_rating_fail, &step_id_to_idx, idx)
};
```

改造后：

```rust
// step 已执行完成，进入工艺驱动阶段
let outcome = phase_driver
    .execute_step(
        ctx,
        loop_,
        loop_execution_id,
        step,
        step_exec,
        record_id,
        &all_steps,
        idx,
        last_output.as_deref(),
    )
    .await?;

// LoopRunner 只负责：应用 outcome、更新计数器、处理暂停、推进 current_idx
gate_passed = outcome.gate_passed;
step_rating = outcome.rating;
error_msg = outcome.error_message;
current_idx = outcome.next_idx;

if outcome.paused {
    return Ok(LoopRunOutcome::Paused);
}
```

`apply_rating_gate` 方法保留但标记为 deprecated，后续 M3 移除；M2 把它内部逻辑迁移到 `gate_ai_criteria_review.rs`。

### 3.3 一次环节执行的完整流程

```
LoopRunner 执行 todo 完成（execution_record 已生成）
    │
    ▼
PhaseDriver::execute_step
    │
    ├─ ArtifactCapture::capture_step_artifacts
    │     ├─ file  → 检查 workspace 相对路径是否存在
    │     ├─ text  → 从 execution_record.result 按 marker 提取
    │     ├─ url   → 正则匹配
    │     ├─ json  → 提取 JSON 块
    │     └─ delivery-state / repair-log → 特殊维护
    │
    ├─ 写入 loop_step_artifacts
    │
    ├─ GateEvaluator::evaluate_gates
    │     ├─ artifact_present
    │     ├─ ai_criteria_review（复用现有 auto_review runtime）
    │     ├─ human_approval（返回 Pending，暂停 Loop）
    │     └─ script_check
    │
    ├─ 写入 loop_step_execution_gates
    │
    ├─ TransitionResolver::resolve
    │     ├─ 全通过 → on_success
    │     └─ 有失败 → on_gate_fail（fallback on_rating_fail）
    │
    ├─ ReworkTracker::track_rework
    │     ├─ 目标 step 索引 ≤ 当前索引 → rework_count + 1
    │     └─ 最大返工检查
    │
    └─ DeliveryState / RepairLog 维护
```

### 3.4 Skill-centric 工艺模型

M2 采用「**结构化四元组 + skill 内容模板**」的混合模型：

| 元素 | 是否结构化 | 内容来源 | 作用 |
|------|-----------|---------|------|
| 环节（Step/Link） | ✅ 结构化 | 工艺模板 YAML `phases[].links[]` | 定义做什么 |
| 使用哪些 skill | ✅ 结构化 | `link.skills: [...]` | 定义怎么做、按什么模板做 |
| 产物位置 | ✅ 结构化 | `link.expected_artifacts[]` | 定义产出物放哪里 |
| 怎么校验 | ✅ 结构化 | `link.gates[]` | 定义门禁规则 |
| 产物/环节具体内容 | ❌ 由 skill 承载 | `bundled-repo/skills/*.md` | 定义内容结构、必须/禁止、输出格式 |

**为什么这样设计**：

- 工艺差异大（PRD、设计文档、测试计划结构完全不同），硬套统一 schema 会束缚 AI；
- 但「用哪个 skill、产物放哪、怎么校验」必须管住，否则不是工艺而是自由发挥；
- skill 文件本身就是「活的模板」，既能规定章节、必须/禁止、输出格式，又能让 AI 智能推理。

**工艺配套 skill 的内容规范**（建议强制）：

```markdown
# Skill: write-prd

## 目标
本环节必须完成 PRD 编写。

## 必须包含
1. 背景与目标
2. 功能清单（逐条可验证）
3. 验收标准
4. 非目标
5. 边界与约束

## 禁止
- 不要写实现细节
- 不要写代码

## 输出产物
- 文件：docs/requirements/{process_name}-PRD.md
- frontmatter 必须包含 title, version

## 自检清单
- [ ] 每个功能点都能回答"怎么验证"
- [ ] 验收标准可量化
- [ ] 非目标明确
```

**工艺约定可复用**：

阶段级规范 `phase.spec` / `phase.acceptance_criteria` 支持两种写法：

1. inline 文本（适合简单工艺）；
2. 引用外部 markdown 文件（适合多工艺共用同一套规范）：

```yaml
phases:
  - id: requirement
    name: 需求
    spec_ref: bundled://processes/conventions/requirement-phase-spec.md
    acceptance_criteria_ref: bundled://processes/conventions/requirement-acceptance-criteria.md
```

**skill 依赖检查**：

工艺模板安装时（`installer.rs`），必须检查 `link.skills` 中引用的 skill 文件是否已存在于 `bundled-repo/skills/` 并已同步到本地。缺失时：

- 安装失败并返回明确错误（推荐，避免运行时才发现 skill 不存在）；
- 或自动把缺失 skill 一并安装（如果 skill 也包含在工艺包内）。

这样保证工艺的 skill 依赖在实例化前就已经满足，不会在执行阶段因缺少 skill 而失败。

### 3.5 前端必须显性化展示四元组

工艺库详情页、Loop Studio 详情页、工艺执行看板，都必须能清晰展示：

```
环节：生成 PRD
├── 使用 skill：4p12s-prd, prd-template
├── 产物：
│   └── PRD → docs/requirements/{process_name}-PRD.md
├── 门禁：
│   ├── PRD 存在 [artifact_present]
│   └── 符合 PRD 规范 [ai_criteria_review]
└── 流转：
    ├── 通过 → 下一步
    └── 失败 → 返工到本环节
```

这样用户才能一眼看到「这个工艺管了什么、每个环节必须做什么、产物在哪、怎么校验」。

## 4. 核心模块设计

### 4.1 PhaseDriver

职责：step 执行完成后，协调产物捕获、门禁、流转、返工、阶段状态、标准产物维护。

```rust
pub struct PhaseDriver;

pub struct StepOutcome {
    pub gate_passed: bool,
    pub rating: Option<i32>,
    pub error_message: Option<String>,
    pub next_idx: Option<usize>,
    pub paused: bool,
}

impl PhaseDriver {
    pub async fn execute_step(
        &self,
        ctx: &LoopRunnerCtx,
        loop_: &loops::Model,
        loop_execution_id: i64,
        step: &loop_steps::Model,
        step_exec: &loop_step_executions::Model,
        record_id: i64,
        all_steps: &[loop_steps::Model],
        current_idx: usize,
        last_output: Option<&str>,
    ) -> Result<StepOutcome, String>;
}
```

执行步骤：

1. 解析 `expected_artifacts` JSON；
2. 调用 `ArtifactCapture`；
3. 调用 `GateEvaluator`；
4. 根据门禁结果调用 `TransitionResolver`；
5. 调用 `ReworkTracker` 计算 `rework_count`；
6. 更新 `loop_step_executions`（status / rating / error_message / rework_count）；
7. 更新阶段状态 `loop_phase_executions`；
8. 更新 `delivery-state.md` / `repair-log.md`；
9. 如果 `human_approval` 返回 pending，设置 `paused=true`。

### 4.2 ArtifactCapture

产物捕获分两层：

1. **按 `expected_artifacts` 捕获**：知道产物应该叫什么、放在哪；
2. **按 skill 输出格式提取**：知道产物内容应该按什么结构组织。

产物类型：

| type | 定位符 | 捕获逻辑 |
|------|--------|---------|
| `file` | `path` / `locator` | `resolve_within_workspace` 后检查文件是否存在；存在则记录路径快照；同时可读取内容用于后续校验 |
| `text` | `locator`（marker） | 从 `execution_record.result` 中按 marker 提取；skill 输出格式应规定 marker |
| `url` | `locator`（regex，可选） | 从结果中正则匹配第一个 URL |
| `json` | `locator`（path/query，可选） | 提取 ```json ... ``` 块或整段 JSON |
| `delivery-state` | `path=.ntd/delivery-state.md` | 由 `DeliveryState` 模块维护，不直接捕获 |
| `repair-log` | `path=.ntd/repair-log.md` | 由 `RepairLog` 模块维护，不直接捕获 |

**与 skill 联动**：

- 执行器完成 todo 后，`ArtifactCapture` 同时读取本次 step 使用的 `skill_names`；
- 解析 skill 文件中的「输出产物」章节，和 `expected_artifacts` 交叉验证；
- 若 skill 要求文件必须包含特定 frontmatter 或 marker，可提前写入 `loop_step_artifacts.content_text` 供门禁使用。

安全：所有 `file` 路径必须经 `resolve_within_workspace` 校验，禁止 `..`、绝对路径、符号链接逃逸。

写入表：`loop_step_artifacts`（`loop_step_execution_id`, `name`, `artifact_type`, `locator`, `content_text`, `captured_at`, `captured_by=record_id`）。

同时建议记录本次 step 使用的 skill 名称到 `loop_step_executions` 的扩展字段或 `loop_step_artifacts.captured_by`，方便审计链路追溯。

### 4.3 GateEvaluator

门禁类型：

| type | 说明 | 结果 |
|------|------|------|
| `artifact_present` | 检查指定产物名是否已捕获 | passed / failed |
| `ai_criteria_review` | 复用现有 `auto_review` runtime，按 acceptance_criteria 评审 | score + pass/fail |
| `human_approval` | 暂停 Loop，等待人工审批 | pending → passed/failed |
| `script_check` | 执行项目内已存在的脚本/白名单命令 | passed / failed |

门禁配置来源：

- `loop_steps.gate_config` JSON 数组；
- 兼容现有 `min_rating`：若 `gate_config` 为空但 `min_rating` 有值，隐式生成一条 `ai_criteria_review`；
- 兼容现有 `review_type=human`：若 `review_type=human` 且未显式配置 human_approval 门禁，隐式生成一条。

**与 skill 联动（`ai_criteria_review`）**：

AI 评审的 prompt 应自动注入：

1. 环节对应 skill 文件中的「自检清单」；
2. 阶段级 `acceptance_criteria`；
3. 环节级 `acceptance_criteria`；
4. 被评审的产物内容。

这样 AI 评审就不是自由打分，而是在验证「是否按 skill 要求 + 工艺验收标准执行」。

示例 prompt 拼接：

```
请根据以下要求评审产物 {artifact_name}：

# skill 自检清单
{skill_self_check_list}

# 阶段验收标准
{phase_acceptance_criteria}

# 产物内容
{artifact_content}

请给出 pass/fail、score(0-100)、issues 数组。
```

门禁结果写入：`loop_step_execution_gates`。

### 4.4 TransitionResolver

输入：门禁结果集合、当前 step、`on_success` / `on_gate_fail` / `on_rating_fail`。

规则：

1. 所有 required 门禁 passed → 走 `on_success`；
2. 任一 required 门禁 failed / pending 导致失败：
   - 优先走 `on_gate_fail`；
   - 若 `on_gate_fail` 为默认/未配置，fallback 到 `on_rating_fail`；
3. `next` / `goto:<step_id>` / `end` / `break` / `skip` 语义保持不变。

### 4.5 ReworkTracker

返工判定：

- `on_gate_fail` 或 fallback 后的策略为 `goto:<target_step_id>`；
- 且 `target_idx <= current_idx`；
- 则视为返工。

处理：

- 新 step_execution 的 `rework_count = predecessor.rework_count + 1`；
- `rework_count >= max_rework` → 强制失败，不再跳转，触发 abnormal_handler；
- 调用 `RepairLog::append_repair_entry`。

### 4.6 DeliveryState / RepairLog

两个文件都位于工作空间 `.ntd/` 目录下：

- `delivery-state.md`：当前阶段、已捕获产物清单、各门禁结果、当前状态；
- `repair-log.md`：每次返工/门禁失败/人工审批拒绝的条目（时间、环节、原因、 rework_count）。

更新时机：

- `delivery-state`：step 完成、进入新 phase、Loop 终态时重写；
- `repair-log`：门禁失败导致返工、人工审批拒绝、达到 max_rework 时追加。

```bash

# 查看工艺实例审计

```

### 6.3 与现有审批接口的兼容

现有人工审批 API（如果有）审批后调用 `LoopRunner::resume_loop_execution`。M2 需要：

- 审批接口同时更新对应的 `loop_step_execution_gates` 记录；
- `resume_loop_execution` 不再自己重新评分，而是直接读取 gate 结果并继续。

## 8. 安全设计

1. **路径安全**：`artifact_present` / `script_check` / `delivery-state` / `repair-log` 的所有路径解析必须走 `resolve_within_workspace`，禁止目录遍历。
2. **脚本白名单**：`script_check` 只能执行项目目录内已存在的脚本文件，或全局配置白名单中的命令；禁止任意 shell 命令注入。
3. **Workspace 隔离**：所有新增 API 经过 `workspace_guard` 校验。
4. **Token 限额**：`ai_criteria_review` 受 `limits_config.max_total_tokens` 约束。

| `gate_evaluator` | 全通过、部分失败、required vs optional、隐式 min_rating 映射 |
| `transition_resolver` | next/goto/end/break/skip、on_gate_fail 优先 |
| `rework_tracker` | 上游跳转计返工、下游跳转不计、max_rework 触发失败 |
| `delivery_state` / `repair_log` | 文件生成 frontmatter、追加条目 |

### 9.2 集成测试

- 安装工艺模板 → 触发执行 → 验证产物捕获、门禁记录、返工流转；
- 人工审批接口 → 验证状态变更与 Loop 继续；
- 审计 API → 验证阶段/环节/产物/门禁/返工完整链路。

### 9.3 前端测试

- Playwright：工艺执行看板渲染、门禁状态展示、人工审批按钮。

## 10. 实施顺序建议

按依赖顺序分 5 批实现，每批可独立测试：

| 批次 | 内容 | 验证方式 |
|------|------|---------|
| 1 | `ArtifactCapture` + `loop_step_artifacts` 写入 | 单元测试 + 跑一个工艺看 DB |
| 2 | `GateEvaluator`（artifact_present / script_check / ai_criteria_review） | 单元测试 |
| 3 | `TransitionResolver` + `ReworkTracker` + `loop_step_executions.rework_count` | 单元测试 + 集成测试 |
| 4 | `PhaseDriver` 接入 `LoopRunner` + `human_approval` 暂停/恢复 | 跑完整 superpowers-task 工艺 |
| 5 | `DeliveryState` / `RepairLog` + 审计 API/CLI + 前端看板 | Playwright + CLI 验证 |

## 11. 风险与回退

| 风险 | 处理 |
|------|------|
| 改造 LoopRunner 引入回归 | 保留旧路径：无 phase/artifact/gate 的旧 Loop 走兼容逻辑 |
| AI 门禁不稳定导致反复返工 | 可配置 min_score、保留人工审批兜底 |
| script_check 安全风险 | 白名单 + 路径校验，首期只支持项目内已存在脚本 |
| 产物捕获依赖 AI 输出格式 | 提供多种提取策略，允许手动补充 |
