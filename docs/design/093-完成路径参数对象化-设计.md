## 1. 现状与证据（executor_service 完成路径）

参数穿透链：`SpawnRuntime`/`SpawnContext` 已经聚合了全部字段，但下游函数仍逐字段解包传递：

| 函数 | 参数数 | 实参来源 |
|------|-------|---------|
| `completion.rs finalize_normal_completion` | **19** | 调用点逐字段 `ctx.xxx.clone()`（spawn_lifecycle.rs:663） |
| `completion.rs emit_completion_events` | 15 | 上者内部展开 |
| `completion.rs handle_timeout_branch` | 14 | `run_timeout_path` 逐字段传（SpawnRuntime 全有） |
| `completion.rs handle_cancellation_branch` | 12 | `run_cancellation_path` 逐字段传（SpawnRuntime 全有） |
| `spawn_lifecycle.rs handle_spawn_failure` | 12 | `try_spawn_executor_child` 逐字段传（SpawnRuntime 全有） |
| `spawn_lifecycle.rs run_cancellation_path / run_timeout_path` | 17 | `dispatch_*` 逐字段传；且 dispatch_* 与 run_* 一一对应互为壳（Middle Man） |

## 2. 设计

### C1：新增两个参数对象（`executor_service/types.rs`）

```rust
/// 执行终态结果三元组：success/exit_code/result_str 总是结伴出现（Data Clump）
pub(crate) struct CompletionOutcome {
    success: bool,
    exit_code: i32,
    result_str: String,
}

/// select! 终态后 kill+drain 所需的进程句柄簇（5 个参数总一起传递）
pub(crate) struct ProcessTeardown<'a> {
    child: &'a mut command_group::AsyncGroupChild,
    stdout_task: Option<tokio::task::JoinHandle<()>>,
    stderr_task: Option<tokio::task::JoinHandle<()>>,
    log_flusher: std::sync::Arc<crate::log_flusher::LogFlusher>,
    flush_timer: tokio::task::JoinHandle<()>,
}
```

### C2：签名收窄（纯机械，无逻辑改动）

| 函数 | 新签名 |
|------|--------|
| `finalize_normal_completion` | `(ctx: &SpawnContext, outcome: CompletionOutcome)`，19→2 |
| `emit_completion_events` | `(ctx: &SpawnContext, outcome: &CompletionOutcome, duration_secs: i64, total_tokens: i64)`，15→4 |
| `handle_cancellation_branch` | `(runtime: &SpawnRuntime)`，12→1 |
| `handle_timeout_branch` | `(runtime: &SpawnRuntime)`，14→1（`format_timeout_secs(execution_timeout_secs)` 移入函数内） |
| `handle_spawn_failure` | `(runtime: &SpawnRuntime, error: std::io::Error)`，12→2 |
| `run_cancellation_path` / `run_timeout_path` | `(teardown: ProcessTeardown, runtime: &SpawnRuntime)`，17→2；`dispatch_*` 壳函数内联删除（Remove Middle Man） |

### C3：删除全部 6 处失效的 `#[allow(clippy::too_many_arguments)]`

参数对象化后这些压制不再必要，让 clippy 恢复对该路径的守卫能力。
6 处构成（评审后审计口径）：原 commit 删 3 处（`dispatch_cancellation`/`dispatch_timeout`
两个壳上的随壳删除 + `handle_cancellation_branch` 上 1 处）；CodeRabbit #1008 评审后
补删残留 3 处（`handle_timeout_branch`/`finalize_normal_completion`/`emit_completion_events`，
塌缩后参数数 1~4，远低于 clippy 阈值 7）。其余 4 处 allow（`spawn_flush_worker`/
`handle_flush_msg`/`maybe_run_auto_review`/`dispatch_outcome`）参数仍多，属有效压制，不在本批。

## 3. 不做的事（范围边界）

- `db/usage.rs` 的 `create_usage_daily_stat`（16 参）/ `replace_daily_stats_for_date`（14 参）是另一个独立簇（usage 统计写入），候选后续 PR 做 `DailyStatRow` 参数对象；
- `message_debounce.rs` 的 12/10 参函数同理留待后续；
- SpawnContext/SpawnRuntime 两个结构体本身不合并（生命周期与字段集不同，合并是过度设计）。

## 4. 影响模块

`executor_service/{types.rs, completion.rs, spawn_lifecycle.rs}` 三个文件。纯签名重构，无逻辑变化。

## 5. 验证方案

1. `cd backend && cargo clippy --all-targets -- -D warnings` 零告警（删 allow 后仍零告警即证明参数数达标）；
2. `cd backend && cargo test`：executor_service 区（含 NTD-012 回归与完成路径覆盖）全过；
   全量口径为 1634 通过 / 1 失败——失败项 `git_sync` 属预存量环境问题
   （本机 git 版本过老不支持 `init -b`，main 上同样失败），与本批次无关；
3. 假执行器端到端冒烟（同 B2 方法）：任务跑通 + Finished 事件字段完整（duration/tokens/result）。

## 6. 安全反思

纯参数传递结构变化；字段来源不变（同一 runtime/ctx）；无接口/行为变化。
