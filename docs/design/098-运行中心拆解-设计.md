# 098 - 运行中心拆解：视图归位各菜单

## 1. 背景

`097` 把独立「看板」菜单改名为「运行中心」（todo 看板归位事项、清理 memorial 命名）。用户进一步要求：**运行中心本身也该拆解**，内容归位到各菜单。

调查结论（RunningBoard vs TodoCenterCardView）：
- 两者重叠度**中低**——数据对象不同（执行记录 vs todo 定义），是「定义 vs 执行」的正交分工。
- 运行视图独有价值：实时 WS、评审流水线列、执行粒度、单执行日志 Drawer。
- 结论视图 = 「最近 N 小时已完成 todo 瀑布流」，与事项 card + `statusFilter=completed` 重叠高。

用户在三个方案中选了 **B（全归事项）**：接受事项 4 态、执行卡与定义卡混置、评审流水线失去专属视角的代价，换取菜单精简。

## 2. 方案 B（已确认）

| 视图 | 去向 | 形态 |
|---|---|---|
| 运行视图 (RunningBoard) | **事项菜单** 第 4 态 `running` | 复用 RunningBoard，6 列执行监控 |
| 环路视图 (LoopKanban) | **环路菜单** 加 `kanban` 态 | 复用 LoopKanban，8 列执行历史 |
| 结论视图 (conclusion) | **删除** | 能力由事项 card + 已完成筛选覆盖 |
| OpsCenter（运行中心菜单） | **删除** | LeftRail 去「运行中心」，View 去 `ops`，BoardMode 类型整个移除 |

最终菜单：
```
事项   card | list | kanban | running   ← 4 态
环路   list | kanban                       ← kanban 新增（复用 LoopKanban）
（运行中心菜单消失）
```

## 3. 接入点与设计决策

### 3.1 事项 running 态（复用 RunningBoard）

`RunningBoard` props：`{ searchText?: string; hours?: number }`，**受控**；自带统计栏（含刷新按钮）+ 6 列 + 实时 WS + Record Drawer，**不自带搜索框/时间窗**。

**决策 A——running 态顶栏**（推荐 A1）：
- **A1（推荐）**：running 态 `TodoListHeader` 精简为「Segmented + 新建」（与 kanban 态一致），`<RunningBoard />` **不传 props**（全量执行记录，靠自带统计栏 + 刷新 + 实时 WS）。理由：running 的 job 是「看现在跑什么」，全量 + 实时足够；与 kanban 态精简一致；避免 TodoListHeader 搜索/刷新与统计栏重复。
- A2：TodoListHeader 在 running 态提供搜索 + 时间窗传给 RunningBoard——但与统计栏的刷新重叠，层次冗余。

### 3.2 环路 kanban 态（复用 LoopKanban）⚠️ 维度不同

`LoopKanban` 受控：`searchText/hours/onSearchChange/onHoursChange/onOpenTodo`。

**关键问题**：环路菜单的 `list` 态是 **loop 定义管理**（table，`listLoops`），而 `kanban` 态（LoopKanban）是 **loop 执行历史**（8 列，`useLoopExecutions`）。**两者数据维度不同**——切换 list/kanban 看到的是不同对象（定义 vs 执行），不像 tasks/todos 的 list/kanban 是「同数据不同形态」。

**决策 B——维度差异的处理**（推荐 B1）：
- **B1（推荐）**：Segmented 选项标注维度差——`列表(定义)` / `看板(执行)`，让用户预期切换会换数据维度。kanban 态 PageCard 标题用「环路 · 执行历史」。
- B2：环路菜单只加「loop 定义的看板」（按启停/工艺分组），不复用 LoopKanban——但需新组件，且 LoopKanban（执行历史）就无处可去，违背「把环路视图放回去」。
- B3：环路 kanban 态用 LoopKanban 但不标注——用户切换会困惑（数据突变）。

**LoopKanban 接入**：LoopListPage kanban 态需提供 searchText/hours/onOpenTodo。LoopListHeader 现有搜索；需补时间窗（TimeRangeSegmented）+ onOpenTodo（跳事项详情，复用现有 pushUrl）。

### 3.3 conclusion 删除的影响

conclusion = 最近 N 小时已完成 todo 瀑布流（带时间窗）。事项 card 有 `statusFilter=completed` 但**无时间窗**（看全部已完成）。

**决策 C——时间窗丢失**（推荐 C1）：
- **C1（推荐）**：接受能力降级。删 conclusion，用户用「事项 card + 已完成筛选」看完成态。如后续需要「最近 N 小时」时间窗，再给 card 视图加（独立小改）。
- C2：删 conclusion 同时给 card 加时间窗——扩大本 PR 范围。

### 3.4 OpsCenter 拆解

- 删 `OpsCenter.tsx`（及对 `RunningBoard`/`LoopKanban` 的 import；两子组件本身保留，改由事项/环路菜单引用）。
- `useViewState.ts`：`View` 联合去 `'ops'`；`BoardMode` 类型 + `ALL_BOARD_MODES` + `boardMode` state + 3 处 fallback + `getInitialBoardMode` + `syncStateFromOptions/syncFromHash` 里 mode 处理 **整体移除**（无 OpsCenter 后无 boardMode 概念）；`NavOpts.mode` 字段删；`VIEW_TO_NAV_KEY` 去 ops。
- `LeftRail.tsx`：去「运行中心」菜单项 + `LeftRailKey` 去 `'ops'`。
- `App.tsx`：lazy import 去 `OpsCenter`；`handleRailSelect` 去 `key==='ops'`；视图分发去 `activeView==='ops'` 分支。
- `onboarding/concepts.tsx`：「运行中心」节点删除（或改指事项 running 态，但 onboarding 图语义会变，倾向删除该节点 + execution→ops 连线）。
- 帮助：`ops.md` 删除；`board-*.md`（运行中心功能文档集）迁移/精简——running 相关迁到事项、loop_kanban 相关迁到环路、其余删。

## 5. 风险

- **事项 4 态偏多**：card/list/kanban/running，Segmented 横向空间紧。缓解：running 用差异化图标（`ThunderboltOutlined`）+ tooltip。
- **执行卡与定义卡混置**：事项 running 态的执行记录卡（同 todo 多张）与 card/kanban 的 todo 定义卡心智不同。缓解：running 态 PageCard 副标题标注「执行记录维度」。
- **环路 list/kanban 维度跳变**：见决策 B，靠 Segmented 标注缓解。
- **conclusion 时间窗丢失**：见决策 C，接受降级。
- **URL 失效**：`/#/ops` 失效（fallback 到事项）；`?mode=running|loop_kanban|conclusion` 全失效。

097 的 **OpsCenter 改名部分会被 098 覆盖**（OpsCenter 删除）。为避免 097 白做 OpsCenter 改名：

- **推荐**：先 merge #1020（097），098 在 main 之上新分支做。097 的看板归位 + 命名清理独立有价值；098 删 OpsCenter 时，097 的 memorial→ops 命名清理在 098 后大部分随 OpsCenter 一起消失（无害）。
- 备选：暂停 #1020，098 直接在 main 重做（含看板归位 + 拆解），关闭 #1020——但 #1020 已 review 完成丢弃可惜。
