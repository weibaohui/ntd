## 1. 概述

自动评审当前存在两条并行路径（todo 级和 step 级），共享相近的执行逻辑但 prompt 解析策略不同，且通过 `min_rating.is_some()` 相互耦合。此设计将两条路径统一为单一入口，使 prompt 三级回退（环节内联 → 环路模板 → 默认）在统一位置实现，消除 `min_rating` 对评审触发的耦合。

基于需求：`docs/requirements/034-自动评审路径统一-需求.md`。

## 2. 现状分析

### 2.1 评审触发流程（当前）

## 3. 总体设计

### 3.1 统一评审路径

评审执行统一在 `executor_service/auto_review.rs` 中进行，`maybe_run_auto_review` 作为唯一入口：

```
todo 执行完成
  │
  └→ finalize_normal_completion
       │
       └→ maybe_run_auto_review
            │
            ├─ 非 loop_stage → run_auto_review_inner（无 step 上下文，用默认模板）
            │
            └─ loop_stage →
                 │ 查出 step.review_prompt + loop.review_template_id
                 │
                 └→ run_auto_review_inner（带 step 上下文）
                      │
                      ├─ step.review_prompt 非空  → 用它作为模板正文
                      ├─ 否则 loop.review_template_id → 查 review_templates 表
                      └─ 否则 → 默认模板（全局默认行）
                      │
                      └→ 执行评审实例 → 轮询 → 写回评分

loop_runner 继续
  │
  ├→ wait_for_step_finish（此时评分已在 DB）
  │
  ├→ [Path A] 工艺步骤
  │    │
  │    ├→ 预检查：❌ 移除（L799-820 整段删除）
  │    │
  │    └→ phase_driver::execute_step
  │         └→ gate_evaluator（评分已在 DB → 正常门禁判定）
  │
  └→ [Path B] 旧风格步骤
       └→ apply_rating_gate（评分已在 DB → 短路为纯门禁检查）
```

### 3.2 需要改动的边界

#### `maybe_run_auto_review`（completion.rs:844）

**当前行为**（简化伪码）：
```rust
async fn maybe_run_auto_review(..., trigger_type) {
    if trigger_type == "auto_review" { return; }
    if trigger_type.starts_with("loop_stage") {
        if let Ok(Some(step)) = db.find_loop_step_by_todo_id(todo_id).await {
            if step.min_rating.is_some() { return; }  // ← 移除
        }
    }
    run_auto_review(...).await;
}
```

**改后行为**：
```rust
async fn maybe_run_auto_review(..., trigger_type) {
    if trigger_type == "auto_review" { return; }
    
    // 对于环路步骤，查出 step/loop 上下文，用于 prompt 三级回退
    let (step_review_prompt, loop_review_template_id) = if trigger_type.starts_with("loop_stage") {
        if let Ok(Some(step)) = db.find_loop_step_with_loop_review_template(todo_id).await {
            (step.review_prompt, step.loop_review_template_id)
        } else {
            (None, None)
        }
    } else {
        (None, None)
    };
    
    run_auto_review_with_context(..., step_review_prompt, loop_review_template_id).await;
}
```

关键改动：
1. 移除 `min_rating.is_some()` 提早返回——所有 loop 步骤都走统一评审
2. 查出 step 的 `review_prompt` 和其所属 loop 的 `review_template_id`
3. 传给 `run_auto_review_inner` 使用

#### `run_auto_review_inner`（auto_review.rs:140）

新增参数 `step_review_prompt: Option<String>` 和 `loop_review_template_id: Option<i64>`。

```rust
async fn run_auto_review_inner(
    ..., 
    step_review_prompt: Option<String>,
    loop_review_template_id: Option<i64>,
) -> Result<(), String> {
    let original = load_original_todo(&db, todo_id).await?;
    if !should_review_todo(&original) { ... return; }
    let record = load_and_validate_record(...).await?;
    
    // 统一模板解析：步骤内联 → 环路 → 默认
    let resolved = resolve_review_template(
        &db, step_review_prompt.as_deref(), loop_review_template_id
    ).await?;
    let (template_prompt, owning_id, owning_name) = resolved;
    
    // 合成评审 prompt（机制不变，只是使用解析后的模板正文）
    let composed_prompt = compose_review_prompt_advanced(
        &original, &template_prompt, record.result.as_deref()
    ).await?;
    
    // 执行评审实例
    execute_review_instance_with_owning(&db, ..., composed_prompt, owning_id, owning_name).await?;
    ...
}
```

#### `resolve_review_template`——抽取为独立函数

当前是 `LoopRunner` 的方法（loop_runner.rs:1590），逻辑不依赖 `self` 的字段（只调用 `self.ensure_review_template`，后者只用 `self.ctx.db`），可抽出为接受 `db` 参数的独立函数。

```rust
// 在 auto_review.rs 中（或 db/review_template.rs）
/// 三级回退解析评审模板正文。
/// 顺序：step_review_prompt → loop 级 review_template_id → 全局默认。
/// 返回 (模板正文, 归属 template_id, 归属名称)。
pub async fn resolve_review_template(
    db: &Database,
    step_review_prompt: Option<&str>,
    loop_review_template_id: Option<i64>,
) -> Result<(String, i64, String), String> {
    // 1. 步骤内联
    if let Some(prompt) = step_review_prompt.filter(|s| !s.trim().is_empty()) {
        return Ok((prompt.to_string(), 0, "环节内联评审".to_string()));
    }
    // 2. 环路级
    if let Some(tid) = loop_review_template_id {
        if let Some(t) = db.get_review_template(tid).await.map_err(|e| format!("load template: {}", e))? {
            return Ok((t.prompt, t.id, t.name));
        }
    }
    // 3. 全局默认
    let default_id = db.ensure_default_review_template().await.map_err(|e| e.to_string())?;
    let t = db.get_review_template(default_id).await
        .map_err(|e| e.to_string())?
        .ok_or_else(|| "default reviewer template vanished".to_string())?;
    Ok((t.prompt, t.id, t.name))
}
```

**注意**：`ReviewTemplate` 模型的 `name` 字段需确认存在。查看 `db/entity/review_templates.rs`：

```rust
pub struct Model {
    pub id: i64,
    pub name: String,    // ← 大概率存在
    pub prompt: String,
    pub workspace_id: Option<i64>,
}
```

#### `execute_review_instance` 的复用策略

当前 `execute_review_instance` (L307) 以 `template.id` 为 key 查找是否已有可复用的评审实例 todo：

```rust
let existing = db.find_review_instance_by_template(template.id).await;
```

统一后，环节内联 prompt 无对应 `review_templates` 行，需要使用哨兵 ID `0`。`find_review_instance_by_template(0)` 会找不到（DB 中没有 `review_template_id=0` 的 todo），因此会为每个有内联 prompt 的步骤**各自创建一条评审实例**。

这是当前设计的固有限制，但可接受：同一环节（同一 step_id）的多次执行共享同一评审实例，因哨兵 ID 固定为 0。跨环节的内联 prompt 不同，评审实例各自独立——这也是正确的，因为 prompt 不同不应共享实例。

**与现状对比**：当前默认模板共享一条全局评审实例，所有评审都复用它。统一后不是退步——旧风格 `apply_rating_gate` 路径已通过 `resolve_review_template` 实现了相同的哨兵策略（L1597: `return Ok((rp.to_string(), 0, "环节内联评审".to_string(), 0));`）。

## 5. 数据流

```
todo 执行完成
  │
  ├─ todo.auto_review_enabled=true? ──否──→ 结束
  │
  ├─ loop_stage? ──是──→ find_loop_step_with_loop_review_template
  │                          │
  │                          ├─ step.review_prompt = Some → 用它
  │                          ├─ loop.review_template_id = Some → 查表
  │                          └─ 都没有 → 默认模板
  │
  └─ 非 loop_stage → 默认模板
       │
       └→ 占位符替换
            → 创建/复用评审实例 todo (todo_type=2)
            → run_todo_execution（执行评审）
            → 轮询评审记录至终态
            → 解析 RATING: N
            → 写回 execution_record.rating
            → link_review_to_source

loop_runner
  │
  ├─ [Path A] phase_driver::execute_step
  │     gate_evaluator 读 execution_record.rating → 门禁判定
  │
  └─ [Path B] apply_rating_gate
        execution_record.rating.is_some() → 短路，只需 min_rating 阈值对比
```

4. 旧风格 `min_rating.is_some()` 步骤 → 评分正确写入，门禁正确判断，无重复评审

---

## 8. 安全反思

- **评审实例复用**：哨兵 ID 0 的评审实例会在有 `review_prompt` 的步骤间共享。若用户期望不同 prompt 走不同实例，当前设计不会满足（同 step_id 共享一条）。这是可接受的——prompt 重置在 `reuse_or_create_review_instance` 中已实现（每次评审前重置 prompt/executor）。
- **`run_auto_review` 调用频次**：统一路径对 `min_rating.is_some()` 的旧风格步骤也会触发评审。这些步骤之前由 `apply_rating_gate` 触发评审，现在由统一路径触发，频次相同。`apply_rating_gate` 的短路机制确保不重复执行。
- **DB 查询新增**：`find_loop_step_with_loop_review_template` 在每次 `maybe_run_auto_review` 中被调用，仅 loop_stage 路径。`maybe_run_auto_review` 本身已有 `find_loop_step_by_todo_id` 调用（L862），替换为 JOIN 版本后查询次数不变。
- **无新增越权面**：评审 prompt 来源从「默认模板」变为「step 内联 prompt 或默认模板」，内容由工艺作者定义（信任级别同 `acceptance_criteria`），不引入新风险。

---

## 9. 风险与回退

| 风险 | 应对 |
|------|------|
| 统一路径对 `min_rating.is_some()` 旧风格步骤触发评审后，`apply_rating_gate` 读到评分立即短路——但如果 `run_auto_review_inner` 因某种原因未写出评分（如超时/崩溃），`apply_rating_gate` 会重新触发评审（因为它检查 `rec.rating` 为 None） | 接受：这是正确的容错行为，统一路径失败后 `apply_rating_gate` 兜底 |
| `find_loop_step_with_loop_review_template` 的 JOIN 查询影响性能 | 按 todo_id 查询 + LIMIT 1，索引已覆盖（todo_id 有索引），可忽略 |
| 评审实例 todo 的复用策略变化导致不必要的实例创建 | step 内联 prompt 用哨兵 ID 0，跨不同步骤不共享实例。可通过在未来步骤 ID 作为复用 key 来优化——不在本次范围内 |
| 回退 | 恢复 `maybe_run_auto_review` 的 `min_rating.is_some()` 提早返回 + 恢复 Path A 预检查 + 恢复 `resolve_review_template` 方法 + 恢复 `build_review_prompt`。所有删除/修改都在可 git revert 的粒度 |
