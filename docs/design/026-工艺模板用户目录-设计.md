# 026-工艺模板用户目录-设计

| 修改人 | 修改时间 | 修改内容 |
|--------|---------|---------|
| AtomCode (GLM-5.2) | 2026-07-25 | 初始版本 — 仿照专家双层目录，为工艺模板新增用户层 `~/.ntd/processes/`，避免 bundled 同步覆盖用户自定义工艺 |

---

## 1. 设计目标

当前工艺模板只存放在 `bundled-repo/processes/` 下，属于系统层。
`bundled-repo` 是一个 git 仓库，每次"立即同步"会执行 `git reset --hard <remote/branch>`（`backend/src/git_sync/mod.rs:267`），
**强制覆盖 `bundled-repo/processes/` 下的所有文件**。
用户若直接修改系统层工艺，下次同步就丢失。

本设计的目标：

1. 为工艺模板引入**用户层目录** `~/.ntd/processes/`，与专家模板的 `~/.ntd/experts/` 对齐。
2. 用户层工艺不会被 bundled 同步覆盖。
3. 系统同步不会删除用户层工艺。
4. 在前端"更多设置 → 模板管理"中新增"工艺模板"Tab，展示系统工艺与用户工艺的合并列表。
5. 用户可一键"复制为用户工艺"：把系统工艺复制到用户层，之后对它的修改不会被同步覆盖。

---

## 2. 现状分析：skill / 专家 / 事项如何解决同步覆盖

### 2.1 双层目录模式（专家）

`backend/src/expert/loader.rs` 定义了两套目录：

```
~/.ntd/bundled/experts/   ← 系统层，从 bundled-repo 同步，会被 git reset --hard 覆盖
~/.ntd/experts/           ← 用户层，用户自定义，不会被同步覆盖
```

加载顺序（`backend/src/main.rs:540-559`）：

1. 先加载系统专家（`ExpertSource::System`）
2. 再加载用户专家（`ExpertSource::User`）
3. **用户同名专家覆盖系统专家**（`ExpertIndexManager::update_index` 后入为主）

### 2.2 事项模板模式（todos）

`backend/src/handlers/bundled.rs:461` 的 `import_todo_templates_from_bundled`：

- 扫描 `bundled/todos/*.yaml`，upsert 到数据库，标记 `is_system=true`
- 用户在前端"新建模板"时，写入数据库 `is_system=false`
- 系统模板只读、不可编辑/删除；用户模板可增删改

### 2.3 Skill 模板模式

`backend/src/handlers/skills.rs:30` 的 `executor_skills_dir_str`：

- 系统层：`~/.ntd/bundled/skills/` （从 bundled-repo 同步）
- 用户层：各执行器目录 `~/.{executor}/skills/`（用户安装的 skill）
- 前端"安装 skill"按钮把系统 skill 复制到用户层

### 2.4 工艺模板当前缺少用户层

| 维度 | 系统层 | 用户层 |
|------|--------|--------|
| 专家 | `~/.ntd/bundled/experts/` | `~/.ntd/experts/` ✅ |
| 事项 | `bundled/todos/` → DB `is_system=true` | DB `is_system=false` ✅ |
| Skill | `~/.ntd/bundled/skills/` | `~/.{executor}/skills/` ✅ |
| **工艺** | `bundled-repo/processes/` → DB `is_system=true` | **❌ 缺失** |

数据库 `process_templates` 表已有 `is_system` 和 `workspace_id` 字段（`backend/src/db/migration/v71.rs`），
但目前所有数据都来自 bundled 同步（`is_system=true`），**没有用户工艺目录**。

## 3. 方案设计

### 3.1 目录结构

```
~/.ntd/
├── bundled/
│   └── processes/              ← 系统层（从 bundled-repo 同步，会被覆盖）
│       ├── software/
│       │   ├── 4p12s-delivery.yaml
│       │   └── superpowers-task.yaml
│       └── step-templates/
└── processes/                  ← 用户层（新增，不会被同步覆盖）
    ├── software/
    │   └── my-custom-process.yaml
    └── step-templates/
```

**关键约定**：

- 系统层路径：`~/.ntd/bundled/processes/` （已有，由 `git_sync::bundled_dir` 派生）
- 用户层路径：`~/.ntd/processes/` （新增）
- 用户层与系统层**目录结构完全一致**（`software/`、`step-templates/` 等子目录平级）
- 同名工艺：用户层优先（与专家模式一致）

### 3.2 加载与覆盖语义

**同步触发**：复用现有"立即同步"按钮，同步 `Subdir::Processes` 时一并扫描用户层目录。

**加载顺序**（更新 `import_process_templates_from_bundled`）：

1. 先扫描系统层 `~/.ntd/bundled/processes/**/*.yaml`，upsert 为 `is_system=true`
2. 再扫描用户层 `~/.ntd/processes/**/*.yaml`，upsert 为 `is_system=false`
3. **用户同名工艺覆盖系统工艺**（`name` 为唯一键，后写入者覆盖）

**覆盖语义实现**：

- 当前 `upsert_system_process_template` 以 `name` 为键 upsert（`backend/src/db/process_template.rs:43`）
- 新增 `upsert_user_process_template`，同样以 `name` 为键 upsert，但设置 `is_system=false`
- 当用户层有同名工艺时，第二次 upsert 会把 `is_system` 从 `true` 改为 `false`，表示"用户已自定义覆盖系统工艺"

### 3.3 数据库设计

**无需新增表**。`process_templates` 表已有 `is_system` 和 `workspace_id` 字段，直接复用：

```sql
-- 系统工艺（来自 bundled 同步）
is_system = 1, workspace_id = NULL, source_path = 'bundled://processes/...'

-- 用户工艺（来自 ~/.ntd/processes/ 扫描）
is_system = 0, workspace_id = NULL, source_path = 'user://processes/...'
```

**字段含义**：

- `is_system`：是否为系统工艺（true=来自 bundled，false=用户自定义）
- `workspace_id`：工作空间级工艺的归属（本设计先支持全局用户工艺，`workspace_id=NULL`）
- `source_path`：来源路径前缀（`bundled://` vs `user://`），便于前端区分展示

### 3.4 同步删除策略

**问题**：bundled 同步时，如果系统层删除了某个工艺（远程仓库删了文件），数据库里对应的 `is_system=true` 记录是否要删除？

**策略**：

1. 系统层同步采用 **"先删后插"** 策略：同步开始时，删除所有 `is_system=true` 的 `process_templates` 记录，再重新 upsert。
2. 用户层同步采用 **"upsert 不删除"** 策略：用户层文件被用户手动删除时，数据库记录保留，但前端可标记为"文件缺失"。
3. **用户层工艺永远不会被系统同步删除**。

**风险与缓解**：

- "先删后插"会短暂让系统工艺列表为空，但同步是同步操作，前端在同步完成后再刷新列表，不会看到中间状态。
- 如果用户层有同名工艺覆盖系统工艺，删除系统层记录后再 upsert 用户层记录，最终 `is_system=false` 的用户工艺保留，语义正确。

### 3.5 用户工艺的编辑能力（M1 范围）

本设计先支持**只读展示 + 一键复制为用户工艺**，与 Skill 模板的"安装到执行器"模式一致：

1. **只读展示**：表格列出所有工艺（系统 + 用户），用户工艺标记"用户"Tag。
2. **复制为用户工艺**：系统工艺行有"复制到用户层"按钮，把系统工艺的 YAML 文件复制到 `~/.ntd/processes/` 对应路径，并触发用户层同步 upsert。
3. **完整 CRUD（M2 范围，不在本设计内）**：新建/编辑/删除用户工艺，需要 YAML 编辑器与校验器。

## 4. API 设计

### 4.1 复用现有 API

无需新增 API。复用 `backend/src/handlers/process.rs` 的现有端点：

```text
GET    /api/bundled/processes            → 列出所有工艺（系统 + 用户合并）
GET    /api/bundled/processes/{name}    → 查看单个工艺详情
POST   /api/bundled/processes/{name}/install → 安装工艺为 Loop
```

### 4.2 新增"复制为用户工艺"API

```text
POST   /api/v1/processes/{name}/copy-to-user
       → 把系统工艺 YAML 复制到 ~/.ntd/processes/ 对应路径
       → 触发用户层 upsert
       → 返回 { user_source_path: 'user://processes/...' }
```

**实现要点**：

- 源路径：系统工艺的 `source_path`（`bundled://processes/software/4p12s-delivery.yaml`）
- 目标路径：`~/.ntd/processes/software/4p12s-delivery.yaml`
- 复制后调用 `import_user_process_templates`，把用户层文件 upsert 到数据库
- 路径安全：目标路径必须在 `~/.ntd/processes/` 内，禁止 `..` 逃逸

## 7. 数据流与同步时序

### 7.1 用户点击"立即同步"时的时序

```
前端 TemplatesPanel.handleSync()
    │
    ▼
POST /api/v1/bundled/sync?subdir=processes
    │
    ▼
handlers/bundled.rs::sync_bundled
    │
    ▼
git_sync::sync_repo(~/.ntd/bundled/, remote, branch, Overwrite)
    ├─ git fetch
    └─ git reset --hard <remote/branch>     ← 强制覆盖 bundled-repo/processes/
    │
    ▼
import_process_templates_from_bundled(state, local_path)
    │
    ├─ 1. delete_all_system_process_templates()      ← 清空系统工艺记录
    ├─ 2. 扫描 ~/.ntd/bundled/processes/**/*.yaml    ← 系统层
    │      └─ upsert_system_process_template (is_system=true)
    └─ 3. 扫描 ~/.ntd/processes/**/*.yaml            ← 用户层（新增）
           └─ upsert_user_process_template (is_system=false)
              └─ 同名工艺覆盖系统层
```

### 7.2 用户点击"复制到用户层"时的时序

```
前端 ProcessTemplatesTab.handleCopyToUser(name)
    │
    ▼
POST /api/v1/processes/{name}/copy-to-user
    │
    ▼
handlers/process.rs::copy_process_to_user
    │
    ├─ 1. 查询系统工艺记录（name + is_system=true）
    ├─ 2. 计算目标路径：~/.ntd/processes/<相对路径>
    ├─ 3. 校验目标路径在 ~/.ntd/processes/ 内
    ├─ 4. 创建父目录，写入 YAML 内容
    └─ 5. 调用 import_user_process_templates，upsert 用户工艺
```

## 8. 安全与权限

1. **路径安全**：用户层目录扫描与"复制为用户工艺"的路径解析必须使用 `resolve_within` 模式（仿照 `backend/src/expert/loader.rs:249`），禁止 `..` 逃逸和绝对路径注入。
2. **文件权限**：用户层文件由 ntd 进程创建，权限为 0644（rw-r--r--），与 bundled 同步产物一致。
3. **YAML 校验**：用户层 YAML 在 upsert 前必须通过 `parse_process_file` 解析校验，非法 YAML 跳过并 warning（不阻断整体同步）。
4. **无权限模型变化**：本设计不引入新的 workspace 隔离或用户权限模型，工艺模板管理仍由全局配置控制。

## 11. 与现有设计的衔接

本设计是对 `docs/design/025-工艺管理-设计.md` 第 7 节"工艺模板市场与实例化"的补充：

- 025 设计只定义了系统层 `bundled-repo/processes/` 的同步机制
- 本设计新增用户层 `~/.ntd/processes/`，解决"用户自定义工艺被同步覆盖"的问题
- 与 025 设计的 §7.2 同步机制完全兼容，只是在同一同步流程中增加了用户层扫描步骤

本设计与 `docs/design/025-工艺管理-M3-设计.md` 的关系：

- M3 设计的第 3.4 节"可视化编排器"支持用户编辑 YAML，但未明确存储位置
- 本设计为用户工艺提供明确的存储路径 `~/.ntd/processes/`，为 M3 的可视化编排器奠定基础

## 12. 已知限制与待改进点

1. **用户工艺删除**：本设计先不实现"删除用户工艺"功能。用户需手动删除 `~/.ntd/processes/` 下的文件并重新同步。M2 可增加前端删除按钮。
2. **工作空间级用户工艺**：本设计先支持全局用户工艺（`workspace_id=NULL`）。若未来需要工作空间级用户工艺，可扩展 `workspace_id` 字段的 upsert 逻辑。
3. **用户工艺 YAML 编辑器**：本设计只支持"复制系统工艺为用户工艺"，不支持在前端直接编辑用户工艺 YAML。M2 可集成 Monaco 编辑器（参考 M3 设计 §3.4）。
4. **用户工艺版本管理**：本设计不引入用户工艺的版本 diff 与升级提示，这部分由 M3 设计覆盖。

## 13. 风险

| 风险 | 处理 |
|------|------|
| 用户层目录不存在时扫描失败 | `import_user_process_templates` 在目录不存在时返回 Ok(())，与系统层逻辑一致 |
| 用户层 YAML 格式错误 | 解析失败时 warning 跳过，不阻断同步（与现有 `parse_process_file` 逻辑一致） |
| 同名工艺覆盖导致数据丢失 | 用户层覆盖系统层时，系统层 YAML 仍在 `~/.ntd/bundled/processes/`，可随时恢复 |
| "先删后插"策略的中间状态 | 同步是同步操作，前端在同步完成后再刷新列表，不会看到中间状态 |
