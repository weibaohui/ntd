## 1. 总体思路

核心约束沿用 060：**执行系统是 Todo 中心的**，所有执行走 `run_todo_execution`，必须有 Todo 作载体；Task 本身不直接执行。060 已经把「发含 `@` 的讨论帖 → 建隐藏载体 Todo → 触发执行 → 结论回帖」跑通了。

因此本设计的总策略仍是 **「不造新引擎，复用现有管线」**：

1. **委派不是新执行路径** → 委派任务创建 = 建 task（无 loop）+ 在讨论区落地一条含 `@处理人` 的首帖，**直接复用 060 的 `@` 触发执行**。委派任务的「执行」就是讨论区里的一次 `@` 触发。
2. **自动接力（管家调度）只新增一个 completion 分支** → 在 `executor_service/completion.rs` 的 discussion 回写之后，新增「若该任务是 delegate + auto_continue，则把 assignee 管家专家的输出当作调度指令继续推进」的逻辑。
3. **数据层最小改动** → `tasks` 表加 5 列表达「执行方式 + 委派对象 + 接力开关/计数」，不动 `task_posts`、不动执行管线。

专家与执行器正交（060 已述）；管家不是新实体，就是被开启自动接力的那个**协调者专家**。

## 2. 已采纳决策（需求澄清结论）

| 决策点 | 采纳方案 | 落地影响 |
|--------|----------|----------|
| 模式划分 | **工艺环路 / 委派** 两条；托管用「委派 + 自动接力开关」表达，不单列第三模式 | `execution_mode: loop \| delegate` |
| 委派首次执行 | **复用讨论区 `@` 首帖**（建 task + 落首帖触发） | 抽取 060 触发逻辑为公共函数，零新执行路径 |
| 自动接力触发方式 | **事件驱动**（completion 回调），非同步阻塞 | 新增 `completion.rs` 接力分支 |
| 自动接力唤醒对象 | **assignee 管家专家为中枢**：被@者执行完→唤醒管家；管家结论含@→触发被@者 | completion 按「本次专家是否 assignee」分两个子分支 |
| 默认管家 | **不做工作空间级默认**；任务级指定 assignee 即可 | 不新增配置项 |
| 处理人选择 UI | **创建弹窗显式选**专家或执行器 | 复用 `ExecutorPicker`/`ExpertPicker` |
| 自动接力适用范围 | **仅专家可开**（执行器无调度能力） | UI 禁用 + 后端 400 双重校验 |

## 3. 现状与缺口

| 环节 | 现状 | 缺口 |
|------|------|------|
| 任务执行方式 | 只能绑环路（`CreateTaskModal` 必填 loop） | 需新增「委派」方式 |
| `tasks` 表 | 无执行方式/委派对象字段 | 需加 5 列 |
| 委派执行 | 讨论区 `@` 触发已具备（060），但入口在「任务已存在后的讨论 tab」 | 需在**创建入口**直接落地首帖 |
| 触发执行的可复用性 | `task_posts.rs::trigger_discussion_execution` 与发帖逻辑耦合在 `create_post` handler 内 | 需抽公共函数供 `create_task` 与自动接力复用 |
| 执行完成后的接力 | `completion.rs` 仅回写讨论帖，不继续推进 | 需新增自动接力分支 |
| 接力护栏 | 无 | 需轮数计数 + 上限熔断 |
| 委派任务详情页 | 任务详情以环路环节视图为主 | 委派任务需以讨论 tab 为主视图 |

## 4. 数据模型设计

### 4.1 `tasks` 表新增列（migration `v91`）

| 字段 | 类型 | 默认 | 说明 |
|------|------|------|------|
| `execution_mode` | TEXT | `'loop'` | `'loop'` / `'delegate'` |
| `assignee_kind` | TEXT | NULL | `'executor'` / `'expert'`（仅 delegate） |
| `assignee_name` | TEXT | NULL | 委派处理人名 |
| `auto_continue` | INTEGER | `0` | 自动接力开关；仅 `assignee_kind='expert'` 允许 `1` |
| `continue_rounds` | INTEGER | `0` | 接力已执行轮数（护栏计数） |

- `delegate` 模式下 `loop_id=NULL`（现有 `loop_id: Option<i64>`，兼容）。
- 同步更新 `db/entity/tasks.rs`（ActiveModel 字段）与 `consolidated_schema.rs`（全新库的 `CREATE TABLE tasks` 含新列）。
- migration 幂等：参考既有加列迁移（如 `v65`/`v68`）的「查 `pragma table_info` 判列存在再 ADD」模式，避免重复执行报错。

### 4.2 复用 060 的载体 Todo 与讨论帖

委派任务的所有执行（首帖 + 每轮接力）都产生：
- 一条 `task_posts`（人帖=首帖/接力指令；智能体帖=执行结论）。
- 一个隐藏载体 `todos`（`kind='discussion'`，对事项中心隐藏，060 已实现过滤）。

**本需求不改 `task_posts` 与 `todos` 任何字段**，仅复用。

### 4.3 关系图

```text
tasks(execution_mode=delegate, assignee=专家E, auto_continue=1)
  └─ has_many ─► task_posts
        ├─ 首帖(人帖, @E <需求>)                         ← create_task 落地
        ├─ E 结论帖(智能体帖, content 含 "@codex 做X")    ← 首次执行回写
        ├─ codex 结论帖(智能体帖)                         ← 被@者执行回写
        └─ E 决策帖(智能体帖, content 含/不含 @)          ← 接力唤醒管家
                └─ 每条智能体帖 source_execution_id ──► execution_records(trigger_type=discussion|discussion_auto)
                                              └─ source_todo_id ──► todos(kind=discussion, 隐藏)
```

## 5. 执行流程设计

### 5.1 委派任务创建（首帖触发，复用 060）

```text
前端 POST /workspaces/{ws}/tasks { requirement, execution_mode:'delegate',
                                    assignee_kind:'expert', assignee_name:'E', auto_continue:true }
  │
  ▼
handlers/tasks::create_task（新增 delegate 分支）
  ├─ 1. 校验：delegate 必带 assignee_kind/name；executor+auto_continue→400；
  │       assignee_name 服务端校验专家/执行器真实存在
  ├─ 2. 建 task（execution_mode=delegate, loop_id=NULL, assignee_*, auto_continue）
  ├─ 3. 复用公共函数 trigger_task_post_execution(task, 人帖正文="@{assignee} {requirement}",
  │       trigger_type='discussion')：建载体 Todo + run_todo_execution + 写占位帖
  └─ 4. 返回 { task_id, loop_id:null, execution_id }
```

> 处理人是「执行器」时，首帖正文为 `@codex {requirement}`；是「专家」时为 `@专家E {requirement}`，由 060 的 `classify_mention`（先专家后执行器）正确归类。

### 5.2 自动接力循环（completion 新增分支，核心机制）

**接力中枢规则**：assignee 管家专家 E 是调度中枢。每次讨论类执行（`trigger_type` 为 `discussion` 或 `discussion_auto`）完成、回写结论帖之后，若 `task.auto_continue=true`，按「本次执行的专家是否就是 assignee E」分两个子分支：

```text
某次讨论类执行完成 ──► completion.rs
  ├─ discussion 回写（060 既有）：把结论写回对应智能体占位帖   ← 对 discussion/discussion_auto 都生效
  └─【新增】接力判断（仅 task.execution_mode=delegate && auto_continue）：
       (a) continue_rounds += 1；若 continue_rounds > MAX_ROUNDS(10) → 写「已达上限，停止接力」帖，return
       (b) 取本次执行的专家 X（载体 todo 的 expert_name/executor）：
            ├─ X == assignee E（管家决策）→ 解析其结论帖正文里的 @：
            │     ├─ 含 @yyy → 触发 yyy 执行(trigger='discussion_auto')，结束本步（yyy 完成后会再回到这里）
            │     └─ 不含 @  → 管家判定完成，写「任务已完成」说明帖，循环终止
            └─ X != assignee E（被@者）→ 唤醒管家：以 E 身份触发一次决策执行
                  (trigger='discussion_auto', message=决策提示：前序结论 + 让 E 决定下一步)
```

**完整时序示例**（管家 E 自动接力）：

```text
首帖 @E(需求) ──执行(管家决策, trigger=discussion)──► 结论帖 C1(content:"@codex 修X")
  └─ 回写 C1 → 接力判断: X==E → 解析 C1 的 @ → 含 @codex → 触发 codex(trigger=discussion_auto)
codex ──执行──► 结论帖 C2(content:修复结果)
  └─ 回写 C2 → 接力判断: X==codex≠E → 唤醒 E 决策(trigger=discussion_auto)
E ──执行(决策)──► 结论帖 C3(content:"任务完成，无需再处理")
  └─ 回写 C3 → 接力判断: X==E → 解析 C3 的 @ → 不含 @ → 写「已完成」帖，终止
```

### 5.3 关键复用点：解析智能体帖的 `@`

060 的 `@` 解析（`extract_at_tokens` + `resolve_mentions`）目前只对**人帖**触发。自动接力需要**解析管家结论帖（智能体帖）里的 `@`** 来决定下一步。做法：

- 把 `extract_at_tokens`（已是 `pub(crate)`）与 `resolve_mentions` 提升为模块内可复用（`resolve_mentions` 当前是 `task_posts.rs` 私有 async，提到可被 `completion.rs` 调用的可见度）。
- 在接力分支用它们解析管家结论帖 `content`，得到 `mentions`，取首个 executor/expert 作为下一跳。

### 5.4 接力帖的 message 构造

「唤醒管家决策」时给管家的 message 复用 060 `build_carrier_prompt` 的思路，但角色提示不同：

```text
你是任务 #{id} 的任务管家（协调者）。任务需求：{description}。
## 最近的讨论/执行结论（按时间正序）
{最近 N 条讨论帖，含被@者结论}
## 你的职责
决定下一步：@合适的专家或执行器去做具体的事；若任务已全部完成，则直接回复结论、不要 @ 任何人。
（你的回复若含 @某人，系统会自动触发其执行；不含 @ 则任务结束。）
```

管家专家的人设由 `inject_expert_context` 按 `expert_name=E` 自动注入，不在此重复。

## 6. 后端详细改动

### 6.1 `db/entity/tasks.rs` + `v91` migration
- entity 加 5 个字段；`v91.rs`（`V91TaskDelegateExecution`）ALTER TABLE 加列（幂等）；`mod.rs` 注册；`consolidated_schema.rs` 同步。

### 6.2 DAO：`db/task.rs`
- `create_task` 扩展：写入 `execution_mode`/`assignee_*`/`auto_continue`（`continue_rounds` 默认 0）。
- 新增 `increment_continue_rounds(task_id) -> i64`（原子 +1 并返回新值，护栏判定用）。
- 新增 `get_task_delegate_meta(task_id)`：取 `execution_mode/assignee_kind/assignee_name/auto_continue/continue_rounds`，供 completion 接力判断（轻量单行查询）。

### 6.3 `handlers/task_posts.rs`：抽取公共触发函数
- 把 `create_post` 内的「建载体 Todo + 触发执行 + 写占位帖」与「@ 解析」抽成模块级函数，供 `create_task`（首帖）与 `completion`（接力）复用：
  - `resolve_post_mentions(content, state) -> Vec<MentionDto>`（包装 `extract_at_tokens`+`resolve_mentions`，提升可见度）。
  - `trigger_post_execution(state, task, mentions, prompt, trigger_type) -> (todo_id, record_id)`（从 `trigger_discussion_execution` 泛化，支持传入 `trigger_type`）。
- `create_post` 行为不变（仅改为调用抽出的函数），060 回归不破。

### 6.4 `handlers/tasks.rs::create_task`
- 新增 delegate 分支（§5.1）：校验 → 建 task → 调 `trigger_post_execution`（首帖，`trigger_type='discussion'`）→ 返回。
- loop 分支不变。旧请求（无新字段）按 loop 处理，完全兼容。

### 6.5 `executor_service/completion.rs`：自动接力分支
- 在 `finalize_normal_completion` 的 discussion 回写（line 466 一带）之后新增接力判断（§5.2）。
- 拆分为小函数：`maybe_continue_delegated_task(...)`（≤30 行编排）→ `next_delegate_step(...)`（管家/被@者分派）→ 复用 `trigger_post_execution`。
- 失败容忍：接力触发失败只记 `tracing::warn`，不影响本次执行已落定的成功状态（与 060 回写降级哲学一致）。

### 6.6 常量
- `MAX_DELEGATE_ROUNDS: i64 = 10`（接力上限，集中一处便于演进为可配置）。
- `TRIGGER_DISCUSSION_AUTO: &str = "discussion_auto"`。

### 6.7 不改动
- `CodeExecutor` trait / `adapters/*`、`expert/`、`execution_records` 语义、`run_todo_execution` 管线、`task_posts` 表结构、`todos.kind='discussion'` 隐藏过滤、工艺环路全部逻辑。

## 8. 安全与权限反思

- **assignee 服务端校验**：`assignee_name` 必须服务端校验专家/执行器真实存在（防伪造任意名执行），复用 060 的 `classify_mention`/`find_executor`。
- **auto_continue 双重校验**：前端禁用 + 后端 400（executor+auto_continue 拒绝），防绕过。
- **接力护栏不可绕过**：`continue_rounds` 由后端单调递增，前端不可直传；触顶强制停。
- **执行隔离**：载体 Todo 继承任务 `workspace_id`，受既有 workspace 隔离与并发上限约束。
- **接力帖即普通讨论帖**：不引入新鉴权面，沿用 060（删帖暂不鉴权，待用户系统）。
- **递归防护**：接力用专用 `trigger_type='discussion_auto'`，completion 据此与人工 `discussion` 区分日志/统计；循环终止靠「管家不再 @」+「轮数上限」双重保证，不会无限递归。

## 11. 验证限制说明

- 端到端自动接力依赖真实专家人设与执行器；本机以默认执行器（Claude Code）+ 一条临时协调者型用户专家为验证对象，其余执行器仅验证「触发后 argv 正确、占位帖→failed 兜底」。
- 接力循环的终止/护栏以单测（mock completion 分支）为主验证，避免端到端跑满 10 轮消耗 token。
- 自动接力的「成本上限 / 人类检查点」本期不做（需求 §3 已列为非目标），由轮数上限兜底。
