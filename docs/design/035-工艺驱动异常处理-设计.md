## 1. 设计目标与原则

把异常处理从「环路弹窗手选外部 Todo」统一为「工艺 YAML 唯一权威来源」。核心原则：

1. **工艺即权威**：异常处理的 prompt 与触发条件都在工艺 YAML 定义，安装写入环路。
2. **环路忠实执行**：环路运行时只读工艺定义，不可偏离；环路弹窗对异常处理配置**只读展示**。
3. **运行时注入上下文与错误信息**：`trigger_abnormal_handler` 把异常上下文、失败原因等以**占位符替换**注入到异常处理 prompt（而非旧的 `format!` 硬编码拼接），并前置 workspace 共识、末尾兜底追加异常上下文段落。

### 关键设计发现（修正）

`trigger_abnormal_handler` 当前逻辑：读 `loops.abnormal_handler_todo_id` → 加载 Todo → 取 `todo.prompt` → `format!` 拼接 `## 异常上下文` 段落 → 执行。

**两点结论：**

- **运行时执行路径不变**：只要安装工艺时把异常处理 prompt 包成一个 Todo 并写入 `abnormal_handler_todo_id`，`trigger_abnormal_handler` 仍能照常加载执行——**底层 `run_todo_execution_with_params` 不动**，载体 Todo 复用它。这正是方案 A1 的低成本基础（不碰 executor 接口）。
- **prompt 合成需要改造**：当前用 `format!` 硬拼，用户在 prompt 里写 `{{loop_name}}` 等占位符**不会被替换**。本次改为占位符替换（与评审 prompt 的 `compose_review_prompt` 一致），让快捷变量输入条有意义，并新增 `{{error_detail}}` 注入失败原因。

> 表述澄清：v1 文档「运行时零改 executor」易被误解为「运行时不做事」。准确含义是——**不改底层 executor 接口**，但 `trigger_abnormal_handler` 内的 **prompt 合成逻辑要改造**（占位符替换 + 错误注入）。

载体 Todo 用 `todo_type=3`（异常处理）标识，无需隐藏——它在事项列表里带「异常处理」标签显示，与评审实例（`todo_type=2`）模式对称。

## 2. 数据模型变更

### 2.1 `loops` 表

新增列（migration v76，**只加列，不回填**）：

| 列 | 类型 | 说明 |
|----|------|------|
| `abnormal_handler_prompt` | `TEXT NULL` | 工艺定义的异常处理 prompt 快照（只读展示/导出用） |

`abnormal_handler_todo_id`（`INTEGER NULL`）**保留列、不删**——运行时仍读取它（指向安装时创建的载体 Todo），但不再通过 HTTP API 写入（见 §4）。

### 2.2 `AbnormalHandlerConfig`（工艺 YAML）

```rust
// services/process/mod.rs
pub struct AbnormalHandlerConfig {
    // 移除：pub todo_template: Option<String>
    pub prompt: Option<String>,        // 异常处理提示词（可含占位符）
    #[serde(default)]
    pub trigger_on: Vec<String>,       // capped_step / capped_token / failed
}
```

> `AbnormalHandlerConfig` 不加 `#[serde(deny_unknown_fields)]`，旧 YAML 里残留的 `todo_template` 字段反序列化时静默忽略，不报错。

### 2.3 todo_type 扩展

| 值 | 语义 | 状态 |
|----|------|------|
| 0 | 普通事项 | 在用 |
| 1 | 评审任务模板（历史） | 已废弃 |
| 2 | 评审实例 | 在用 |
| **3** | **异常处理（loop abnormal handler）** | **本次新增** |

后端新增常量（`db/todo.rs`，供 installer / loop_runner / handler 引用，替代魔法数字）：

```rust
/// 异常处理载体 Todo 的类型。
/// 工艺安装时为 abnormal_handler.prompt 自动创建，作为运行时执行的容器，
/// 避免异常处理依赖工艺外的「手选 Todo」。模式与 todo_type=2 评审实例对称。
pub const TODO_TYPE_ABNORMAL_HANDLER: i32 = 3;
```

## 3. 数据流

### 3.1 安装工艺（install / upgrade）

```
工艺 YAML
  abnormal_handler: { prompt, trigger_on }
        │ installer
        ├─（若 prompt 非空）─→ 创建 todo_type=3 载体 Todo
        │     title: "[异常处理] {工艺显示名}"
        │     prompt: = 工艺 abnormal_handler.prompt
        │     todo_type: 3
        │     workspace_id: 继承
        │     auto_review_enabled: false   // 异常处理本身不评审，防嵌套
        │     executor: None               // 运行时用默认执行器
        │
        ├─→ loops.abnormal_handler_todo_id   = 载体 Todo.id
        ├─→ loops.abnormal_handler_prompt    = 工艺 prompt（只读快照）
        └─→ loops.abnormal_handler_trigger_on = trigger_on 序列化

（若 prompt 为空）─→ 三列均置空，不创建载体 Todo
```

### 3.2 运行时触发（执行路径不变，prompt 合成改造）

```
loop_runner 异常触发点（4 处，位置不变；新增 error_detail 参数）
  → trigger_abnormal_handler(loop_id, ..., abnormal_status, error_detail)
     ├─ 读 loops.abnormal_handler_todo_id     // = 载体 Todo
     ├─ 读 loops.abnormal_handler_trigger_on   // 过滤当前状态
     ├─ 加载载体 Todo，取 prompt（= 工艺 prompt）
     ├─ 【改造】占位符替换：把 {{loop_name}} {{abnormal_status}}
     │         {{error_detail}} 等替换为运行时实际值（双花括号，与评审 prompt 一致）
     ├─ 前置 workspace 共识（不变）
     ├─ 末尾兜底追加 ## 异常上下文 段落（含 error_detail，确保不写占位符也能看到上下文）
     └─ run_todo_execution_with_params 执行    // 复用现有路径，接口不变
```

### 3.3 环路弹窗 / 详情（只读）

```
loops.abnormal_handler_prompt  ─→ 弹窗「异常处理 Prompt」只读展示
loops.abnormal_handler_trigger_on ─→ 弹窗「触发条件」Checkbox disabled
（载体 Todo 不在弹窗暴露，用户无法改异常处理配置）
```

## 4. API / DTO 变更（决策 B2）

HTTP 层彻底移除 `abnormal_handler_todo_id`（用户不再手选 Todo）：

```rust
// models/loop_.rs
pub struct LoopDto {
    // ...
    pub abnormal_handler_prompt: Option<String>,      // 新增
    pub abnormal_handler_trigger_on: String,
    // 移除 abnormal_handler_todo_id（不再返回给前端）
}

// CreateLoopRequest / UpdateLoopRequest：移除 abnormal_handler_todo_id
//   异常处理 prompt 只由 installer 写入，手工 loop 无异常处理配置
```

`db::loop_::update_loop` 签名**不改**（已有 11 个参数，再加会触红线）。installer 的 upgrade 路径沿用既有模式——在 `update_loop` 之后用 `ActiveModel` 单独 set 新字段（与 `process_template_version` 的更新方式一致，见 `installer.rs:582-589`）：

```rust
// installer upgrade：update_loop 后单独更新 prompt（不改 update_loop 签名）
let existing = loops::Entity::find_by_id(loop_id).one(conn).await?;
if let Some(c) = existing {
    let mut am: loops::ActiveModel = c.into();
    am.abnormal_handler_prompt = ActiveValue::Set(prompt_opt);
    am.updated_at = ActiveValue::Set(Some(now));
    am.update(conn).await?;
}
```

## 5. 运行时 prompt 合成设计（本次改造重点）

### 5.1 占位符变量集

| 占位符 | 含义 | 来源 |
|--------|------|------|
| `{{loop_name}}` | Loop 名称 | `loop_.name` |
| `{{loop_execution_id}}` | Loop 执行 ID | 触发点传入 |
| `{{abnormal_status}}` | 异常状态 | `capped_step` / `capped_token` / `failed` / `partial` |
| `{{total_executed_steps}}` | 已执行步数 | 触发点传入 |
| `{{total_tokens_used}}` | 已消耗 Token | 触发点传入 |
| `{{error_detail}}` | **失败原因（新增）** | 见下 |

### 5.2 `error_detail` 来源（4 个触发点）

| 触发点 | error_detail |
|--------|-------------|
| run 致命失败（`Err(e)`） | `e.to_string()`（错误信息） |
| 步数超限 capped_step | `已达最大执行步数上限` |
| Token 超限 capped_token | `已达最大 Token 上限` |
| 主循环结束 failed/partial | 空（无具体错误；兜底段落仍带 abnormal_status） |

> `{{error_detail}}` 替换为空字符串时，prompt 应自然容忍（兜底段落也会体现异常状态）。实现上用 `.replace("{{error_detail}}", &error_detail)` 即可。

### 5.3 合成顺序

```
final_prompt =
    workspace 共识（前置注入，不变）
  + 占位符替换后的 prompt 正文（{{loop_name}} 等已替换）
  + "\n\n## 异常上下文\n- Loop 名称: ...\n- 异常状态: ...\n- 已执行步数: ...\n- 已消耗 Token: ...\n- 失败原因: {error_detail 或省略}"
```

> 占位符替换与兜底段落**并存**：用户写占位符则精确引用；不写也能从末尾段落看到全部上下文。模式与正常 step 的 `inject_requirement`（占位符替换 + 兜底追加）一致。占位符统一 **双花括号**，复用评审 prompt 的替换工具，避免历史「单花括号不替换」问题。

### 5.4 实现要点

- `trigger_abnormal_handler` 签名新增 `error_detail: Option<&str>` 参数；4 个触发点分别传入（见 5.2）。
- 占位符替换抽成独立小函数 `compose_abnormal_handler_prompt(template, vars) -> String`，便于单元测试（函数 ≤50 行）。
- `context_params`（现有 HashMap）保留，继续作为执行器 params 传递；占位符替换是 prompt 层的额外加工。

## 6. 导入 / 导出（不主动改造）

环路导入导出**保持现状，本次不改造**（后期会整体移除该功能）。

- 现有导入导出读 **loop model（entity）**，entity 保留了 `abnormal_handler_todo_id` 列，导入导出通常**不受** `LoopDto` 字段变更影响。
- 仅当字段移除导致编译错误时，做**最小适配**（保持现有以 todo_id 为基础的逻辑，不重构成 prompt 权威）。
- 不在本次新增 prompt 的导出/导入。

## 9. 边界与一致性

- **prompt 为空**：不创建载体 Todo，三列置空；运行时静默跳过；弹窗展示「未配置」。
- **upgrade 时 prompt 变化**：旧载体 Todo 存在 → 更新其 `prompt`（保持 todo_id 不变，历史执行记录引用稳定）；旧 loop 无载体 Todo、新 prompt 非空 → 新建。
- **upgrade 时 prompt 清空**：不删旧载体 Todo（避免破坏历史 step_execution 引用），只把 loop 的 prompt/todo_id 置空。
- **载体 Todo 被误删**：运行时加载失败 → 走现有「Todo not found 静默跳过」。
- **执行器**：载体 Todo `executor=None`，运行时落默认执行器（dev 环境为 pi）。
- **防嵌套评审**：载体 Todo `auto_review_enabled=false`（与评审实例对称）。
- **占位符未写**：兜底段落仍注入全部异常上下文，AI 不致信息缺失。

## 12. 约束遵循

- 单函数 ≤50 行：installer install/upgrade 的「创建载体 Todo + 写 loop」拆为小函数（`ensure_abnormal_handler_todo`）；prompt 合成抽 `compose_abnormal_handler_prompt`。
- 零告警：`cargo clippy --all-targets -- -D warnings` + `npx tsc --noEmit`。
- 注释：新增/改动逐行说明「为什么」，尤其 todo_type=3 设计意图、占位符替换机制、为什么保留两份 prompt（loop 列只读快照 + 载体 Todo 执行容器）。
- `@/` 绝对路径：前端跨目录导入统一 `@/`。
- 占位符双花括号：与评审 prompt 一致，复用替换工具。
