## 1. 总体思路

核心约束：**执行系统是 Todo 中心的**，所有「让执行器干活」都走 `run_todo_execution`（`executor_service/mod.rs`），必须有一个 Todo 作载体；Task 本身没有执行器概念。

因此本设计的总策略是 **「不造新引擎，复用现有管线」**：

1. **讨论帖是新东西** → 新增一张轻量表 `task_posts`，挂在 `tasks` 上。
2. **`@` 触发的执行不是新东西** → 复用 `run_todo_execution`，载体是一个**对事项中心隐藏的 Todo**（`kind='discussion'`），由它承载 `executor` / `expert_name` / `prompt`。
3. **结论回帖** → 在既有完成路径 `executor_service/completion.rs` 里**新增一个 `trigger_type='discussion'` 分支**，执行落定时把结论写回对应的智能体帖。
4. **界面** → `TaskDetailPanel` 新增第 4 个「讨论」Tab，帖子流 + 输入器。

专家与执行器正交（专家是人设、自己不跑），`@专家` = 用默认执行器 + `inject_expert_context` 注入该专家人设。

## 2. 已采纳决策（需求澄清结论）

需求阶段提出 4 个决策点，本设计采纳推荐方案：

| 决策点 | 采纳方案 | 落地影响 |
|--------|----------|----------|
| 跟帖结构 | **扁平主楼层 + 一层楼中楼** | `task_posts.parent_post_id` 仅允许指向主楼层（深度≤1） |
| `@专家` 如何跑 | **走系统默认执行器**（可配，默认 Claude Code） | 载体 Todo 的 `executor` 取默认执行器；`expert_name` 取被@专家 |
| @对象范围 | **仅 @专家 和 @执行器** | `@选择器` 数据源 = 专家列表 + 执行器列表，不引入用户系统 |
| 回帖形式 | **占位帖 + 实时更新结论** | 智能体帖有 `running`→`success`/`failed` 状态机；前端轮询/事件管道更新 |

> 上述任一项可经需求变更调整；改动集中于载体 Todo 构造与帖子状态机，影响面可控。

## 3. 现状与缺口

| 环节 | 现状 | 缺口 |
|------|------|------|
| 任务讨论实体 | 无任何 comment/reply/discussion 表 | 需新增 `task_posts` |
| 任务详情页 | `TaskDetailPanel` 三个 Tab（概览/执行环路/执行历史） | 需加第 4 个「讨论」Tab |
| @提及组件 | 项目无任何 mention/comment 库 | 需基于 `MdEditor` 自建 `@选择器` |
| 执行触发 | 必须有 Todo 作载体；Task 无执行器概念 | 需为每次 `@` 触发创建隐藏载体 Todo |
| 执行完成回写 | `completion.rs` 按 `trigger_type` 分派（`auto_review`/`blackboard`） | 需加 `discussion` 分支回写帖子 |
| 载体可见性 | `todos.kind` 在列表/事项中心查询**未做过滤** | 需加 `kind != 'discussion'` 排除 |
| Markdown 编辑/渲染 | `@uiw/react-md-editor`（`MdEditor.tsx`，已暴露光标位置）+ `@ant-design/x-markdown` | 已具备，直接复用 |
| 快捷话术 | `QuickButtonBar` + `quick_buttons` 表 | 已具备，复用到讨论输入器 |

**可参考但不直接复用**：`todo-post/`、`ForumPostCard`、`ReplyInput` —— 它们渲染 `ExecutionRecord`、调用 `resumeExecutionRecord`，语义是「与 AI 续聊」，强绑定执行器/评分/会话恢复。仅作**视觉与交互模板**参考。

## 4. 数据模型设计

### 4.1 新增表 `task_posts`

```sql
CREATE TABLE task_posts (
  id                   INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id              INTEGER NOT NULL,            -- FK tasks.id, ON DELETE CASCADE
  parent_post_id       INTEGER,                     -- 楼中楼：指向主楼层；NULL=主楼层。深度限制≤1
  kind                 TEXT    NOT NULL,            -- 'human' | 'agent'
  author_name          TEXT    NOT NULL,            -- 显示名
  executor             TEXT,                        -- 智能体帖：执行器名（逻辑引用 executors.name）
  expert_name          TEXT,                        -- 智能体帖：被@专家名
  content              TEXT    NOT NULL DEFAULT '', -- Markdown 正文
  mentions             TEXT    NOT NULL DEFAULT '[]',-- JSON [{type,name,display}]
  status               TEXT    NOT NULL DEFAULT 'sent', -- 人帖'sent'；智能体帖 running|success|failed
  source_execution_id  INTEGER,                     -- 智能体帖：来源 execution_records.id
  source_todo_id       INTEGER,                     -- 承载执行的隐藏载体 todos.id
  created_at           TEXT,
  updated_at           TEXT,
  FOREIGN KEY (task_id)        REFERENCES tasks(id)        ON DELETE CASCADE,
  FOREIGN KEY (parent_post_id) REFERENCES task_posts(id)   ON DELETE CASCADE
);
CREATE INDEX idx_task_posts_task_id ON task_posts(task_id);
```

**字段取舍说明**：
- `mentions` 用结构化 JSON 而非靠正则解析正文 —— 触发逻辑与徽标渲染都依赖它，正文里的 `@token` 仅作展示，不作为触发依据（可靠）。
- `source_execution_id` + `source_todo_id` 让智能体帖可一键跳转完整执行记录/日志，复用现有执行详情页。
- `parent_post_id` 只允许指向主楼层（应用层校验深度≤1），避免任意深度嵌套的渲染复杂度。

### 4.2 载体 Todo（复用 `todos`，加 `kind='discussion'`）

每次 `@` 触发创建一个载体 Todo，字段填充：

| todos 字段 | 取值 |
|-----------|------|
| `kind` | `'discussion'`（**新增值**，用于隐藏过滤） |
| `title` | `讨论帖 #{post_id}` 或取帖子首行 |
| `prompt` | 帖子正文 + 任务标题/描述上下文（见 §5.2） |
| `executor` | 被@执行器；未指定则系统默认执行器 |
| `expert_name` | 被@专家（若有） |
| `workspace_id` | 任务所在 workspace |
| `todo_type` | `0`（普通） |
| `model` | 沿用默认回退链 |

### 4.3 关系图

```
tasks ──has_many──► task_posts (parent_post_id 自引用，深度≤1)
                  └─ agent 帖 ──source_execution_id──► execution_records
                              └─source_todo_id──► todos (kind='discussion', 对事项中心隐藏)
                                                            todos.expert_name ──► expert (人设注入)
                                                            todos.executor  ──► executors (CLI)
```

## 5. 执行流程设计（`@` 触发 → 结论回帖）

### 5.1 时序

```
前端 POST /tasks/{id}/posts {content, parent_post_id?}
  │
  ▼
handlers/task_posts::create_post
  ├─ 1. 校验 task 存在、content 非空、parent_post_id 归属本任务且深度≤1
  ├─ 2. 解析 mentions（正文 @token → 结构化），服务端校验专家/执行器存在性
  ├─ 3. 写入人帖 task_post(kind='human', status='sent')
  ├─ 4. if mentions 非空：
  │     a. 创建载体 Todo(kind='discussion', executor/expert_name/prompt)
  │     b. 构造 RunTodoExecutionRequest{todo_id, message=帖子正文+上下文,
  │        req_executor, trigger_type='discussion', source_todo_id, source_todo_title}
  │     c. 调 run_todo_execution → 生成 execution_record(running)，拿到 record_id
  │     d. 立刻写智能体占位帖 task_post(kind='agent', status='running',
  │        source_execution_id=record_id, source_todo_id, author_name=专家/执行器)
  └─ 5. 返回：人帖 + 占位帖（前端立即渲染「正在干活…」）

  ……执行器异步跑（LogFlusher 写日志、回写 session_id）……

completion.rs 执行落定（success/failed）
  └─ trigger_type=='discussion' 分支：
       按 source_todo_id / source_execution_id 找到占位帖 →
       更新 content=result（结论摘要）、status=success|failed、updated_at
```

### 5.2 发给执行器的 message 构造

帖子正文本身不直接当 prompt（避免占位符/上下文缺失），而是在创建载体 Todo 时拼装：

- `todo.prompt` = 固定模板 + 帖子正文，模板形如：
  ```
  你是被 @ 到任务讨论区的{{expert或executor}}。任务：{{task.title}}。
  任务需求：{{task.description}}。
  讨论诉求（来自楼层 #{post_id}）：
  {{post.content}}
  请给出可直接用于回复的结论（Markdown）。
  ```
- 复用现有 `replace_placeholders`（`models/mod.rs`）做占位符替换；专家人设由 `inject_expert_context`（`pre_spawn.rs`）按 `todo.expert_name` 自动前置注入，无需本设计额外处理。

### 5.3 完成回写（`completion.rs` 新增分支）

`persist_completion_record` 之后既有按 `trigger_type` 分派的后处理（`auto_review`、`blackboard`）。新增：

```rust
// 讨论帖触发：把执行结论回写到对应的智能体占位帖。
// 放在 success/failed 落定之后、与 auto_review 同级的并列分支。
if trigger_type == "discussion" {
    if let Err(e) = db.finalize_discussion_post(record_id, final_status, &result_str).await {
        // 回写失败只记日志，不影响执行本身的成功落定（帖子可由前端轮询兜底）。
        tracing::warn!(error = %e, record_id, "finalize discussion post failed");
    }
}
```

`finalize_discussion_post`（DAO 新增）：按 `source_execution_id = record_id` 定位占位帖，更新 `content`/`status`/`updated_at`。

## 6. 后端详细改动

### 6.1 `db/entity/task_posts.rs`（新增）
- `DeriveEntityModel`，字段对应 §4.1；`Relation`：`BelongsTo tasks`、`BelongsTo self(parent)`。

### 6.2 `db/task_post.rs`（新增 DAO）
- `create_post` / `get_post` / `list_posts_by_task(task_id, parent_id, page, limit)` / `delete_post` / `finalize_discussion_post`。
- `list_posts_by_task` 支持分页与按 `parent_id` 过滤（主楼层 vs 某楼层的楼中楼）。

### 6.3 `handlers/task_posts.rs`（新增）
- `post_routes()` → 挂在 task 路由下：`/api/v1/workspaces/{ws}/tasks/{id}/posts`（及子路由）。
- `create_post`：编排 §5.1 的 5 步；拆分为 `validate_and_parse` / `create_carrier_todo` / `trigger_execution` / `create_placeholder_post` 等小函数（每个 ≤30 行）。

### 6.4 `@` 解析与触发
- `parse_mentions(content, experts, executors) -> Vec<Mention>`：正文 `@token`（空白/标点分隔）→ 先匹配专家名/显示名，再匹配执行器名/别名；同名歧义按 §10 风险策略处理。
- `create_carrier_todo`：填 §4.2 字段写 `todos`。
- 触发：复用 `executor_service` 的公共入口（与 `handlers/execution.rs::start_todo_execution` 同一构造路径），`trigger_type='discussion'`。

### 6.5 隐藏载体 Todo（防污染）
- `todos.kind` 当前在列表/事项中心查询未过滤；在以下查询加排除条件 `kind != 'discussion'`（或白名单 `kind IN ('item','step')`）：
  - `db/todo.rs::get_todo_center_page`
  - todo 列表查询（`list_todos` 等）
- 统计接口（计数/看板）同步排除，避免讨论载体污染数据。

### 6.6 migration
- 新增 `db/migration/v88.rs`（编号接当前最新 +1）：建 `task_posts` 表 + 索引；并在 `consolidated_schema.rs` 同步 `CREATE TABLE task_posts`（保持与既有 schema 聚合文件一致）。
- `todos.kind` 无需 schema 改动（TEXT，新增值即可）。

### 6.7 不改动
- `CodeExecutor` trait / 各 `adapters/*.rs`、`expert/`、`execution_records` 既有字段、`todo-post/` 组件 —— 全部不动。

## 8. 安全与权限反思

- **mentions 服务端校验**：前端传上来的 mention 仅为便捷，后端必须重新解析正文 + 校验专家/执行器真实存在，防伪造任意名触发执行。
- **执行隔离**：载体 Todo 继承任务的 `workspace_id`，受既有 workspace 隔离与并发上限（`count_active_running_for_todo`）约束。
- **删帖鉴权**：仅 `created_by` 本人可删；删 running 智能体帖需同时取消执行（调既有取消路径）。
- **结论注入风险**：执行器结论作为帖正文渲染，Markdown 渲染需防 XSS（沿用现有渲染器的 sanitize 策略，不额外 `dangerouslySetInnerHTML`）。
- **资源占用**：每次 `@` 触发一次真实执行（耗 token），`@选择器` 选中即视为用户确认；不做静默批量触发。

## 11. 验证限制说明

- 本机不一定安装全部 13 个执行器二进制；端到端「@某执行器 → 真实执行 → 结论」以默认执行器（Claude Code，本机可用）为主验证对象，其余执行器仅验证「触发后 argv 正确、占位帖→failed 兜底」路径。
- `@专家` 依赖 `~/.ntd/experts/` 或 bundled 专家存在；若本地无专家，用一条临时用户专家验证人设注入（`inject_expert_context` 拼装结果）。
- SSE 实时更新若一期未接入，以轮询兜底，功能不缺，仅体验降级（M4 补齐）。
