## 1. 设计总览

### 1.1 目标消息路由模型

```
飞书消息
 ├─ 内置斜杠命令（/feishupush /list /help /new /stop，精确匹配）→ 照旧
 ├─ 自定义斜杠规则（workspace_slash_commands 表，命令名精确匹配）
 │    ├─ command_type=todo → 触发 todo（照旧）
 │    └─ command_type=loop → 触发环路（照旧）
 └─ 其余一切消息（含未命中规则的 /xxx）
      └─→ 空间管家通路（butler_chat）
           ├─ 已配置管家 → 执行器聊天 + 管家专家 prompt 注入（session 连续）
           └─ 未配置管家 → 回复配置引导提示（不执行任何东西）
```

### 1.2 核心思路：组合现有三块积木，不新造子系统

| 积木 | 现成位置 | 管家通路中的角色 |
|------|---------|-----------------|
| 执行器聊天（session 连续 + 飞书回复） | `message_debounce.rs::handle_default_response_executor` | 改名 `handle_butler_chat`，作为管家执行底座 |
| 专家 prompt 注入 | `expert/inject.rs::inject_expert_message`（todo/wiki chat 通路同款） | 执行前注入管家专家 agent MD + 技能清单 |
| ntd CLI（todo/loop 全套子命令） | `cli/commands.rs` | 管家的「手脚」，能力写进专家规则 |

## 2. 命名决策（命名与功能一致，需求 2.4）

| 类别 | 旧名（删除/改名） | 新名 |
|------|------------------|------|
| DB 列 | `default_response_type` / `default_response_todo_id` / `default_response_loop_id` / `default_response_executor` | `butler_expert_name` / `butler_executor`（仅 2 列） |
| trigger_type | `default_response` / `default_response_executor` / `default_response_loop` | `butler_chat`（单一新值；旧值仅历史消息展示用） |
| listener 函数 | `route_slash_or_default_response` / `dispatch_default_response` / `debounce_push_default` / `debounce_push_executor_default` / `debounce_push_loop_default` | `route_slash_or_butler` / `dispatch_butler_chat` / `debounce_push_butler_chat` |
| debounce 函数 | `handle_default_response_executor` | `handle_butler_chat` |
| debounce 函数 | `handle_default_response_loop`（仅被 default_response_loop/slash_command_loop 共用） | `handle_slash_command_loop`（删 default 分支后只服务斜杠规则，名字如实反映） |
| API 字段 | `default_response_*` ×4 | `butler_expert_name` / `butler_executor` |
| 前端组件 | `DefaultResponseConfigPanel.tsx` | `ButlerConfigPanel.tsx` |
| 内置专家 | （无） | `workspace-butler`（空间管家） |

**`butler_expert_name` 而非 `butler_expert_id`**：专家在 `ExpertIndexManager` 中以名字为键（`get_expert_by_name`），存名字就得叫 name，避免 `_id` 后缀误导。

## 3. 数据层设计

### 3.1 Migration V95（`db/migration/v95.rs`）

幂等守卫风格对齐 V94（`table_has_column` 判定，半途残留态可自愈）：

1. `ALTER TABLE workspace_settings ADD COLUMN butler_expert_name TEXT`（守卫：列不存在才加）
2. `ALTER TABLE workspace_settings ADD COLUMN butler_executor TEXT`（同上）
3. 数据承接：`UPDATE workspace_settings SET butler_executor = default_response_executor WHERE butler_executor IS NULL AND default_response_executor IS NOT NULL`——已配置过执行器的工作空间升级后管家用同一执行器，行为不断档
4. `ALTER TABLE workspace_settings DROP COLUMN default_response_type` 等 4 列（SQLite ≥3.35 支持 DROP COLUMN；4 列均无索引/约束引用）
5. 测试：老库（v94 态 + default_response_executor 有值）升级后 butler_executor 承接成功、4 旧列消失、幂等重跑不报错

### 3.2 同步更新 `consolidated_schema.rs`

`workspace_settings` 建表语句改为最终形态（漂移测试会比对迁移链与合并 schema 一致性）。

### 3.3 entity（`db/entity/workspace_settings.rs`）

删 4 个旧字段，加 `butler_expert_name: Option<String>` / `butler_executor: Option<String>`。`system_prompt`、`delegate_max_rounds` 不动。

### 3.4 DAO（`db/workspace_setting.rs`）

`upsert_workspace_settings` 签名瘦身：

```rust
pub async fn upsert_workspace_settings(
    db: &Database,
    workspace_id: i64,
    butler_expert_name: Option<String>,  // Some("") = 显式清空管家专家
    butler_executor: Option<String>,     // Some("") = 显式清空管家执行器
    system_prompt: Option<String>,
) -> Result<(), sea_orm::DbErr>
```

- 增量语义沿用：None 不动，Some 覆写；空串语义从「loop_id=0 清空」改为「空串清空」（String 类型天然支持，去掉 0 哨兵特例）。
- 新建行不再有任何默认值（旧逻辑默认 `default_response_type="todo"` 随之消失）。
- `update_workspace_delegate_max_rounds` 的新建行口径同步去掉旧字段。

## 4. 消息路由改造（`services/feishu_listener.rs`）

### 4.1 `route_slash_or_butler`（原 `route_slash_or_default_response`）

```rust
if let Some(command_ctx) = Self::parse_slash_command(prep.content) {
    Self::dispatch_slash_command(...)   // 规则未命中 → 内部转管家，不再转默认响应
} else {
    Self::dispatch_butler_chat(...)
}
```

### 4.2 `dispatch_slash_command` 的三处兜底删除

| 现状 | 改为 |
|------|------|
| 无 workspace_id → `dispatch_default_response` | 记 warn 后转 `dispatch_butler_chat`（管家不需要 workspace_id？需要。见 4.4） |
| workspace_id 查询 DB 错误 → `dispatch_default_response` | 记 error 后转 `dispatch_butler_chat` |
| 规则未命中 → `dispatch_default_response` | 转 `dispatch_butler_chat`，消息原文（含 `/xxx`）交给管家 |

### 4.3 `dispatch_butler_chat`（替代 `dispatch_default_response`）

逻辑（每步小函数，≤30 行）：

1. 查 bot 的 workspace_id：失败/为空 → 记日志 + 发提示「bot 未绑定工作空间」；
2. 读 workspace_settings：查不到或 `butler_executor` 为空 → 发提示「本工作空间尚未配置空间管家，请在工作空间设置中选择管家专家与执行器」（`reply_butler_not_configured`）；
3. 已配置 → `debounce_push_butler_chat`：`trigger_type="butler_chat"`，`executor=Some(butler_executor)`，`todo_id=0`，params=None。

### 4.4 删除的函数

`debounce_push_default`、`debounce_push_executor_default`、`debounce_push_loop_default` 三个函数全部删除，收敛为单一 `debounce_push_butler_chat`。

### 4.5 `build_trigger_params` 处理

`models/todo.rs::build_trigger_params` 对非斜杠内容返回 `("default_response", params)`。剩余调用方 `feishu_history_fetcher.rs:375`（历史消息重放）也要走管家：trigger_type 字符串返回值改为 `"butler_chat"`，函数注释同步更新（slash 仍返回 `"slash_command"`，行为不变）。

## 5. 管家执行（`services/message_debounce.rs`）

### 5.1 `dispatch_execution` 分支调整

```rust
match msg.trigger_type.as_str() {
    "slash_command_loop" => Self::handle_slash_command_loop(...)   // 改名，删 default_response_loop 匹配项
    "butler_chat" => Self::handle_butler_chat(...)                 // 原 default_response_executor 分支
    _ => 普通 todo 执行（照旧）
}
```

历史消息重放/旧 trigger_type 不再产生，存量 PendingMessage 只在进程内存中（无持久化），无兼容负担。

### 5.2 `handle_butler_chat`（原 `handle_default_response_executor` 改名 + 注入）

在原函数开头加一步（其余逻辑不动）：

```rust
// 管家注入：执行时现读 workspace_settings 拿管家专家名，
// 配置变更立即生效，且 PendingMessage 结构零改动。
let message = match workspace_id {
    Some(wid) => {
        let expert = load_butler_expert_name(db, wid).await;   // 小函数，DB 失败静默 None
        inject_expert_message(expert_manager, expert.as_deref(), message, "butler chat: ")
    }
    None => message.to_string(),
};
```

- 专家未配置/找不到 → `inject_expert_message` 原样返回（既有静默回退语义），管家退化为纯执行器聊天；
- 注入发生在 debounce 合并后的 `merged_content` 上（多条消息合并为一次执行，注入一次）。

### 5.3 blackboard 不受影响

`services/blackboard.rs::chat_with_wiki` 只是「参考了该模式」的独立实现（自带 expert_name 参数与注入），不调用 `handle_default_response_executor`，改名零波及。

## 9. 内置「空间管家」专家（ntd-resource 仓库）

在 bundled 专家源头仓库新增 `workspace-butler` 专家，agent MD 要点：

- **角色**：工作空间管家，所有非斜杠消息的第一接收人；
- **能力清单**：`ntd todo list/create --workspace-id N`、`ntd loop ...` 等 CLI 用法（含 dev 18088 / 生产 8088 的 server 区分说明）；
- **行为准则**：执行动作（触发 todo/loop/创建事项）前先向用户确认；闲聊直接回复不触发任何动作；不确定时追问；
- **边界**：不伪造执行结果，触发动作以 CLI 真实返回为准。

本仓库侧：`bundled.rs` 同步机制无需改动（专家目录随 bundled sync 自动下发）。

## 11. 安全反思

- **越权**：管家继承执行器聊天通路的 workspace 隔离（executor_session 按 (workspace_id, executor) 隔离），不引入新的跨空间访问面；
- **注入**：管家专家名来自 DB（管理员配置），非用户消息直拼；用户消息经 `inject_expert_message` 包装为 prompt 文本，无 SQL/命令拼接；
- **误触发**：管家自主调用 CLI 触发 todo/loop 的风险由专家规则中的「动作前确认」准则约束（v1 行为准则级约束，非代码级硬门禁——已确认接受）；
- **CLI 可达性**：executor 进程内 `ntd` 需指向正确 server，实测验证。

## 12. 已知限制

- 每条管家消息都携带完整专家 prompt（session resume 模式下每轮重注），token 成本高于纯聊天；后续可优化为「仅新 session 注入」；
- 历史 `default_response*` trigger_type 的消息记录保留旧标签，不做数据迁移。
